# engine/imagegen

## Purpose
Pictures for RenderUI `Image` elements that carry a `prompt` instead of a URL (F174): the engine paints them on the operator's ComfyUI server (the 4070 Ti Super PC) and keeps them with the project. `annotate` runs synchronously on the one final spec of a RenderUI call in a project chat: each prompted Image gets an engine-only `image` state (**`UiImageState`** (`engine/bridge/protocol.ts:183`); its event is **`UiImageEvent`** (`engine/bridge/protocol.ts:193`)) the surface draws at once as a placeholder, and a job unless the picture is already made or already in flight. The model's turn never waits: jobs run one at a time beside it, and a `ui.image` event keyed on the image key (never on a surface) tells the page when a picture is ready. Each picture lands in `<project>/images/<key>.png` beside a JSON sidecar recording exactly how it was made — the prompt, seed, checkpoint, the filled graph submitted and ComfyUI's output names — which a later image → 3D → STL step will read. An unset, unreachable or misconfigured server is a named reason in the card, the tool result and the log; nothing crashes. The same `annotate` call also marks each Image whose src is the project-relative path of an image file the model wrote (`annotateFileImages`): `{ status: 'file', slug, path }` in a project chat — served by the file route (`servedProjectFile`), needing no ComfyUI — or `off` elsewhere. This package may import from `engine/projects/` (`layout.ts`, `history.ts`), `engine/genui/spec.ts` (`projectImagePath`, the file-path rule) and the type-only `engine/bridge/protocol.ts`; it never imports `conversationLoop`. Status: the loop hands it each final RenderUI spec (`emitFinalUiRender`, through the loop's `images` option) and calls its `warm` at the start of every project-chat turn, `ui.image` is an `EngineEvent`, and `main.ts` builds it, probes in the background and shuts it down in `cleanShutdown`; the dashboard serves the pictures (`GET /api/projects/:slug/images/<key>.png|json`, `engine/dashboard/server.ts`), a reloaded chat gets each picture's state back (`withValidatedSurfaces`, `engine/projects/api.ts`), and the page draws every state and fills it in on `ui.image` (`engine/genui/CLAUDE.md`).

## Important types & functions
- **`comfyConfig`** (`config.ts:159`) — `(env) → { ok, cfg } | { ok: false, reason }`, never throws; run once when `ImageService` is constructed, so a change needs an engine restart. Refusals: unset (`UNSET_REASON`, `config.ts:118`, names `LOCALCODE_COMFYUI_URL` and an example address), a non-http(s) URL, a size that is not `WxH` in multiples of 64 from 512 to 2048 (refused, never defaulted), and every workflow-file problem prefixed `LOCALCODE_COMFYUI_WORKFLOW:`.
- **`comfyUrl`** (`config.ts:38`), **`comfySteps`** (`config.ts:62`) and their siblings — one pure reader per variable in the shape `envVarScan.mjs` derives a default from; the clamps (steps 1–150, cfg (0, 30], timeout 30–3600 s) apply to env values only.
- **`ComfyConfig`** (`config.ts:99`) — base URL (path prefix kept, no trailing slash), host, port, configured checkpoint or null (pick at probe), the workflow (`ComfyWorkflow`, `config.ts:89`: source, sha256 or `builtin-1`, graph, `usesCheckpoint`), size, steps, cfg, timeout, sampler, scheduler, negative prompt.
- **`BUILTIN_WORKFLOW`** (`workflow.ts:34`) — CheckpointLoaderSimple → two CLIPTextEncode → KSampler → VAEDecode → SaveImage, placeholders as whole string values.
- **`parseWorkflow`** (`workflow.ts:80`) — refuses non-JSON, a UI-format export (top-level `nodes` + `links`), a node that is not `{class_type, inputs}`, an unknown `{{x}}`, a numeric placeholder inside a longer string, no `{{prompt}}`, and no SaveImage node.
- **`fillWorkflow`** (`workflow.ts:138`) — walks the parsed object on a `structuredClone`; a whole numeric token becomes a number, a string token is replaced in place by a function replacement (so `$&` and a literal `{{seed}}` in a prompt stay inert); keys, `class_type` and `_meta` are never touched.
- **`ComfyClient`** (`client.ts:52`) — every call carries its own `AbortSignal.timeout` (`CLIENT_TIMEOUTS`, `client.ts:34`: stats 3 s, models and nodes 5 s, submit 15 s, history 5 s, view 30 s, interrupt/queue 2 s), and every failure is a **`ComfyError`** (`client.ts:18`) whose `reason` the card and the model show as is; an unreachable server names `--listen` and the firewall port. `submit` (`client.ts:133`) returns the server's `prompt_id`, which wins over the one sent (older servers ignore it); a 400 becomes `ComfyUI refused the workflow: … node <id> (<class>): …`, cut to 300 characters, and is the one `ComfyError` marked `refused` (ComfyUI queued nothing, so the worker cancels nothing). `history` (`client.ts:150`) returns null while pending. `download` (`client.ts:166`) refuses a bad reference before asking, an over-cap body by Content-Length or while streaming, and bytes without the PNG signature.
- **`probeComfy`** (`client.ts:258`) — `/system_stats`, then the checkpoint (only when the workflow has `{{checkpoint}}`: a configured name must be listed exactly; otherwise the alphabetically first `/juggernaut/i`, else `/xl/i`, else a refusal — the built-in graph is SDXL-only), then `/object_info/<class>` for every class the workflow uses. Never throws. A good answer (`ProbeResult`, `client.ts:243`) carries, beside every field it had, the server's `/models/checkpoints` list as sent (`checkpoints`, strings only) when the workflow has `{{checkpoint}}`, and none when it has not; `runJob` checks the checkpoint a picture was keyed on against it before the POST (F179). The service takes a checkpoint found gone off a good answer read before it left, list and count (`withoutCheckpoint` (`service.ts:175`); `dropVanished`, below).
- **`imageKey`** (`store.ts:194`) — 32 hex of sha256 over the canonical JSON of prompt, negative, seed, size, steps, cfg, sampler, scheduler, checkpoint (the one that will paint: the configured one, else the pick known at annotate — the last good probe's, refreshed by `warm` at each project-chat turn — else `'auto'`, before any probe has picked or after `dropVanished` unset the pick until a probe picks again; **`ImageService.keyFields`** (`service.ts:549`), F179) and workflow sha; known before any network call; `KEY_RE` (`store.ts:37`) is a key's only spelling, and the page checks its own copy of it before it builds a URL. **`seedFor`** (`store.ts:182`) — the first 48 bits of sha256(prompt + negative): the default seed, so the same prompt paints the same picture everywhere in a project; element ids are left out so a renamed id never repaints. An Image's own `seed` (a safe non-negative integer the validator kept) replaces it — the same prompt with another seed is another key, another take (`ImageService.keyFields`; F176: with the derived seed the only one, a second take had no spelling); the same prompt and seed is the same picture.
- **`ImageSidecar`** (`store.ts:64`) — schema 1: status, reason, `runId`, every generation parameter (`seed` with `seedFrom: 'model' | 'prompt'` saying whether the Image gave it or `seedFor` derived it; absent on records from before the field, any other value reads as no record), `apiPrompt` (the filled graph submitted), `comfy` (host, promptId, outputs), sha256/bytes, timings (`queueMs` enqueue→submit, `genMs` submit→history entry, `execMs` from ComfyUI's own timestamps) and the origin. **`readSidecar`** (`store.ts:331`) type-checks every field; a bad file reads as no record. It reads only a regular file under a size cap (`readSmallFile`, opened non-blocking and checked on the descriptor), so a planted FIFO, a link to /dev/zero or a huge file is no record at once instead of a frozen engine thread.
- **`readOrigins`** (`store.ts:365`) / **`recordOrigins`** (`store.ts:388`) — `images/index.json`, `<chatFile>#<toolId>#<elementId>` → key, a null-prototype map keeping only well-formed pairs, capped at `ORIGINS_CAP` (oldest dropped); read the same guarded way.
- **`storeFault`** (`store.ts:293`) — why the engine must not store pictures in a project: `images/` and `.cynco/tmp/` must each be a real folder inside it (not a link or junction, nothing whose real path leads out) or not exist yet, and `.gitignore` a regular file or absent. Checked at annotate (every picture `off` with the reason), at job start and again at the PNG write (the job fails with it); `writeSidecar`/`recordOrigins` refuse on their own too. Every write is a fresh file created `wx` (an unguessable temp name, or the `.part` after removing whatever was there) and renamed into place, so a link planted at a target or a temp name is replaced, never written through.
- **`promptedImages`** (`store.ts:453`) — every `Image` with a non-empty prompt reachable from the root, in draw order, with its `seed` when it is a safe non-negative integer (checked again here: a replayed transcript spec is unvalidated): the one definition both `annotate` (what to queue) and `withValidatedSurfaces` (what to look up on reload) use.
- **`fileImages`** (`store.ts:471`) — every `Image` whose src is a path in the project (`projectImagePath`, checked again here so no unchecked path reaches an annotation) and no prompt, in draw order. **`annotateFileImages`** (`store.ts:489`) — gives each its engine-only state and takes the src out of its props: `{ status: 'file', slug, path }` in a project chat, `off` with `FILES_ONLY_REASON` (`store.ts:44`) elsewhere; run by `annotate` on the live frame and by `withValidatedSurfaces` on reload, whether or not the file exists.
- **`servedProjectFile`** (`store.ts:583`) — the file route without HTTP: the path must pass `projectImagePath` (400 `bad file path`), the file must be a regular file really inside the project with one name (`realInside` follows symlinks; a link out, a hard link — a second name whose content may live outside the project — a folder or nothing there is 404), at most 32 MB — an SVG `SVG_CAP_BYTES` (`store.ts:46`) = 2 MB — (413), and carry its format's signature (415): PNG, JPEG `FF D8 FF`, GIF87a/89a, RIFF…WEBP, or for `.svg` `isSvg` (`store.ts:123`), which reads the head only: the first tag after an optional BOM, whitespace, the XML declaration (`<?xml` then whitespace — a processing instruction such as `<?xml-stylesheet` is not skipped), a DOCTYPE (its quoted literals skipped, so a `>` inside one is not its end; an internal subset is refused — entities are never served) and comments is `<svg`. Returns the bytes with the extension's fixed type. **`isProjectFile`** (`store.ts:569`) — the same existence check, for the note.
- **`servedImage`** (`store.ts:515`) — the image route without HTTP: `<32 hex>.png|json` only, `realInside` both the project and its `images/`, a regular file, at most 32 MB, PNG signature checked (415 otherwise); `.json` serves `publicSidecar` (`store.ts:501`) only.
- **`storedImageState`** (`store.ts:609`) — what a reloaded chat's Image shows, found through the origin index (the exact picture shown live, even after the knobs changed); a queued/running record under another `runId` reads `failed: interrupted …` (`effectiveStatus`, `store.ts:357`), a `done` record whose PNG is gone reads `failed`, a missing or unreadable record reads `off`, and an origin the index does not hold reads `off: this picture was not generated`.
- **`ImageAnnotator`** (`service.ts:55`) — what the loop holds (`ConversationLoopOptions.images`): `annotate(spec, at: AnnotateAt)` → **`Annotation`** (`service.ts:53`) `{ note, start }`, and the optional `warm()` it calls at the start of every project-chat turn. **`AnnotateAt`** (`service.ts:44`) is the bound project chat (`{ dir, slug, chatFile }`, or null for a coding session), the toolId, the surface and whether the call was cut off.
- **`ImageService`** (`service.ts:181`) — constructor deps `{ env?, fetchFn?, emit, now?, log?, pollMs?, timeoutMs? }` (the last two are test seams). `probe` (`service.ts:252`) logs `[imagegen] ready: …` / `not ready: …` / `off: LOCALCODE_COMFYUI_URL unset` once per state change, and keeps a good probe's checkpoint (`lastCheckpoint`) through later failures for `keyFields`. `warm` (`service.ts:269`) — synchronous, never throws — starts a background probe (through `runProbe`'s dedupe) unless one is running or the last one finished, whatever it answered, less than 30 s ago (`WARM_MIN_AGE_MS`, `service.ts:78`, measured from `lastProbe`, so a server that keeps failing is asked at most every 30 s), and does nothing when the config is refused or the engine is shutting down; the loop calls it at the start of every project-chat turn, tens of seconds before the turn's RenderUI is annotated, so the pick is fresh when the turn's keys are made (F179). `ensureReady` (`service.ts:358`) reuses a failure for 60 s and a success for 10 minutes (each edge pinned with an injected clock), and starts (or joins) a probe only when the cache is empty or stale. **`runProbe`** (`service.ts:287`) joins the probe running, else starts one: **`startProbe`** (`service.ts:301`) numbers each probe as it starts (`probeSeq`, which `dropVanished` reads) and judges the answer of one started before a drop (`dropVanished`, below: one that still picks the gone checkpoint is not used and a fresh probe follows; one that picks another and only lists it is used without it). A failure never replaces a good probe still inside its 10 minutes (F179): one failed warm-up used to fail, with no POST, every job that started in the next 60 s while the server answered. Only a probe `warm` or `probe` starts, or the fresh one that follows a stale answer (`dropVanished`, below), can meet such a probe — `ensureReady` starts one only on a stale cache and `dropVanished` only after clearing it — and the failure still logs `not ready`, keeps `lastCheckpoint`, and is the last check a call's note reports (`The last check of ComfyUI failed (<reason>); if it still fails, the cards will say so.`).
- **`ImageService.annotate`** (`service.ts:372`) — synchronous, never throws. `annotateFiles` (`service.ts:387`) runs first: each file Image gets its file state (a project chat) or `off` (elsewhere) whatever ComfyUI is, and the note names a file that is not a regular file inside the project (`Files: not in the project — <paths>; write the file first, or describe the picture in "prompt" and the engine generates it.`; nothing is said when every file is there; `Files: not shown — files are shown in project chats only.` in a coding session). Then `annotatePictures` (`service.ts:407`), whose throw is logged and turns every prompted Image `off` with the reason; the note puts files before pictures. Pictures are off for no project, a config refusal, a cut-off call, an engine shutting down, a store the model tampered with (`storeFault`), past 18 distinct pictures per call (`PER_CALL_CAP`, `config.ts:28`: three designs × six takes, ~3 minutes of GPU at ~10 s a picture (gen 9.4–10.4 s, 40 steps, 1024², measured 2026-10-13) on the SDXL base — the operator's ask; it was 6, one design's takes, F176), a full queue (48 waiting, `QUEUE_CAP`, `config.ts:30`); otherwise in flight → that job's status, done with its PNG → `done`, the same picture under its `'auto'` key (`autoTwin` (`service.ts:566`): asked before the first probe or made before F179 — a running or finished one only when its record names the checkpoint the new key names; a queued one has taken no pick yet, so the join pins it to that checkpoint (`Job.pinned`, `service.ts:97`) and it paints that one whatever its own probe picks, unless that checkpoint is found gone before the job paints — its probe's list without it, or a refusal naming it — which unpins it) → that key's status, with the origin on that key, anything else → a `queued` sidecar, an origin and a job. Returns the tool-result `note` (`Pictures: …`, counting distinct pictures, not Images — Images that repeat a prompt and seed are one picture, and the note says so: `N Images repeat the prompt and seed of another — give each take its own "seed" for another picture`; the server's address is never in it, since the prompt says never to call it and `engine/projects`' fence refuses a command at it — the `[imagegen]` log lines carry it; past three distinct generating it also says the wait — `About <jobs>×<s> s at the last measured pace` from the last picture's `genMs`, with the jobs ahead in the queue counted and named, or `The first takes longer while the model loads` before any was measured) and `start`, which kicks the worker after the final frame. A call whose pictures are all made already queues nothing, so no job's commit would carry the origins it recorded: it commits `images/index.json` (and `.gitignore`) itself, beside the turn (`images: <n> shown again`).
- **`ImageService.runJob`** (`service.ts:640`) — probe, then the probe's checkpoint list (F179; no checkpoint configured, the workflow has `{{checkpoint}}`): a key's checkpoint the list no longer holds fails the job there, before the sidecar says `running` and before any POST, with our own reason — `the checkpoint <name> this picture was keyed on is no longer on the image server — ask again and it is painted on <pick>`, the second half only while there is a pick (`lastCheckpoint`, what the same ask keys on now) — and a pin it no longer holds is let go (`[imagegen] <key8>: ComfyUI no longer lists <name>, which an ask pinned this 'auto' picture to; it paints on the probe's pick, <pick>`): the job's key says `'auto'`, so it paints on the pick. Either goes to `dropVanished` (`service.ts:793`), described below. Then fill with the checkpoint the job was asked with (only a job still saying `'auto'` — asked before any probe, and pinned by no join or unpinned since — takes the probe's pick, which the sidecar then records; a newer pick is logged beside it, never painted, so a key and its picture always agree — F179), sidecar `running` with `apiPrompt` BEFORE the POST, submit (a 400 refusal of the checkpoint painted with — the list was read before it left — goes to `dropVanished` too), emit `running`, poll `/history` every `pollMs` (three failed polls in a row give up). Once the POST may have reached ComfyUI, every give-up but a 400 refusal — a lost POST answer, the failed polls, the deadline, a throw — first withdraws the prompt (interrupt + dequeue by id), so the next job never makes two prompts on the server. Then read `execution_error`/`execution_interrupted`, pick the first `type: 'output'` image across outputs by node id, download to `.cynco/tmp/<key>.part` (created `wx` after removing anything planted there), rename to `images/<key>.png`.
- **`ImageService.dropVanished`** (`service.ts:793`) — runs, while no checkpoint is configured and the workflow has `{{checkpoint}}`, when `runJob` finds the checkpoint a job was keyed on or pinned to gone from the server: the probe the job trusts no longer lists it (before the POST), or ComfyUI refuses the POST (400) naming it — the fallback for a list read before it left. Only a refusal of the checkpoint painted with counts: ComfyUI's value_not_in_list detail is `<input>: '<name>' not in [...]` (or `(list of length N)`), matched as `'<name>' not in`, so a refusal of another loader whose list merely names the checkpoint does not. The drop always records the checkpoint and the number of the last probe started (`vanished`, a map of every checkpoint found gone, so a second drop while a probe runs cannot make that probe's answer forget the first), even when nothing else is to be done; a probe started before them is judged against all of them. Every queued job pinned to that checkpoint goes back to `'auto'` and paints what its own probe at job start picks. While the checkpoint is still the pick, `lastCheckpoint` and the cached probe are cleared: until a probe answers with a pick a picture asked keys `'auto'`, and one painted on the vanished checkpoint under its `'auto'` key still reads as made; once one picks another, that picture keys on it and is painted again (F179). A probe then starts at once; one already running is joined instead, its answer judged as below, and a fresh probe follows it too when it fails (`reprobeAfter`), so a blip on a needless extra probe cannot fail the pictures behind for 60 s. A pick that already names another checkpoint (a probe since) is kept, and so is a cached good probe whose list still names the checkpoint: that list was read before it left, so the checkpoint is only taken off it (`withoutCheckpoint`, its `at` unchanged) and no probe starts — every job behind keyed on the checkpoint then fails in `runJob` before any POST with our reason, and every job keyed on the pick still paints (F179 review, round 2: Juggernaut installed and picked, the base then removed, three takes keyed on the base — the drop did nothing, and takes 2 and 3 went out and were refused with ComfyUI's text; round 3: clearing that probe and probing again let one failed probe become the only answer left, and every picture behind — those keyed on Juggernaut, still on the server, too — failed with no POST for 60 s). A probe started before the drop read the server's list from before it, so `startProbe` judges its answer: a good one that still picks the checkpoint is not used — neither `lastCheckpoint` nor the cache; logged `[imagegen] a probe started before <name> left the server still picks it; not used — probing again` — and a fresh probe follows it; a good one that picks another and only lists it is used, as the pick and in the cache, with the checkpoint taken off its list (logged `[imagegen] a probe started before <name> left the server still lists it; used without it`); one that neither picks nor lists it read the server after it left and is used as it is. Whoever waits on a probe a fresh one follows (a job's `ensureReady`, `whenIdle`) gets the fresh one's answer: it replaces the other as the probe running before that one settles (F179 review: the probe a drop joined had read the list before the checkpoint left, and its good answer made the checkpoint the pick again, cached for 10 minutes, until one more picture was refused). Logged as `[imagegen] <key8>: ComfyUI no longer has <name>` followed by what it did (`; probing again for the pick (…)` after clearing the pick, `; the trusted probe still listed it — taken off that list (the pick stays <pick>)` after trimming the cached probe, `; <n> queued picture(s) pinned to it …`); with no pick to clear, no pin to undo and no cached list naming the checkpoint, it does nothing else and logs nothing.
- **`ImageService.whenIdle`** (`service.ts:601`) — resolves once the worker has nothing left to do, commits included (a cache hit's too), and once a probe still running (a `warm`'s, a `dropVanished`'s, or the fresh one that follows another) has finished; for tests and `check.ts`, never the loop.
- **`ImageService.record`** (`service.ts:868`) — sidecar, journal (`image.generated` / `image.failed`), `ui.image` event and log line in one synchronous step, then `finish` (`service.ts:900`) commits.
- **`ImageService.shutdown`** (`service.ts:937`) — marks the running job and every queued one `failed: the engine stopped before this picture finished — ask for it again`, interrupts and dequeues the running prompt by id, commits; bounded to 3 s. It cancels only while ComfyUI may still hold the prompt (`Job.onServer`: never once it finished, was refused or was withdrawn); a POST still in flight is waited for, so the cancel names the id the server answered with and lands after the prompt is queued. The cancel and the commits (a cache hit's still running among them) run side by side, so a ComfyUI that stops answering costs the bound and no more — pinned with `/interrupt` and `/queue` both hung.

## Data flow
1. At engine start `new ImageService({ emit })` runs `comfyConfig` once; `probe()` checks the server in the background and logs its state. At the start of every project-chat turn the loop calls `warm()`, which checks it again in the background when the last check, whatever it answered, finished 30 s ago or more; a failed check leaves a good one still inside its 10 minutes trusted.
2. After the final `ui.render` frame of a RenderUI call in a project chat, `annotate` gives each file Image its file state (no job, no server) and each prompted Image its `image` state, writes `queued` sidecars and the origins (after `ensureImageIgnore` (`store.ts:408`) adds `images/*.png` to `.gitignore`; a planted link named by `storeFault` turns every picture `off` instead), and returns the note for the tool result. `start()` kicks the worker.
3. The worker takes jobs FIFO, one at a time across the engine (dedupe on `dir|key`, so two surfaces showing one prompt share one job): `runJob` → `record` emits `ui.image running`, then `done` or `failed` with the reason → `commitHistory` (`engine/projects/history.ts:47`) commits `.gitignore`, the sidecar, `images/index.json` and `journal.md`. A call that queued nothing (every picture already made) commits the origin index it changed on its own.
4. The page fills every node showing the key in that project (its picture map is keyed on slug and key: two projects asking for one prompt run two jobs under one key) and fetches a done picture with the token into a blob URL; a reload (`withValidatedSurfaces`) asks `storedImageState` per Image through the origin index; the route (`engine/dashboard/server.ts`, `imageResponse`) serves bytes through `servedImage` under inert headers (`image/png` from the extension, `nosniff`, a sandbox CSP, no ACAO). A file Image is fetched from `GET /api/projects/:slug/files/<path>` (`fileResponse` there: the extension's type, `nosniff`, the sandbox CSP, `no-store`), again on every frame that shows it; an SVG reaches the `<img>` as a `data:` URL, never a same-origin blob URL, so a script inside it can run under no origin that holds the token (F175 review).

## Gotchas
- Configuration is environment variables only (`LOCALCODE_COMFYUI_*`): a profile file replaces the bundled one wholesale, and a YAML typo there would drop the setting silently. A change needs an engine restart.
- Never `fetchGuarded`/`validateUrl`: they refuse 192.168/16, and the ComfyUI URL is the operator's choice, not the model's. Plain `fetch` through an injectable `fetchFn`, as `JlensClient` does.
- The server's output filename is never a local path. It goes back to ComfyUI only as a `/view` query parameter (`URLSearchParams`); the local file is named from the key alone. Pinned by the hostile-filename tests (`../../x.png`, `C:\x`).
- The sidecar is written `running` before the POST, so a crash leaves a record naming the prompt id. Its `runId` (`RUN_ID`, `store.ts:36`) is the engine process that queued it: any reader that finds `queued`/`running` under another `runId` reports `failed: interrupted — the engine stopped before this picture finished`, and `annotate` re-queues it — a crash needs no extra plumbing. Resume after restart is not built; the sidecar keeps `promptId` so a later change could poll `/history/{id}` instead.
- Pictures are found by name only (`<32 hex>.png`), and a PNG is never named in a commit: `images/*.png` is git-ignored, and naming an ignored file makes `git add` exit 1 and journal `history.failed`.
- Everything under `images/` is untrusted on read: the model can write anywhere in a project (`gradeProjectCall`), so keys are checked against `KEY_RE`, sidecars are type-checked, origins land in a null-prototype map, every read takes only a regular file under a cap, and the route checks the PNG signature and refuses links out of the project. Nor does the engine write through anything planted: a link at `images/`, `.cynco/tmp/`, `.gitignore`, a `.part` or a temp name is refused or replaced, never followed — the fence `gradeProjectCall` puts on the model's file tools binds the engine's own writes too; the project's own `journal.md` is fenced the same way (`appendJournal`/`readJournal`, `engine/projects/CLAUDE.md`).
- A file Image (F175) is the model's own file, read under the same guards as a picture and its own: the route checks the decoded path against the validator's rule before any join, follows symlinks with `realInside` and refuses a hard link (a second name whose content may live outside the project: 404, like a link out), reads only a regular file under its cap (an SVG 2 MB) through `readSmallFile`, checks the format's signature and serves it under a fixed type, never cached, so the model can rewrite a template and show it again. An SVG goes only into an `<img>` on the page, where it runs no script and loads no external resource; a DOCTYPE with an internal subset is refused outright. A name that is not ASCII, starts with a dot, or holds `..`, a backslash or a quote cannot be shown — the validator's hint gives the path rule, so the model can rename the file. Files need no ComfyUI: an engine with `LOCALCODE_COMFYUI_URL` unset still shows them.
- An absent `/history/{id}` entry (`{}`) means pending or running: ComfyUI adds the entry only when the prompt ends, successfully or not.
- `MeshToFile3D` writes GLB only, and its history entry sits under `"3d"`, not `"images"`: the output picker (`outputRefs`) is generic over the kind for that later step, and an STL needs a local GLB → STL converter.
- An image key names the checkpoint that paints (F179). With `LOCALCODE_COMFYUI_CHECKPOINT` unset (the operator's setup) every key said `'auto'`, so once Juggernaut XL was installed and picked, a prompt and seed already painted on the SDXL base was a cache hit and showed the old picture — "Juggernaut in the checkpoints folder is the upgrade" was false for every take already made. Now `keyFields` names the configured checkpoint, else the pick known at annotate (the last good probe's, kept through failed probes: annotate asks the server nothing, and a picture already made still shows while the server is away), else `'auto'`; `runJob` paints with the checkpoint the key names, so a key and its picture always agree and the old picture stays where its chat's origin points. The pick is refreshed at each project-chat turn (`warm`, at most every 30 s), at a job's start once the cached probe is stale, and at once after a drop unsets it (`dropVanished`), so a checkpoint added or removed since is seen at the next turn that starts 30 s or more after the last probe — not only at an engine restart or the 10-minute reuse, which once left a whole call of up to 18 pictures keyed and painted on the checkpoint it replaced. A failed probe never replaces a good one still inside its 10 minutes, and `warm`'s 30 s run from the last probe whatever it answered: one failed warm-up once failed every picture queued behind the one painting for 60 s, with no POST, while the server answered. A checkpoint removed from the server is found before any POST: the probe carries the server's checkpoint list, so a picture keyed on it fails with our own reason (`the checkpoint <name> this picture was keyed on is no longer on the image server — ask again and it is painted on <pick>`), and a queued `'auto'` picture pinned to it paints on the pick. ComfyUI's 400 (`Value not in list: ckpt_name: '<name>' not in [...]`) is the fallback for a list read before the checkpoint left — matched as `'<name>' not in`, so another loader's refusal that merely lists the name does not count. Either drops it (`dropVanished`): queued `'auto'` jobs pinned to it go back to `'auto'`; while it is the pick, the pick is unset, so a picture asked keys `'auto'` only until a probe picks, and a picture painted on the removed checkpoint under its `'auto'` key is painted again on the new pick, not shown as made — and a probe starts at once, or the one running is joined, a fresh one following it when it fails; while the pick is already another (Juggernaut installed and picked, the base then removed, takes still keyed on the base), the pick stays and so does the trusted probe, with the removed checkpoint taken off its list and no probe started (F179 review: clearing that probe and probing again once let one failed probe become the only answer, and every picture behind — those keyed on Juggernaut, still on the server, too — failed with no POST for 60 s). A probe running at the drop is joined, not passed over: it started before the drop and read the list from before it, so an answer that still picks the removed checkpoint is not used and a fresh probe follows (one such answer once made the checkpoint the pick again until one more picture was refused), and a good answer that picks another but still lists it is used with that name taken off its list. So, while the checkpoint stays off the server, the only picture keyed on it that is POSTed is the first to trust a list read before it left, which ComfyUI refuses; every one behind it fails before any POST with our reason — at once when the pick was already another, once the new probe answers when it was the pick (a cached list still naming the base, kept whole because the pick was Juggernaut, once let takes 2 and 3 of three go out and be refused with ComfyUI's text) — and every picture keyed on the pick still paints. A picture keyed `'auto'` — asked before the first probe, or any made before F179 — is shown again (`autoTwin`) only when it is painting or was painted with the checkpoint the asking key names; a queued one has taken no pick yet, so the ask that joins it pins it to its own checkpoint (unpinned again if that checkpoint is found gone — its probe's list without it, or a refusal — before the job paints). Pinned in `engine/__tests__/imagegen/service.test.ts` ("the key names the checkpoint that paints").
- The system prompt never varies with configuration: whether ComfyUI is set up, reachable or refusing reaches the model only through the tool result's `Pictures:` note, so the prompt stays byte-stable and the prefix cache holds.
- Events carry the key, slug and status only, never bytes: the loop's emit fans out to the TUI too, which has no use for megabytes. The page fetches the PNG from the gated route.
- One job at a time across the engine, FIFO; a job captured its `dir`, `slug` and `chatFile` at annotate time, so an abort, halt or project switch leaves it alone and it finishes into the project it was made for. A settled job still committing is not "in flight": a re-request the moment a picture fails gets a fresh job, and the old failure's event has already gone out. A job given up after its POST is withdrawn from ComfyUI before the next one goes out.
- The `[imagegen]` log lines are the latency evidence: one per RenderUI call (`<n> pictures — <q> queued, <c> already made[, <o> not generated: <reason>]`) and one per job (`<key8> done in <t>s (queue <qw>s, gen <g>s[, exec <e>s]) …` or `failed after …`). `queue` is enqueue → submit, `gen` is submit → history entry (ComfyUI's own waiting and a cold model load included), `exec` is ComfyUI's `execution_start` → `execution_success`. Read them beside the loop's `[loop] message_stop … elapsed=` line.
- The chat never drives ComfyUI itself (F176): the project prompt says the engine paints and never to call an image server, write a workflow or save renders (`engine/genui/prompt.ts`, `engine/projects/profile.ts`), and `engine/projects`' grader refuses a Bash command, or a file about to be written, that would (`comfyFence`). The live run of 2026-10-12/13 wrote a six-KSampler workflow per design and drove the server through Bash because the pipeline could not do what the design needed: a prompt cut at 1,000 characters, one seed per prompt (no second take), six pictures a surface. What it needed is now in the pipeline — a prompt as long as the design (bounded by `LIMITS.stringChars`), a `seed` per take, 18 pictures a call with the wait said — and ComfyUI's own `CLIPTextEncode` chunks a prompt past 77 tokens by itself, so a long prompt needs no `ConditioningCombine` in a custom workflow either.
- The build container has no ComfyUI: the tests run against `engine/__tests__/imagegen/mockComfy.ts`, a `node:http` fake on port 0 with the real routes, a call log and failure modes (never finishes, hostile filename, oversized, not a PNG, 400 `node_errors`). A real server is proved only with `bun engine/imagegen/check.ts --generate "<prompt>"` on the operator's PC.
- Shutdown interrupts by `prompt_id` only, and only a prompt of ours that ComfyUI may still hold — an older ComfyUI may treat `/interrupt` as global, which is acceptable only because it then stops our own job. One case is weaker: a POST whose answer was lost is withdrawn by the id sent, and on an older server that ignores client ids and interrupts globally, that may stop whatever is running if ours was still queued — accepted, as the alternative leaves our prompt on the GPU beside the next one. A dispatch swap (F141) loses in-flight pictures the same way; they read `failed` and a re-render re-queues them.
