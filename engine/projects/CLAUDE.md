# engine/projects

## Purpose
Projects mode: a non-code project (a diorama, a cookbook) as a plain folder under a projects home, independent of `cyncoHome` and of the engine loop. `layout.ts` owns the folder shape — `project.json`, `instructions.md`, `knowledge/`, `chats/`, `artifacts/`, `plan.md`, `inbox/`, `journal.md` — plus the file indexes and the append-only journal that every later feature (ingestion, search, chat, tools, `/api/projects/*`) reads and writes. `registry.ts` keeps a `registry.json` cache of every project under a home so the TUI/dashboard can list projects without walking the filesystem each time, but treats that cache as disposable: any staleness rebuilds it from the folders. `history.ts` puts a git repo under each project folder and commits after writes, invisibly — a user never runs git, and a commit failure is reported and journaled, never thrown. A project may also hold `images/`, the pictures its chats' RenderUI Images asked for (F174): `engine/imagegen` owns that folder — `<key>.png` (git-ignored), a `<key>.json` sidecar each and an `index.json` of origins — through this package's `writeJsonAtomic`, journal and history, and it is not under `knowledge/` or `artifacts/`, so `rescanProject` never journals a picture as unindexed. A chat's Image may also show any png/jpg/gif/webp/svg file the model wrote into the project, by its relative path, through `GET /api/projects/:slug/files/<path>` (`servedProjectFile`, `engine/imagegen/store.ts`). This package never imports from `engine/bridge/`; later tasks wire it into the engine from the other direction.

## Important types & functions
- **`ProjectMeta`** (`layout.ts:14`) — the `project.json` shape; `schema: 1` is checked on every read so a future schema bump can't be silently misread.
- **`createProject`** (`layout.ts:139`) — lays out every file/folder a fresh project needs (`knowledge/`, `chats/`, `artifacts/`, `inbox/`, `.cynco/index/`, the two index.json, `plan.md`, `.gitignore`, `journal.md`) and appends the `created` journal line. It makes no `images/`: `engine/imagegen`'s `ensureImageIgnore` appends `images/*.png` to `.gitignore` before a project's first picture, so a project made before F174 and a new one take the same path.
- **`SLUG_RE`** (`layout.ts:50`) — the one spelling of a valid slug (`/^[a-z0-9-]{1,64}$/`); `projectDir` (`layout.ts:52`) throws a named `Error` and `readProject` (`layout.ts:160`) returns `null` for anything else, so a slug decoded from a path segment (e.g. `..%2Foutside` → `../outside`) can never resolve outside the projects home even when an api.ts function is called directly.
- **`isInside`** (`layout.ts:62`) — lexical: case-folded on win32, accepts the root itself. Never the only check on a path a model or page names — a junction or symlink inside the project passes it while pointing anywhere; use `realInside`.
- **`realInside`** (`layout.ts:122`) — `isInside` on real paths: `realPathOf` (`layout.ts:95`) resolves the deepest existing ancestor with `realpathSync.native` (fallback `realpathSync`), follows a dangling link to its target, and re-appends the not-yet-existing tail; the root is resolved the same way. Returns `{ inside, real }` so a refusal names where the call would really land (spec §5, "no symlink escapes"; final review I2). Used by `gradeProjectCall` and AddToKnowledge-by-path.
- **`isReservedFileName`** (`layout.ts:129`) — `index.json` in any case is each area's own file index (`RESERVED_FILE_NAME`); SaveArtifact, AddToKnowledge (source and destination name) and `promoteArtifactApi` all refuse it by name, or the artifact/knowledge records would be overwritten (final review I1).
- **`JournalEvent`** (`layout.ts:18`) — the closed set of journal event names: `created`, `knowledge.added`/`.removed`/`.unindexed`, `artifact.saved`/`.unindexed`/`.removed`/`.promoted`, `chat.opened`/`.renamed`, `index.rebuilt`, `history.failed`, `registry.rebuilt`, and `image.generated`/`image.failed` (`engine/imagegen/CLAUDE.md`). The History tab shows the name verbatim, so a failure never rides a success name (`artifact.unindexed`, not `artifact.saved … not indexed`).
- **`writeJsonAtomic`** (`layout.ts:133`) — every JSON write here: a fresh file under an unguessable temp name, created `wx`, then renamed into place, so a link planted at the target or at a temp name is replaced, never written through. Exported for `engine/imagegen`'s sidecars and origin index (F174).
- **`appendJournal`** (`layout.ts:206`) — appends one journal line per event, through `journalAppend` (`layout.ts:251`): `journalFault` (`layout.ts:236`) `lstat`s `journal.md` first, and a link, a folder, a FIFO or anything but a regular file (or an absent one, which the append creates) drops the line with the reason and the line logged — never written through, never thrown; an append that fails is logged the same way (review of F174: the same class as the image store's planted-link findings).
- **`readJournal`** (`layout.ts:210`) — reads those lines back newest first, through `journalRead` (`layout.ts:267`): the same `journalFault` check, then an `O_NONBLOCK` open checked on the descriptor (`fstat` `isFile` — a FIFO's plain read would wait for a writer that never comes), and only the last `JOURNAL_READ_CAP` (`layout.ts:224`) = 8 MB of an over-cap file with the cut first line dropped, so the newest entries still reach the History tab; a fault or a failed read is logged and reads as no journal. Pinned by `engine/__tests__/projects/journalFence.test.ts`.
- **`readRegistry`** (`registry.ts:84`) — returns the cached registry plus whether it had to rebuild; the cache is never trusted past one `isFresh` check against the folders on disk, unless called with `{ heal: false }`, which returns the cache as written (still rebuilding when it is missing or unparsable) — used by `engine/projects/search.ts`'s fan-out so a vanished project stays in the list long enough for its own `existsSync` check to produce a `skipped` entry.
- **`rebuildRegistry`** (`registry.ts:29`) — the only place a `RegistryEntry` is derived from a folder's `project.json`; preserves `lastOpenedAt` from the previous cache across a rebuild.
- **`ensureHistory`** (`history.ts:37`) — `git init` once per project folder (idempotent on `.git` already existing), sets a local `user.email`/`user.name` so commits never depend on global git config.
- **`commitHistory`** (`history.ts:47`) — stages exactly the given paths, treats `git diff --cached --quiet` exit 0 as "nothing to record" (not a failure), and only runs `git commit` when something is staged.
- **`assembleProjectPrompt`** (`profile.ts:83`) — builds the project-chat system prompt array (same shape as `assembleBasePrompt`); byte-identical for identical input so the prefix cache holds. Its `PROJECT_WORK` block is clarify-first ("Understand before you act": one question per turn until the purpose is agreed, then two or three approaches) and save-with-consent (SaveArtifact only for what the user asked for or agreed to); a file outside the project is something to ask the user to add to Knowledge, never to read from where it is (projects-fix-1 C, after the first live session researched, drafted and saved unasked and tried to Read a file from Downloads). Options are drawn, not written: a pick among options goes in a RenderUI surface (a Card per option with a Button to choose it), a request to see options, designs or a comparison outranks asking first, and AskUser is for a yes/no before a risky step (F171, after the model answered "show me a few different designs" in markdown); the loop forces such a request with `tool_choice: 'required'` (`engine/genui/CLAUDE.md`). Pictures are one line of the same block: ask with a RenderUI Image `prompt` (another `seed` for another take), the engine paints and keeps every picture under `images/` with its prompt, seed and settings, and the chat never calls an image server, writes a ComfyUI workflow or saves renders itself — not even on a project instruction's say-so (F176: the live run of 2026-10-12/13 did exactly that on a project "directive"; `gradeProjectCall` fences Bash and the file tools).
- **`newChatFile`** (`chat.ts:24`) — names a chat file `<timestamp>-<title slug>.jsonl` and writes its header as line 1.
- **`turnsOf`** (`chat.ts:100`) — pairs each text-only user message with the following assistant text for chat ingestion; skips a user message that is a tool result.
- **`trimDanglingToolCall`** (`chat.ts:88`) — drops trailing assistant messages carrying a `tool_use` no `tool_result` answered (a chat aborted mid-tool), so a reopened chat resumes without a dangling call; `openBinding` applies it, the transcript on disk is left as written.
- **`setProjectToolContext`** (`tools.ts:23`) — sets the module-state `ProjectToolContext` (home/slug/embed client/emit) the three tools below read; `null` outside a project session.
- **`projectSearchTool`** (`tools.ts:37`), **`saveArtifactTool`** (`tools.ts:66`), **`addToKnowledgeTool`** (`tools.ts:103`) — the `ProjectSearch`/`SaveArtifact`/`AddToKnowledge` `ToolImpl`s; each refuses by name when `ProjectToolContext` is unset, every write stays inside the project folder (AddToKnowledge-by-path checks its source with `realInside` and refuses a directory), no file may be named `index.json`, and every write is followed by `ensureHistory`+`commitHistory`.

- **`gradeProjectCall`** (`binding.ts:144`) — file tools: a path whose REAL location (`realInside`, links and junctions followed) is inside the project folder is `safe`, anything else `dangerous` naming the real path; a `Glob` whose `pattern` is absolute or has a `..` segment is `dangerous` naming the pattern, because Glob scans the pattern from its dir and `../other-project/**` lists a sibling project (final review I3 — Grep's `glob` only filters under its dir and needs no check); then, for a tool that writes (Write's `content`, Edit's and each MultiEdit edit's `new_string`, NotebookEdit's `new_source`, ApplyPatch's `patch`, ReplaceFunction's `new_body`), the ComfyUI fence on the text it would write: a file that drives the server is refused before it is written — the live run's render script was a safe Write and then a safe `python tower/render.py`, nothing for the Bash fence to see — while a file that merely names the server (a note) is written. Bash: first the fence — `comfyFence` (`binding.ts:113`) is `dangerous` with `COMFY_FENCE_REASON` (`binding.ts:48`: "pictures are made by the engine from RenderUI Image prompts; a project chat never drives ComfyUI itself — ask with an Image prompt (and a seed for another take)") for ComfyUI's API on any host's 8188 (`/prompt`, `/history`, `/view`, `/object_info`, `/queue`, `/interrupt`, `/system_stats`, `/ws`, `/upload/image`, with or without the `/api/` prefix its web client uses, `:08188` too, the route ended by anything but a name character) and for the configured server — its `host:port` (`comfyHostFromEnv` (`binding.ts:63`), a small parser of `LOCALCODE_COMFYUI_URL` of its own, since `engine/imagegen` imports this package's `layout` and would cycle; the port optional when it is the scheme's default, which no command spells: `http://comfy.local/prompt` under `LOCALCODE_COMFYUI_URL=http://comfy.local`) or `LOCALCODE_COMFYUI_URL` by name (`"$LOCALCODE_COMFYUI_URL/prompt"`, `os.environ[…]`) — in a URL or beside a network client (curl, wget, Invoke-RestMethod, requests, urllib, fetch …), ahead of the download rule so a `curl` at the server is refused, not approved (F176, the live run of 2026-10-12/13 drove ComfyUI through Bash on a project "directive"); then every download (and `git clone`) is `risky`; then the classifier passed in (the bridge's `classifyRisk`, passed because this package never imports from `engine/bridge/`), and a command it calls safe that merely names the server (an echo, a grep, a script's `--server host:port`) is `risky` with `COMFY_MENTION_REASON` (`binding.ts:55`), so the user sees it rather than the chat being refused for saying the address (an `echo` that merely says the word ComfyUI is untouched); every other tool `safe`. The fence catches the natural forms, not every form: a script that takes the address from a config file or opens a raw socket is the prompt's rule (`PROJECT_WORK`), not the fence's.
- **`openBinding`** (`binding.ts:188`) — reads the project (and an existing chat's transcript, if named), ensures history and the registry entry, touches `lastOpenedAt`, journals `chat.opened`; the loop then takes the binding via `ConversationLoop.startProjectSession`.
- **`extractFile`** (`engine/projects/extract/index.ts:20`) — picks the extractor by extension (markdown/txt, pdf, epub); refuses an image outright (`'images are captioned in sub-project 3'`) and anything with no extractor, each with a reason rather than throwing.
- **`chunkSegments`** (`proseChunker.ts:31`) — packs a file's `Segment[]` into chunks that never cross a heading boundary, toward `TARGET_WORDS` and never past `MAX_WORDS`; each new chunk after the first repeats the previous chunk's last paragraph as overlap so a sentence split by the boundary is still findable; a single over-long paragraph is split at sentence ends (`splitLongParagraph`).
- **`ingestFile`** (`ingest.ts:99`) — `extractFile` → `chunkSegments` → embed (or skip, if no embed client) → `IndexStore.insertChunk`, for one knowledge/artifact file; `openForModel` (`ingest.ts:63`) rebuilds the store from scratch when the configured embed model changed since it was created (the vec table's dimension is fixed at first open), deleting it through `removeProjectStore` (`ingest.ts:47`), which removes `project.db` with its `-wal`/`-shm` sidecars (`PROJECT_DB_FILES`) — the store runs in WAL mode, and a sidecar a second connection kept from a checkpoint would replay the old model's frames into the fresh db (final review M4). A delete that fails (EBUSY on Windows while a search holds `project.db` open) is never a throw: `openForModel` logs it and the file is recorded/journaled/emitted unindexed with reason `index rebuild failed: <error>`, the old store left intact for the next rescan (spec §11; `IngestDeps.removeStore` is the test seam). Every outcome — indexed, refused by the extractor, embeddings unavailable, rebuild failed — is written to the area's `index.json`, journaled, and emitted as one `IngestEvent`; nothing is silent.
- **`searchProjects`** (`search.ts:59`) — embeds the query once, then for each target project (one slug, or every entry of `readRegistry(home, { heal: false })` for `scope: 'all'`) runs vector kNN + BM25 over `IndexStore.allChunks` fused by `reciprocalRankFusion`; a project that cannot be opened is named in the result's `skipped`, not dropped.
- **`buildRetrievalBlock`** (`retrieval.ts:23`) — turns search hits into the numbered `[Project knowledge]` text (tag `RETRIEVAL_TAG`), cut to a token budget and at most `MAX_PASSAGES`; returns the `Citation[]` actually included, which `citationsUsed` (`retrieval.ts:45`) later filters down to the ones `[n]` the assistant's reply actually cited.
- **`withValidatedSurfaces`** (`api.ts:174`) — what `getChatApi` (`api.ts:147`) serves: the transcript with each `RenderUI` tool_use input replaced by `{ surface, spec: validateSpec(raw).spec }`, so a reopened chat draws the surface the page drew live (a spec with nothing drawable comes back as `spec: null`); the transcript on disk is never rewritten. With `at` (`{ dir, slug, chatFile }`, which `getChatApi` passes), each Image with a `prompt` gets the picture state it has now (`storedImageState`, `engine/imagegen/CLAUDE.md`), looked up in `images/index.json` — read once per transcript — by `<chatFile>#<tool_use id>#<elementId>` (a transcript block's id is the live toolId); no entry reads `off: this picture was not generated`, and a record left queued/running by an engine that stopped reads `failed: interrupted …`. Each Image whose src is a path in the project gets its file state again (`annotateFileImages`, `engine/imagegen/store.ts`) with the src taken out of props, exactly as the live frame had it, whether or not the file is there now — the file route says. The one-argument call adds no picture state and leaves such a src in props.
- **`makeProjectsDeps`** (`api.ts:26`) — builds the one `ProjectsDeps` (home, embed client, embed model, ingest-event emitter, context length) every `/api/projects/*` and `/api/project-search` handler in this file takes; `main.ts` constructs it once at startup.

## Data flow
1. A caller (a later task's API handler or tool) calls `createProject` (`layout.ts:139`) with a name and optional description/instructions/tags; the returned `ProjectMeta` is the slug every other call keys off.
2. The caller registers the new project with `upsertRegistry` (`registry.ts:91`) so `readRegistry` (`registry.ts:84`) lists it without a rebuild; any later read that finds the cache stale (a hand-deleted folder, a corrupt file) silently calls `rebuildRegistry` (`registry.ts:29`) instead of surfacing the mismatch.
3. Every mutating write under the project folder is followed by `ensureHistory` (`history.ts:37`, once) then `commitHistory` (`history.ts:47`) with the paths that changed; a git failure is journaled via `appendJournal(dir, 'history.failed', ...)` (`layout.ts:206`) and returned as `{ ok: false, reason }` rather than thrown, so the write itself is never rolled back by a history problem.

One chat turn:
4. `openBinding` (`binding.ts:188`) runs once, when the project/chat is opened; `ConversationLoop.startProjectSession` takes the returned `ProjectBinding`, sets `setProjectToolContext` (`tools.ts:23`) and the executor's `Grader` to `gradeProjectCall` (`binding.ts:144`).
5. Each user message: the loop builds the retrieval block from `searchProjects` (`search.ts:59`) and `buildRetrievalBlock` (`retrieval.ts:23`), splices it in as a `[Project knowledge]` system message, then appends both sides of the turn to the chat's JSONL transcript via `appendTranscript` (`chat.ts:35`) once each is produced.
6. If the assistant calls `ProjectSearch`/`SaveArtifact`/`AddToKnowledge` (`tools.ts:37/66/103`), each refuses outside a project session, stays inside the project folder (`realInside`, `layout.ts:122`), and is followed by `ensureHistory`+`commitHistory` the same as any other write.

One upload (`addKnowledgeApi`, `api.ts:87`, or `promoteArtifactApi`, `api.ts:121`):
7. The bytes are written under `knowledge/` (or copied from `artifacts/`), then `ingestFile` (`ingest.ts:99`) runs `extractFile` (`engine/projects/extract/index.ts:20`) → `chunkSegments` (`proseChunker.ts:31`) → embed → `IndexStore.insertChunk`, recording the outcome in `knowledge/index.json` and the journal and returning one `IngestEvent`.
8. `commitHistory` (`history.ts:47`) stages the new file, its area's `index.json`, and `journal.md` in one commit.

## Gotchas
- The registry is a cache, never the truth: `readRegistry` rebuilds whenever the on-disk folder set and the cached slug set disagree (missing folder, extra folder, unparsable JSON, wrong `version`) — never hand-edit `registry.json` and expect it to stick past the next read.
- A history commit must never block or fail the caller's actual write: `ensureHistory`/`commitHistory` always resolve (never reject) and a git failure becomes a `history.failed` journal entry plus `{ ok: false, reason }`, never a thrown exception — see the "never throws" test in `engine/__tests__/projects/history.test.ts`.
- `git diff --cached --quiet` exit 0 means nothing is staged (ok, nothing to record); exit 1 means something is staged and should be committed — do not invert this when touching `commitHistory`.
- Commits for one project directory are serialised through a per-dir promise queue (`queues` in `history.ts`) so two concurrent writes to the same project can't race `git add`/`git commit`; this package uses `execFile` (async), never `spawnSync`, per F155.
- `.cynco/` under a project is git-ignored by the `.gitignore` every `createProject` writes — it holds the local index/db, never history.
- R2: a project's `.cynco/index/project.db` is opened ONLY by `ingest.ts` (`openProjectStore`/`openForModel`) and `search.ts` (`searchOne`), never by `engine/index`'s `ProjectIndexer` — its constructor purges every row `isIndexableSource` rejects, and none of `knowledge`/`artifact`/`chat` is a source file, so the next open would silently empty the project's whole prose index. See `engine/index/CLAUDE.md`.
- A project chat sees only tools it is offered, and nothing it is shown names any other: `projectTools` (`profile.ts:36`) is the one list the loop builds the tool definitions and the `<TOOLS>` block from, with project descriptions applied (Grep's points at ProjectSearch, not CodeIndex); the skill index (it tells the model to call `run_skill`) is not pushed; the executor's CodeIndex nudge is off (`setCodeIndexHints(false)` beside the grader); and a refused `load_tools`/`run_skill` call surfaces nothing — the surfacing step used to rebuild the tool list from the coding core set and could start a workflow, so one remembered call broke the fence (F173). Pinned by `profile.test.ts` ("names no tool the project chat does not offer", which scans the prompt with the real `<TOOLS>` block against the whole registry) and `projectToolFence.test.ts` (the live loop). The engine's `MEMORY` orders "IMMEDIATELY use the SaveLearning tool" on a correction and its governance variety row suggests CodeIndex; neither is in `PROJECT_TOOL_NAMES`, so the project prompt carries `PROJECT_MEMORY` and `PROJECT_GOVERNANCE` instead. SaveLearning stays out on purpose: the learnings store is global and the last 20 learnings ride every prompt, so a project's preference would leak into coding sessions and missions — a lasting preference belongs in the project's instructions.
- R4: the `[Project knowledge]` system block is rebuilt and spliced in fresh by `injectProjectRetrieval` (`engine/bridge/conversationLoop.ts:1245`) on every turn and is never appended to the chat transcript or journal — it is per-turn context, not conversation; `RETRIEVAL_TAG` (`retrieval.ts:11`) is how the loop finds the previous one to delete before adding the new one.
- `GET /api/projects/:slug/images/<32 hex>.png|json` serves a generated picture or its public record (F174, `servedImage` in `engine/imagegen/store.ts`): the name is checked after decoding, so `..%2f`, `%00` or any other name is 400 `bad image name` before a join; a link out of the project is 404, a planted non-PNG 415; the PNG goes out as `image/png` (never sniffed) with `nosniff`, a sandbox CSP, `inline` and an immutable private cache, the record with `no-store`, neither with ACAO. The page fetches it with the token header into a blob URL — there is no query-string token.
- `GET /api/projects/:slug/files/<path>` serves an image file the model wrote anywhere in the project, shown by an Image whose src was its relative path (`servedProjectFile` in `engine/imagegen/store.ts`, `fileResponse` in `engine/dashboard/server.ts`): the decoded segments are joined and checked against the validator's own rule (`projectImagePath`, `engine/genui/spec.ts`) before any join — `..%2f`, `%5c`, `%00`, a dot-leading segment (`.cynco`, `.git`), a drive letter or a non-image extension is 400 `bad file path` — the real path must be inside the project (a link out, a folder or a missing file is 404 `no such file`), a raster must carry its format's signature and an SVG start with `<svg` after an optional BOM, XML declaration, DOCTYPE (one with an internal subset is refused) and comments (415 otherwise), under 32 MB (an SVG 2 MB; 413); it goes out under the extension's fixed type, `nosniff`, a sandbox CSP, `inline`, `no-store` (the model may rewrite the file and show it again), no ACAO. Same inference gate; the page fetches it with the token into an `<img>` only.
- R5: every `/api/projects*` and `/api/project-search` request runs under the `inference` (read) scope regardless of HTTP method — this is a non-code project's own data, not engine configuration — and that check runs before the dashboard server's generic GET=inference/POST=management split, or every POST here would wrongly demand the management token (`engine/dashboard/server.ts`).
- R7: every download (and `git clone`) is graded `risky` by `gradeProjectCall`, never `safe`, however the guardian classifier would otherwise rate it — in a project chat there is always a user to ask, so the engine-wide approve-all download refusal does not apply; see `engine/tools/CLAUDE.md`'s grader step in `ToolExecutor.execute`.
- `readProject` (`layout.ts:160`) rejects any folder name that fails `SLUG_RE` (`layout.ts:50`) before even checking for a `project.json` — a hand-made `My Project/` folder dropped straight into the projects home is invisible to `rebuildRegistry` and to every API route, not merely unlisted until renamed.
- `readRegistry(home, { heal: false })` (`registry.ts:84`) exists for a caller that must see a project the cache still remembers even though its folder just vanished — `searchProjects`'s fan-out uses it so its own `existsSync` check, not a silent rebuild, is what produces that project's `skipped` entry.
- The dashboard sends its CWD box as `cwd` on a coding `user.message`; `ConversationLoop.acceptClientCwd` refuses one while a project is bound, or a page-typed project turn's tools would run in the launch cwd instead of the project folder (found in the Task 11 live proof). The page itself no longer sends one there: while bound, `showProjectCwd` puts the project folder in the box read-only and `sendChatMessage`/`saveAsArtifact` omit `cwd`; `restoreCodingCwd` gives the box back on `project.opened { slug: null }`, never restoring a project folder as the coding cwd (final review M7, `engine/__tests__/dashboard/projectsView.test.ts`).
- A project chat ignores a frame's `contract`, `readOnlyPaths`, `invariants` and `unattended` (`runUserMessage` drops them, logged, before anything reads them): spec §8.2 has no harness contract or sealed gate in a project chat, and the dashboard forwards a page frame whole (final review M1).
- `project.open { slug: null }` while no project is bound is a no-op that only re-emits `project.opened { slug: null }` — a second tab, a reconnecting page or a stale "Leave project" click must never wipe the coding conversation (final review I4). A dashboard socket that connects while a project is bound (a reload, a second tab) gets one `project.opened` from `DashboardDeps.currentProject`, asked of `ConversationLoop.currentProject()` rather than replayed, because a new chat's file is named only by its first message. A socket that connects while NO project is bound gets no frame — a restarted engine (or a dispatch swap, F141) holds none — so the page reconciles on every connect from `/api/session` (`reconcileProjectBinding`, `engine/dashboard/index.html`): a pane still showing a project chat, when `project` is null and the engine is idle with no coding turn taken (`processing` false, `turns` 0), sends `project.open { slug, chat }` for it once and says "The engine holds no project chat (a restart, or another client left it) — reopening …" — the answer cannot tell the two apart, so the line asserts neither; the engine reloads the transcript through `openBinding` and answers `project.opened` (the page's no-op path: same chat, label only — a chat begun as a new chat in the pane counts as shown from the `project.ingest` that named it, and one lost before that, its first turn in flight, is answered with a fresh chat while the drawn turn is kept and its whereabouts said); a `session.error` "project.open refused: …" clears the pane back to the coding session unless it names another chat or project (`main.ts` broadcasts every refusal to every socket, so another tab's click on a chat that is gone is not this page's answer). When `project` is null but a coding turn is running or turns have been taken, another client is in the coding session and a `project.open` would abort that turn and swap its conversation out through `startProjectSession`: nothing is sent, the pane drops to the coding session and says so. Until the connect is settled every project send — a typed message, a slash command, a surface click or FollowUps chip (`sendUiAction`), Save as artifact, Show as UI — is refused with "Reconnecting the project chat — try again in a moment." Before this, the pane kept its strip and every message went, with no cwd, to the coding session (F175, dashboard transcript 2026-10-11; pinned by `engine/__tests__/dashboard/projectsView.test.ts`).
- `initSnapshot` (`engine/bridge/conversationLoop.ts:882`) is a no-op while a `ProjectBinding` is held: the workspace-snapshot store would write `.cynco-snapshots/` into the project's own `.git/info/exclude` and an undo would rewrite project files behind the project's own history. There is no `/undo` inside a project chat — the project's git history is the record.
- The model can write anywhere in a project, links included (`gradeProjectCall` grades `ln -s` inside the folder as safe), so the engine's own files there — `journal.md`, the two `index.json`, `.gitignore`, `images/` and its sidecars — are untrusted to its reads AND its writes, the same rule as the F174 image store (`engine/imagegen/CLAUDE.md`): a name the engine writes to may be a link out of the project (the one thing the file-tool fence forbids the model, carried out by the engine's own append), a FIFO or a device that blocks the engine's thread, or a huge file. Every such path is `lstat`ed before use and written only as a regular file (`writeJsonAtomic`'s fresh `wx` file renamed into place; `journalAppend` refusing by name), read only as a regular file under a cap, opened non-blocking (`journalRead`); a fault drops the line or the read with the reason logged, never a throw — a journal line is a record, not worth breaking the write it records. Pinned by `engine/__tests__/projects/journalFence.test.ts` (a link to an outside file, a folder, a FIFO, a regular and an absent file, the over-cap tail) and `engine/__tests__/imagegen/store.test.ts`.
