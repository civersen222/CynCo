# engine/daemon

## Purpose
The CynCo liveness layer: a tiny always-on sentinel (`main.ts`) that never loads a model itself, ticks scheduled missions on a 30s interval, and spawns a real governed engine run in a separate process only when a trigger is actually due. It talks to the phone over a self-hosted ntfy server (`ntfyChannel.ts`) — publishing digests/recommendations and receiving approve/reject taps and free-text commands — and hands each due trigger to `taskRunner.ts`, which GPU-guards and spawns `engine/main.ts --run-task <file>` as a child process. The child runs `oneShot.ts`, which drives the prompt through the same S5/VSM-governed `ConversationLoop` interactive sessions use, then writes a `TaskOutcome` JSON the daemon reads back. It must never run model inference in-process, never let an SSE command callback start a model run directly (text commands are queued and only fired from `tick()`), and never let the one-shot child inherit the daemon's ntfy credentials.

## Important types & functions
- **`TriggerSpec` / `TaskFileInput` / `TaskOutcome`** (`types.ts:7`, `types.ts:70`, `types.ts:92`) — the contracts every other daemon file passes across the daemon↔engine process boundary.
- **`MissionRunner`** (`missionRunner.ts:62`) — the class whose `tick()` (called every 30s from `main.ts`) drives the whole per-mission scheduling/firing/notification loop.
- **`runGovernedLoop`** (`oneShot.ts:157`) — runs one prompt through the real `ConversationLoop`, called by both `runOneShotTask` and `tradeScan.ts`'s final ranking pass.
- **`runOneShotTask`** (`oneShot.ts:230`) — the function `engine/main.ts` invokes when `--run-task` is passed; reads the task file, dispatches to `runGovernedLoop` or `runTradeScan`, writes the outcome.
- **`TaskRunner`** (`taskRunner.ts:108`) — its `run()` method GPU-guards, spawns the child engine process, enforces the timeout, and reads back the outcome.
- **`isGpuBusy`** (`taskRunner.ts:34`) — nvidia-smi + tasklist heuristic; both probes fail open (can't tell → let the run proceed).
- **`MissionLedger`** (`missionLedger.ts:14`) — loads/saves per-mission `state.json`/`runs.jsonl`; `saveState()` writes atomically via tmp-file rename.
- **`evaluateTrigger` / `computeNextFire`** (`scheduler.ts:137`, `scheduler.ts:108`) — pure trigger arithmetic consumed by `MissionRunner.tick()`.
- **`NtfyChannel`** (`ntfyChannel.ts:36`) — `publish`/`publishRecommendation`/`subscribe` used by `main.ts` and injected into `MissionRunner`.
- **`runTradeScan`** (`tradeScan.ts:163`) — the multi-pass orchestrator dispatched from `oneShot.ts` when `taskType === 'trade-scan'`.

## Data flow
1. `main.ts` loads every `<mission-id>/mission.json` under `missionsDir()` (`engine/paths.ts`: `CYNCO_MISSIONS_DIR` or `<cyncoHome>/missions`, shared with the dashboard's `/api/away`), builds a `MissionLedger` + `TaskRunner` per mission, and starts a 30s `setInterval` calling `runner.tick()` on each `MissionRunner`.
2. `MissionRunner.tick()` (`missionRunner.ts:189`) calls `evaluateTrigger` (`scheduler.ts:137`) per trigger; a due trigger's `nextFire` is persisted to `state.json` *before* firing, then `fire()` (`missionRunner.ts:319`) runs.
3. `fire()` optionally runs the `mfl-delta` precheck, builds mission context (goal + last 3 runs + roster snapshots), and calls `deps.runTask(input)` — in production this is `TaskRunner.run()`.
4. `TaskRunner.run()` (`taskRunner.ts:115`) checks `isGpuBusy()`; if free, it writes the task file (`taskFile.ts:10`) and spawns `bun engine/main.ts --run-task <path>` as a child process (ntfy env vars stripped), enforcing `timeoutMs` with a hard kill.
5. Inside the child, `engine/main.ts` calls `runOneShotTask` (`oneShot.ts:230`), which reads the task file and either calls `runGovernedLoop` (plain prompt) or `runTradeScan` (`tradeScan.ts:163`) for `taskType: 'trade-scan'`.
6. `runGovernedLoop` (`oneShot.ts:157`) drives the prompt through `ConversationLoop` with `approveAll`/`noScouts`, then `extractOutcome` (`oneShot.ts:46`) parses the model's fenced JSON into a `TaskOutcome`, which `writeOutcome` (`taskFile.ts:24`) writes to `outcomePath`.
7. `TaskRunner.run()` reads the outcome back via `readOutcome` (`taskFile.ts:29`) and returns it to `fire()`, which records a `RunRecord` (`missionLedger.ts:58`), saves pending recommendations, and — before any notification — calls `MissionLedger.saveState()`.
8. `fire()` publishes: recommendations via `NtfyChannel.publishRecommendation` (`ntfyChannel.ts:105`), halts/failure streaks via `NtfyChannel.publish` at priority 5, or a plain digest when there's nothing actionable.
9. Phone taps/text arrive over `NtfyChannel.subscribe` (`ntfyChannel.ts:132`, SSE) into `main.ts`'s command handler, which calls `MissionRunner.handleCommand` (approvals) or `handleTextCommand` (queued, drained only by the next `tick()`).

## Per-mission tools and workspace (`allowedTools`, `cwd`)

A mission may widen or narrow the tool pin of its one-shot runs: `MissionConfig.allowedTools` applies to every trigger, `TriggerSpec.allowedTools` overrides it for one trigger, and the daemon falls back to `DEFAULT_TOOLS` (`missionRunner.ts:17`, read-only: `Mfl`, `WebSearch`, `WebFetch`, `Read`) when neither is set. The resolved list rides in `TaskFileInput.allowedTools` and is enforced as a hard pin by the loop (`conversationLoop.ts` "BLOCKED (not in allowedTools)"). Adding `Bash` or `Write` makes the run non-read-only: the loop's read-only phase detection switches off and the model can change files and run commands, so such a mission's prompt must confine the model to a known command surface (the dynasty runbook confines it to `python dynasty/mfl.py ...`, whose write commands themselves refuse to act without the owner's phone approval). `MissionConfig.cwd` / `TriggerSpec.cwd` set the loop workspace (`runGovernedLoop.cwd`, which the loop `initSnapshot()`s and the `Bash` tool runs in); unset, the one-shot engine runs where the daemon spawned it (the repo root). Pinned by `MissionRunner allowedTools and cwd plumbing` in `missionRunner.test.ts`. The loop loads every pinned tool up front, extended ones (WebSearch, WebFetch, Mfl) included, and under a pin it shows no `load_tools` block, no skill index unless `run_skill` is pinned, and no category routing (`pinnedExtendedTools.test.ts`); before 2026-10-28 the core-only seed was intersected with the pin and pinned extended tools never reached the model. Setup for the owner's dynasty mission: `docs/liveness-setup.md` § "Dynasty runbook mission".


## Per-mission wall clock (`timeoutMs`)

`TriggerSpec.timeoutMs` beats `MissionConfig.timeoutMs`, which beats `DEFAULT_TIMEOUT_MS` (15 min); `trade-scan` triggers keep `TRADE_SCAN_TIMEOUT_MS` (60 min) unless the trigger itself sets one. Only a positive finite number counts; anything else falls back (`missionRunner.ts` `timeoutFor`). The value rides in `TaskFileInput.timeoutMs`, which `TaskRunner` races against the child (`taskkill /F /T` on expiry, no outcome written). A longer clock interacts with the scheduler: a `skip` trigger whose fire time passes by more than `GRACE_MS` (10 min) while another run holds the daemon is skipped, so missions that set long timeouts should use `run-once-on-startup` for triggers that must not be lost. Pinned by `MissionRunner per-mission and per-trigger timeoutMs` in `missionRunner.test.ts`.

## Precheck by command (`precheck: 'command'`, `precheckCommand`)

A trigger can ask its own gate before the model is loaded: `fire()` runs `precheckCommand` (via `deps.runPrecheck`, `exec` in the trigger's `cwd` then the mission's, two-minute cap) and reads the first stdout line. `skip...` records an ok run whose summary quotes the line (`precheck skipped the pass: "<line>"`, sanitized by `sanitizePrecheckLine`: bounded plain text, no fences, tags or role markers, since recent summaries ride into the next run's context) and spawns nothing; `go`, anything else, a non-zero exit or a throw lets the pass run, so a broken gate can never silence a mission. Added 2026-11-06: fantasyman's two-hourly trade passes were loading the 30 GB model 47 times a day to hear `skip: no incoming offers`; they now run `python dynasty/mfl.py gate cynco --pass trades --check`.

## Pause and resume (`daemon-control.json`)

The desk widget writes `~/.cynco/daemon-control.json` (`CYNCO_CONTROL_FILE` overrides) as `{"paused": true|false, "requestedAt": ...}` (`control.ts`). `TaskRunner.run()` polls `shouldPause` every 5 s beside the timeout race: on a pause it kills the task tree (the Job Object takes llama-server with it, freeing the GPU), and returns `error: 'PAUSED'` with `paused: { sessionId, elapsedMs }`, the session id parsed from the engine's `[session] Journal:` stdout line. `fire()` stores that as `MissionState.paused` (`PausedRun`: the task input, `remainingMs`, the journal id) and records an ok run, never a failure. While the file says paused, `tick()` fires nothing and leaves `nextFire` alone. The first tick after the pause lifts first moves every trigger whose `nextFire` came due during the pause to its next slot (`computeNextFire(trigger, now)`, saved; logged `pause lifted — N trigger(s) moved to their next slot`), so Resume picks the schedule up from now instead of firing a catch-up burst (owner decision 2026-11-08; only on that edge, never at startup, so `run-once-on-startup` still catches up after a restart); pinned by `MissionRunner resume after a pause` in `missionRunner.test.ts`. It then calls `resumePaused()`: the same task input with `resumeSessionId` and `timeoutMs = max(remainingMs, MIN_RESUME_MS)`; the one-shot (`runGovernedLoop`) calls `loop.resume()` on that journal, `ConversationLoop.resume()` closes a dangling `tool_use` with synthetic interrupted `tool_result`s (`session/repairTail.ts`), and the model gets `buildResumePrompt()` instead of the task prompt. A run killed before it announced a journal simply starts over with the time it had left. Killing only llama-server would not pause anything: the engine's ProcessManager respawns it within seconds. A resumed run that is paused again is parked again (`park()`: new `remainingMs`, the new journal id or the old one), never counted as a failure. A pause that lands during one fire stops the rest of that tick (and `drainOnDemand`) before the next spawn, leaving the remaining triggers' `nextFire` to the from-now move, so it cannot overwrite the run just parked; and `TaskRunner.run()` returns the `PAUSED` outcome without spawning when `shouldPause()` is already true. Pinned by `MissionRunner pause during a run (review fixes)` and `TaskRunner already paused`.

Resume still resumes the parked run (that pass was running when the owner paused, so finishing it is what Resume means); only the passes that merely came due are moved. The file now also carries `by` (`'widget'` or `'dashboard'`, written by `writeControl` in `control.ts`, atomically): it says who flipped the switch, and the Missions tab and the widget show it ("Paused since 2:25 PM (widget)").

## Schedule overrides (`schedule.json`)

The owner's changes to when a pass runs live in `<missionsDir>/<id>/schedule.json`, next to `mission.json` and never inside it, so `make_cynco_mission.py` regenerating `mission.json` cannot lose them. The dashboard writes it (Missions tab, `PUT /api/missions/<id>/triggers/<tid>`, atomic tmp+rename via `writeSchedule`); the daemon only reads it and keeps its own record in `state.json`. A `PUT` while the file is `bad` (below) is refused with 409 and writes nothing: the dashboard would read the bad file as empty, and writing from empty would drop every other override the daemon still honours from memory; the Missions card shows a warning and locks its controls instead. Shape: `{ "updatedAt": iso, "triggers": { "<triggerId>": { "enabled"?: bool, "kind"?, "cron"?, "at"?, "day"?, "everyMinutes"?, "timeoutMs"? } } }`. The override's fields are spread over the `mission.json` trigger (`applySchedule` in `schedule.ts`); `timeoutMs` is 60 000 to 7 200 000. `precheck` and `missedPolicy` are never overridable: they are safety behaviour, not cadence. Unknown trigger ids are kept in the file and ignored.

`readSchedule` returns one of three statuses, and `MissionRunner.loadSchedule` treats them differently every tick (`missionRunner.ts:99`): `ok` replaces the cached override set; `absent` (no file) clears it, so deleting the file means no overrides; `bad` (torn write, invalid JSON, any invalid override) keeps the last good set in memory and logs once per mtime (`schedule.json is unreadable or invalid — keeping the last good overrides`). A torn file therefore never re-enables a disabled pass; a daemon that starts on a bad file has no last good set and runs with none.

Per trigger, `tick()` then does one of three things (after the pause check and the resume-from-now move):

- **Disabled** (`enabled: false`): never evaluated and never fired, but `advanceDisabled` keeps its `nextFire` moving to the next slot from now whenever it comes due, recording nothing. Re-enabling it, or deleting the override, therefore resumes the normal grid with no missed slot for `run-once-on-startup` to catch up.
- **Cadence changed** (`cadenceFingerprint` differs from `state.scheduleSeen[triggerId]`): `applyFingerprint` resets `nextFire` from now with the new cadence and stores the fingerprint. The first sighting (nothing stored yet) only stores it. `state.scheduleSeen` is what the API compares to decide whether a shown next fire is a preview.
- **Unchanged**: evaluated as before (`evaluateTrigger`, `missedPolicy`, grace window).

Because one fire can hold the tick for up to 45 min, `recheckBeforeFire` (`missionRunner.ts:168`) re-reads `schedule.json` immediately before each `fire()`: a trigger switched off meanwhile is not fired (logged; its `nextFire` is already advanced and the next tick's `advanceDisabled` keeps it moving), and one whose cadence changed meanwhile goes through `applyFingerprint` and fires only if it is still due; pinned by `a trigger switched off while an earlier pass in the same tick runs is not fired` in `missionRunner.test.ts`.

A bad cadence cannot stop a tick: `validateOverride` checks fields one at a time, so an override can still describe something `computeNextFire` cannot compute (`kind: 'cron'` with no `cron`). `resolveTriggers` catches that per trigger, logs once, and falls back to that trigger's `mission.json` cadence (its `enabled` switch still applies).

Disabling changes scheduling only. A run already on the GPU is left to finish. A run parked in `state.paused` for a trigger that is now disabled is dropped on the first unpaused tick (`resumePaused`): `paused` is cleared and an ok run is recorded with the summary `dropped on disable: <triggerId>` so the journal is accounted for (the API reports it as `kind: dropped`). A cadence change leaves a parked or running run alone. The wake schedule published to the doorman lists only enabled triggers (`collectNextFires(..., allowedIds)` in `wakeSchedule.ts`), so the PC is not woken for a pass that will not run.

`schedule.json` needs no restart (it is re-read and parsed every tick; the mtime is used to log a bad file once); `mission.json` still does.

## Tell the phone when the engine waits (`waitPush.ts`)

An approval card is refused after five minutes and an AskUser question resolves empty after five minutes (`requestApproval` in `engine/bridge/conversationLoop.ts`, `AskBroker`). A phone whose screen locked has no socket, so the frame that drew the card reached nobody. `engine/main.ts` hands every loop event to `WaitPush.onEvent`; an `approval.request` or `ask.request` frame starts a 5 s clock (`WAIT_PUSH_GRACE_MS`), and when it runs out one notification is published to the alert topic if both hold: the request is still in `ConversationLoop.pendingDecisions()`, and no client is connected (`DashboardServer.clientCount` is 0 and the bridge has no TUI or mission harness, `wsServer.connected`). The frame alone decides nothing: it is emitted before the approval is registered, and the beginner-mode warning frame has the same type and never waits.

- **Switched on by** `CYNCO_NTFY_URL` in the engine's environment (`CYNCO_NTFY_TOKEN`, `CYNCO_NTFY_ALERT_TOPIC` as for the daemon). `scripts/run-headless-engine.cmd` sets it to the doorman's ntfy unless it is already set. Unset: nothing is built, the engine logs `[wait-push] off`, no request leaves the machine.
- **What goes out:** the title (`CynCo needs your approval` / `CynCo has a question`), the tool name and its description or the question and its options, capped at 400 characters, to the same self-hosted tailnet-only ntfy the daemon uses. It is the text the phone page would have shown on the card.
- **Never late:** it publishes with `queueOnFailure: false`, so an unreachable ntfy drops the notice instead of delivering "waiting now" after the wait is over. A failed or throwing publish is one `[wait-push] not delivered` log line and the turn is untouched.
- **Not built on the `--run-task` path:** a daemon one-shot still has `CYNCO_NTFY_*` stripped and reports only through its outcome file (gotcha below).
- **Does not cover:** a desk tab left open while the owner is away (a client is connected, so nothing is sent), or the last client disconnecting after the grace has passed. Both are in `docs/NOW.md`'s backlog.

Pinned by `engine/__tests__/daemon/waitPush.test.ts` (the decision), `guards/waitPushWiring.test.ts` (the lines in `engine/main.ts`), `a publish that says not to queue is dropped on failure` in `ntfyChannel.test.ts` and `clientCount follows the sockets` in `dashboard/server.test.ts`. Not yet seen on the phone.

## Gotchas
- `Stop-ScheduledTask` on the Task Scheduler job is not a pause: the job restarts the daemon within a minute and it fires whatever is due. Pause through the control file, or `Disable-ScheduledTask` first.
- A model run must NEVER start from the SSE command callback — free-text commands are queued in `onDemand` and only fired from `tick()`'s `drainOnDemand` (`missionRunner.ts:240`); pinned by `handleTextCommand("lineup") queues a request and publishes an ack` in `missionRunner.test.ts`.
- `nextFire` is persisted to `state.json` *before* firing, so a crash mid-run can't re-fire the same trigger on restart (`missionRunner.ts:231`); pinned by `persists nextFire to disk before firing — a crash mid-run cannot re-fire`.
- All ledger mutations (pending recs, failure streak) are saved BEFORE any phone notification — a crash between save and publish must never leave a notification with no matching pending state (`missionRunner.ts:477`); pinned by `Fix 1: pending is on disk even when publishRecommendation throws`.
- A HALT (`error` starting with `"HALTED:"`) pages immediately at priority 5 regardless of the failure streak — it does not wait for `FAILURE_ALERT_THRESHOLD` (`missionRunner.ts:459`); pinned by `publishes immediately with priority 5 when the outcome is a HALT, regardless of failure streak`.
- The spawned one-shot engine must NOT inherit the daemon's `CYNCO_NTFY_*` env — it can only report through its outcome file, never talk to the phone directly (`taskRunner.ts:128`); pinned by `strips CYNCO_NTFY_* env so the one-shot engine cannot act as the daemon`.
- Recommendation ids are always minted by `extractOutcome` (`rec-<hex>`), never trusted from the model — they key the ledger's pending map and ride ntfy approve buttons (`oneShot.ts:55`); pinned by `assigns ids to recommendations missing one`.
- `resolveApproval` uses `Object.hasOwn` to guard against prototype-pollution keys like `"constructor"` reaching the plain-object pending map (`missionLedger.ts:88`); pinned by `resolveApproval ignores prototype keys like "constructor"`.
- A corrupt `state.json` (power loss mid-write) is backed up to `.corrupt` and the mission starts with fresh state instead of crash-looping the daemon forever (`missionLedger.ts:33`); pinned by `survives a corrupt state.json: backs it up and starts fresh`.
- `isGpuBusy` fails open on both probes: if nvidia-smi or tasklist can't be read, the run proceeds rather than blocking forever (`taskRunner.ts:32`); pinned by `returns false when the process list is unavailable`.
- `isGpuBusy` first asks the engine's model port (`/health` on `LOCALCODE_PORT`, default 8081): any answer means busy, because a new one-shot's `ProcessManager.ensureRunning()` kills whatever answers there as "stale". Without it, a missed tasklist probe let the daemon kill a live hand-started run's server (2026-10-28); pinned by `a model server answering on the engine port means busy even when tasklist and nvidia-smi miss it`.
- Zero assistant turns (every model call timed out) must report failure, not the unstructured-fallback `ok: true` — `runGovernedLoop` gates on `countAssistantTurns(messages) === 0` before falling through to `extractOutcome` (`oneShot.ts:213`).
- `MissionConfig.leagues` is optional: a mission that is not MFL-bound (fantasy-digest) has none, and `fire`/`buildContext` read it as `?? []` — a required-typed read threw on every tick and no digest ever ran (F184); pinned by `a mission without leagues fires its due trigger with leagues: []` in `missionRunner.test.ts`. `scripts/cynco-services.ps1` is the status/start/stop for the daemon, ntfy and the approval listener.
- `gpu-busy.json` is the arbiter the lazy engine waits on (`readGpuBusy`, `gpuBusyFile.ts`): while it names a live pid the engine never spawns its own llama-server, so a phone message cannot kill a running one-shot's server (the F182 class). `TaskRunner.run()` writes it right after `spawn` and clears it in a `finally`, timeout kill included; pinned by `names the running one-shot while the child runs and clears it after` in `taskRunner.test.ts`.
- The daemon itself never sleeps the PC and holds it awake only while a one-shot runs (`TaskRunner` registers an `oneshot` activity, `engine/power/awake.ts` spawns the hold helper on the 0→1 edge). Between triggers Windows' idle timer may sleep the box; `wakeSchedule.ts` is what gets it back in time. Pinned by `TaskRunner activity (hold-awake)` in `taskRunner.test.ts` and `engine/__tests__/daemon/wakeSchedule.test.ts`.
