# engine/tools

## Purpose
Defines every tool the model can call in an agent turn — file I/O, Bash, Git, search, contract/Definition-of-Done bookkeeping, sub-agents — plus the registry, approval/safety/sealing gates, and the `ToolExecutor` that sits between a model's `tool_use` block and the filesystem/shell. The primary caller is `engine/bridge/conversationLoop.ts`; policy layers (`s5/ruleBasedS5.ts`, `vsm/*`, `agents/trustTier.ts`) narrow which tools are offered but never bypass this package's checks. It must never let a call reach a sealed gate instrument, replace a tool's own error output with engine commentary instead of appending to it, or let the model rewrite the harness contract it is measured against. Shaped directly by F34/F35/F37 (withheld/held-out gate handling), F60 (PowerShell `2>&1`), F136 (missing-file "did you mean"), and F142 (Bash timeout ceiling vs default).

## Important types & functions
- **`ToolImpl`** (`types.ts:39`) — the contract every tool exports: name, description, input schema, approval tier, core/extended flag, `execute`. Implemented by every file under `impl/`.
- **`ALL_TOOLS`** (`registry.ts:34`) — the flat tool registry every lookup/filter function in this file reads.
- **`getToolByName`** (`registry.ts:61`) — registry lookup used by `ToolExecutor`, `approvalGate.ts`, and `load_tools` to resolve a call by name.
- **`ToolExecutor`** (`executor.ts:119`) — turns `(toolName, input)` into a `ToolResult`: sealed check, immutable-path check, download gate, approval, execute, doom-loop check, redaction/cap. With a `Grader` set (`setGrader`, projects mode) one grade replaces the download gate and tier approval: `dangerous` is refused with its reason, `risky` asks, `safe` runs.
- **`ToolExecutor.beginModelCall`** (`executor.ts:183`) — the loop calls it before each model call's tool batches; from then on the trust score takes at most one success and one failure per tool per call. A caller that never calls it — a sub-agent's executor, a test — scores every call, as before (F178).
- **`ToolExecutor.runsUnasked`** (`executor.ts:151`) — whether a call to a tool would run here without a question to the user: `shouldAutoApprove` with this executor's trust profile and approve-all, and false for every tool when a grader is set (a project chat grades each call by its input). It is what the loop hands a sub-agent it starts, so a researcher's web tools never exceed the parent run's (`engine/agents/CLAUDE.md`).
- **`bashTool`** (`engine/tools/impl/bash.ts:133`) — the Bash implementation: safety check, shell-dialect translation, timeout clamp, failure formatting.
- **`bashMaxTimeoutMs`** (`engine/tools/impl/bash.ts:95`) — the hard ceiling any Bash timeout is clamped to, env-raisable up to `HARD_MAX_BASH_TIMEOUT_MS`.
- **`bashDefaultTimeoutMs`** (`engine/tools/impl/bash.ts:125`) — the timeout a Bash call gets when the model doesn't ask for one.
- **`codeIndexTool`** (`engine/tools/impl/codeIndex.ts:67`) — semantic/symbol code search; falls back to `regexFallback` when the vector index returns nothing.
- **`verifyAssertion`** (`contractVerify.ts:169`) — checks a contract assertion against actual repo state; the ground truth behind `ContractAssertPass`.
- **`checkBashSafety`** (`bashSafety.ts:43`) — best-effort blocklist for destructive/blocking commands; explicitly not a sandbox.
- **`ContractState`** (`contract.ts:90`) — Definition-of-Done state machine backing the four Contract* tools; distinguishes unreplaceable `harness` contracts from `auto` ones.
- **`secretPathOf`** (`secretPaths.ts:44`) — `{ action: 'refuse' }` for the resolved `~/.cynco/tokens.json`, `{ action: 'approve' }` for `~/.ssh/**`, `.env`/`.env.*` and `/etc/shadow|passwd|sudoers`, null otherwise; Bash is `bashSafety.ts`'s to judge. Consulted at the top of `ToolExecutor.execute` (`executor.ts:187`) before any tier or grade.
- **`callTouchesSealed`** (`sealedPaths.ts:191`) — refuses any call whose path or Bash text names a withheld gate instrument, its basename, or its gates directory.
- **`shouldAutoApprove`** (`approvalGate.ts:18`) — decides whether a call skips the human approval prompt, given trust profile / approve-all / tool tier.
- **`DoomLoopDetector`** (`doomLoop.ts:11`) — flags a tool call repeated 3+ times with identical input and no intervening workspace change.

## Data flow
1. The conversation loop calls `ToolExecutor.execute(toolName, input)` for a model's `tool_use` block.
2. `getToolByName` (registry.ts) resolves the `ToolImpl`; an unknown name returns an error result immediately.
3. `callTouchesSealed` (sealedPaths.ts) refuses the call outright if it names a withheld gate instrument.
4. `immutableTargetOf` refuses a write to a declared brief/gate path (readable, never writable).
4b. `secretPathOf` (secretPaths.ts) refuses the engine's own token file outright; any other secret path forces `requestApproval` in steps 5 and 7 below, and under approve-all is refused instead (there is no user to ask).
5. If a `Grader` is set (projects mode, `setGrader`), it alone decides what happens next — `dangerous` refuses with its reason, `risky` (or a secret path, 4b) goes straight to `requestApproval`, `safe` proceeds — and steps 6-7 below are skipped entirely.
6. A download command (`isDownloadCommand`) is refused under approve-all, or forced through interactive approval.
7. `shouldAutoApprove` decides tier/trust; if not auto, `requestApproval` blocks on the human/UI before proceeding.
8. `tool.execute(input, cwd)` runs the tool's own implementation (e.g. `bashTool`, `editTool`, `codeIndexTool`).
9. A successful workspace-mutating call clears `DoomLoopDetector` state; a failed repeat is checked via `doomLoop.check`.
10. Output is redacted (`redactSealed`), capped (`capToolResult`), and given a CodeIndex-adoption nudge before returning as the final `ToolResult`; `arbiterVerdict` passes through unchanged.
11. `toolScorer.record` logs success/failure for later demotion/probation decisions — except a file tool's answer to a path that does not exist (`isWrongPathAnswer`, `engine/tools/impl/pathHint.ts:51`), which is recorded neither way (F178); once the loop has marked a model call (`beginModelCall`), a second success or a second failure of the same tool in that call is not recorded either (F178).

## Containment of unattended runs

A dispatched mission starts every command the Bash tool runs through `engine/containment.ts` (F242); on 2026-11-22 one Bash call of an unattended mission deleted every dot-folder of the owner's home, and this is the layer that makes that command fail. Who does what: `scripts/dispatch-mission.sh` mints a run id (`bun scripts/cynco-sandbox.mjs mint`) and, after its exit trap is armed and before it stops anything, creates the run's sandbox (`cynco-sandbox.mjs create`, which calls `establishContainment`): `<LOCALCODE_SANDBOX_ROOT>/<run id>/{home,tmp,scratch}` (the root, default `C:/cynco-sandbox`, is never created by the engine, a dispatch or a test: a root that does not exist is a refusal), a record `containment.json` in the run folder, written before any label, and on Windows a low label on `home`, `tmp`, `scratch` and the mission folder; the run folder itself stays medium, so the run cannot change its own record. The engine's boot block (`engine/main.ts`, after the job object, before the sibling hand-off and the model load) adopts that sandbox from `LOCALCODE_MISSION_RUN_ID` and `LOCALCODE_MISSION_CWD` (`adoptContainment`: it verifies, never creates, and on Windows runs the launcher probe in this process) and sets the run context. An unattended boot (`isContainedRun`, `engine/missionEnv.ts`: a mission key or `--run-task`) that cannot adopt one, or that finds `LOCALCODE_CONTAINMENT_OFF` set, prints `[containment] refused: containment: <reason>`, exits 1 and loads no model, and the dispatch stops on that line. The driver adopts the same record (exit 2 when it cannot) and dispatches only to an engine whose `session.ready` says `contained-tools` (`contained-overlay` off Windows; `containmentDispatchRefusal`, `scripts/cynco-contract.mjs`, exit 4). The mission folder is set back to medium when the run is released: by the dispatch's watcher after the mission engine is gone, by `dispatch_abandoned` when the dispatch stops early, or by `release-dead` at the next dispatch. A release relabels the folder's root and then walks it (never entering a link, one `icacls "<dir>\*" /L` per folder) and sets back every low label the run set on something under it itself, which the root relabel alone leaves in place (measured). A release that could not set everything back says so in its note and, from `cynco-sandbox.mjs`, on stderr as `[sandbox] NOT SET BACK:` with exit 3 (the watcher writes it to the driver log); the next `create` for that folder then refuses while it still reads low and no live run holds it. A folder holding a file with a second name (a hard link) is refused before it is labelled, because a label set on that file would reach its other names. A sandbox folder is deleted only by the sweep, seven days after it was created, and the sweep never follows a link.

From boot on, the run context decides, never a message's `unattended` flag: a note typed into the dashboard during a mission runs contained too. Three things are done to each child. Its environment is built by `toolEnv`: HOME, USERPROFILE, HOMEDRIVE, HOMEPATH, APPDATA, LOCALAPPDATA, TEMP, TMP and TMPDIR point into the sandbox; `CYNCO_SCRATCH` names the run's scratch folder; PATH is kept; PYTHONUSERBASE names the real user site so installed packages are found; GIT_CONFIG_GLOBAL names a `.gitconfig` in the sandbox home that includes the owner's (which the run cannot write); the containment's own keys and the secrets (`SECRET_ENV`) are dropped. On Windows it is started by `engine/lowIntegrityLauncher.ts` (with `--no-env-file` and its own `bunfig.toml`, in the checkout, so nothing the run wrote is read while it is still medium), which lowers its own token to low integrity through bun:ffi and reads the level back before it builds the child's environment and starts the child, so the child and everything it starts are low. Stop and the timeout end the whole tree through the job taken on the launcher's pid (`ownProcessTree`, F201, F210); a `maxBuffer` overflow kills the launcher, and its child was measured to die with it (`containmentLauncher.test.ts`), which is not guaranteed by construction. And it is refused, by name (`Refused [containment]: <reason>. ...`, no exit code), when the run has no working launcher (not Bun, a launcher file missing, a token that would not lower, a launcher that exited 197): there is no downgrade to the overlay alone on Windows. Each contained command costs the launcher's start, measured on the owner's PC at about 30 ms on top of a PowerShell start and about 90 ms on top of a bare `cmd` one.

**What low integrity blocks (measured on NTFS by the Bun fixture and by hand):** creating, changing, renaming or deleting anything in a folder that is not labelled low, which is everything except the run's sandbox, its mission folder and its extra roots: the home folder and every dot-folder in it, CynCo's own checkout and state folder, the run's own record; and making a junction that leads out of what it may write. A configuration file planted in the mission folder or the sandbox home (`bunfig.toml`, `.env`) is not read by the launcher, nor one in the launcher's own working folder (the fixture shows each of `--no-env-file` and `--config=` is what stops it).

**What it does not block:** (1) reading: the run can read whatever the owner can, `~/.ssh` and `~/.cynco/tokens.json` included, and it has the network; (2) other places labelled low: the mission folder itself, other runs' sandboxes, `AppData\LocalLow`, and a folder a dead run left labelled until it is released; (3) volumes without integrity labels: exFAT and FAT drives and network shares are fully writable to it (a sandbox is refused while one is attached and not acknowledged in `LOCALCODE_UNPROTECTED_VOLUMES_OK`), and a hard link carries a label to every name of the file, which is why a mission on CynCo itself works in a clone made with `git clone --no-hardlinks`; (4) brokers: a service that acts for its caller at its own level (Docker, WSL, WMI, Task Scheduler, a COM server, the engine's own API once the token file is read) was not tested and must be assumed open; (5) what the run leaves behind: code in the mission folder is executed by whoever runs it, at their level, and that includes, during the same run, the harness sites named below as not yet contained; (6) the file tools (Read, Write, Edit and the rest), which run inside the engine at medium; (7) anything off Windows beyond the environment overlay; (8) an API that ignores the environment (`[Environment]::GetFolderPath`, `os.userInfo().homedir`) still answers the real home: a write there is denied on Windows, a read is not.

A PowerShell child's non-ASCII output through the launcher came out as UTF-8 in every run measured; the same command run directly (an uncontained Bash call) depends on the console the engine was started in, and was measured garbled in one run.

**What stops working in a contained run on Windows:** nothing that needs Git's msys runtime starts while any other Git Bash is running, which during a dispatched mission is always, because the dispatch itself runs in one: `bash`, `sh`, the programs of Git's `usr\bin` (`grep`, `sed`, `tail`, `head`, `ls`) and a commit in a repository with a shell-script hook fail, and the result carries a `[containment]` hint naming the PowerShell forms (`containmentHint`, also on a pipeline that exits 0 with the error on stderr). A Python program that asks for a temporary file in a folder it may not write spins until its timeout instead of failing, and the timeout result says so (pytest from such a folder needs `-p no:cacheprovider`). `pip install --user` and `git push` over ssh have nowhere to write or no key. Removed uses: a mission in a git worktree, in a subfolder of a repository, in the engine's own checkout or inside a dot-folder of the home folder is refused when its sandbox is created; the driver run by hand against an engine it did not start exits 2. Interactive sessions, the phone engine and project chats are not contained; their Bash children only lose `CYNCO_MISSION_ALSO_LABEL` from the environment. `LOCALCODE_CONTAINMENT_OFF` (`lowil`) is honoured only for a test's context (vitest's Node has no bun:ffi); set at all, it refuses every real run. Refused in a contained run until they are contained (`uncontainedSiteRefusal`): the Git tool and ApplyPatch answer `Refused [containment]: ...`, a contract check command and verify-first are `unrunnable` with that text as their tail, and the contract's git reads answer null (cannot tell). Not yet contained and still run at medium integrity with the real home: best-of-N test runs, LSP diagnostics, the daemon precheck, the driver's marker check, probe and its own `git status` / `git checkout` in the mission folder, and the graders; a daemon one-shot and the ideation one-shot are refused at boot until their starters create a sandbox. **So until those sites are contained, a hook, a git setting (`core.fsmonitor`) or a test file (`conftest.py`) the run writes in its mission folder is executed at medium integrity during the same run by the driver's check, probe or git, and this layer alone does not prevent a repeat of 2026-11-22: no mission is dispatched on it alone.** Recovery commands for the owner: `bun scripts/cynco-sandbox.mjs status | release <id> | release-dead --kind mission | sweep`. Pinned by `engine/__tests__/containment.test.ts` (every refusal, the environment, the argv, the switch, release and sweep), `guards/containedCapability.test.ts`, `guards/containedBootRefusal.test.ts`, `bridge/containedWithoutUnattendedFlag.test.ts`, `scripts/__tests__/cynco-sandbox.test.mjs` and, for the Windows layer under Bun (never on CI), `containmentLauncher.test.ts` with `fixtures/containedShell.ts`.

## Gotchas
- Stop and the timeout kill a running command and what it started (F201, F210): `ToolExecutor.execute` takes the turn's abort signal as a third argument and passes it to `ToolImpl.execute`; only Bash acts on it. Bash takes ownership of its shell's process tree the moment the shell exists (`ownProcessTree`, `engine/processTree.ts`: a Job Object on Windows under Bun, so a kill cannot miss a child started mid-kill; elsewhere, and under vitest's Node, the tree is found when it is killed) and kills it on Stop and on its own timeout: `exec` is given no `timeout`, because exec's kill ends the shell alone. A command that ends on its own releases the handle and kills nothing, so a background process it left on purpose lives on. The result says `command stopped` or `command timeout after Nms`, never the other, and carries the output collected so far; if a survivor holds the pipes the call returns after `STOP_GRACE_MS` anyway. A call that arrives after the Stop is not started. Pinned by `engine/__tests__/tools/bashAbort.test.ts`, `engine/__tests__/processTree.test.ts` and, for the Job Object under Bun, `engine/__tests__/processTreeJob.test.ts`.
- `bashSafety.ts` is explicitly "NOT a sandbox — trivially bypassed... The real protection is Bash tier='approval'" — pinned by `bashSafety.test.ts`.
- `Bash` is deliberately absent from `executor.ts`'s `WORKSPACE_MUTATING_TOOLS` even though the shell can write files — a named, accepted blind spot (finding (f)), not an oversight.
- Downloads never ride on approve-all, including the mission driver's — even unattended runs get a refusal naming the staging path (`approvalGate.ts`), pinned by `approvalGate.test.ts`. Secret paths follow the same rule (`secretPaths.ts`, pinned by `secretPaths.test.ts`): a `.env` under approve-all is refused, not read.
- `fetchGuarded` (`impl/webFetch.ts`, used by `WebFetch` and by `AddToKnowledge` by URL) looks every hop's name up before it connects: a name with ANY address in a range a literal address is refused for is refused with `Blocked: <name> resolves to <address> (<range>)`, and the request then goes to the checked address with the name in `Host` and in the TLS handshake (`pinnedFetch`), so a second lookup cannot answer differently. Until 2026-11-17 only the URL was read, and a public name resolving to 127.0.0.1 reached this PC's own dashboard. The ranges are the ones a literal address was already held to, plus three IPv6 forms added the same day with the owner's yes (NAT64 and 6to4 carrying a refused IPv4 address, and site-local); an IPv6 address is read as its eight groups, so every spelling of it is one address. There is no switch, and a test that injects `fetch` injects `resolve` too. Decision: `docs/decisions/2026-11-17-webfetch-resolves-names.md`. Pinned by `impl/__tests__/webFetch.test.ts`.
- A web page or a search snippet is data: `WebFetch` and `WebSearch` return it between the `untrusted.ts` lines, and the one sentence that explains them is `TOOL_RESULTS_ARE_DATA` in `engine/engine/systemPromptText.ts` (pinned by `untrustedContent.test.ts`). The lines shrink the chance of an injection; the approval cards contain it.
- The sealed-gate refusal (F37) is four layers (reference/enumeration/location/content); read-only alone was insufficient because a command can read gate content while spelling no sealed name. Pinned by `sealedPaths.test.ts`. A data instrument named by a `CHK_SUITE_BASELINE=` prefix (the suite baseline's bare node ids) is sealed by path only — `setTaskSealedPaths`' `contentExempt`, from `contractAutoCreate.ts`'s `contentExemptGatePaths` (Phase 7 T6-N1) — or the model's own `pytest --collect-only` output would be discarded.
- A withheld contract assertion's `command` must never appear in a failure message (F34) — naming it would leak every mutation anchor to the model being graded on defeating them.
- A verification command that is killed by its timeout is `unmeasured`, never `contradicted` (F35) — a timeout must not be recorded as a "no". Pinned in `contractVerify.ts`'s own tests.
- `arbiterVerdict: true` marks an honest "not yet" from a declared arbiter so the doom-loop breaker does not fire on a run correctly re-asking the same graded question.
- Windows PowerShell 5.1 has no `&&`/`||`, and a trailing `2>&1` makes a successful command look failed (F60) — `bash.ts` strips it and reports both streams instead. Pinned by `shellInfo.test.ts` and `bash.test.ts`.
- Bash timeouts have two ceilings, not one: `bashDefaultTimeoutMs` (what a call gets unasked) and `bashMaxTimeoutMs` (hard clamp on any override) — F142 was an operator raising one env var while a separate constant still capped it.
- The Bash tool's shell never inherits the harness's keys: `toolEnv` (`engine/containment.ts`, re-exported from `impl/bash.ts` as `bashToolEnv`) drops `LOCALCODE_MISSION_*`, `CYNCO_MARKER_CHECK*` (the driver's marker check, Phase 7 final review I1) and `CYNCO_MISSION_ALSO_LABEL` in every mode, while the engine process keeps them; in a contained run it also drops the containment's own keys and the secrets. Pinned by `bash.test.ts` and `containment.test.ts`.
- `Write` refuses to shrink a git-tracked file below half its size unless the file is untracked; delete-then-write is the deliberate escape hatch. Pinned by `writeShrinkGuard.test.ts`.
- A path that does not exist is the model's guess, not the tool failing: Read, Edit, MultiEdit and ReplaceFunction answer it with `missingFileHint` (the folder's listing and a "did you mean", F136), and `ToolExecutor` leaves that answer out of `ToolScorer` (`isWrongPathAnswer`, `engine/tools/impl/pathHint.ts:51`, keyed on `MISSING_FILE_PREFIX` at `engine/tools/impl/pathHint.ts:39` and checked on the tool's own output, before the cap or a nudge). Scored as a failure, three guessed prompt-file names in one parallel Read batch demoted Read in a live project chat, and with Read withheld the model read its files through Bash `Get-Content` (F178, 2026-10-13). A refusal that is not a wrong path — a folder given to Read, an Edit whose `old_string` is not there — is scored as before. Pinned by `engine/__tests__/tools/wrongPathTrust.test.ts`.
- A batch the model fired together is one decision: once the caller marks model calls (`ToolExecutor.beginModelCall` (`executor.ts:183`), called by the loop where it clears the circuit breaker's per-call strikes), the trust score records at most ONE success and ONE failure per tool per model call (`executor.ts:304`): a call that both succeeded and failed with a tool counts one of each.
