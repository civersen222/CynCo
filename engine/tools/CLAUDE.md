# engine/tools

## Purpose
Defines every tool the model can call in an agent turn — file I/O, Bash, Git, search, contract/Definition-of-Done bookkeeping, sub-agents — plus the registry, approval/safety/sealing gates, and the `ToolExecutor` that sits between a model's `tool_use` block and the filesystem/shell. The primary caller is `engine/bridge/conversationLoop.ts`; policy layers (`s5/ruleBasedS5.ts`, `vsm/*`, `agents/trustTier.ts`) narrow which tools are offered but never bypass this package's checks. It must never let a call reach a sealed gate instrument, replace a tool's own error output with engine commentary instead of appending to it, or let the model rewrite the harness contract it is measured against. Shaped directly by F34/F35/F37 (withheld/held-out gate handling), F60 (PowerShell `2>&1`), F136 (missing-file "did you mean"), and F142 (Bash timeout ceiling vs default).

## Important types & functions
- **`ToolImpl`** (`types.ts:50`) — the contract every tool exports: name, description, input schema, approval tier, core/extended flag, `execute`. Implemented by every file under `impl/`.
- **`ALL_TOOLS`** (`registry.ts:37`) — the flat tool registry every lookup/filter function in this file reads.
- **`getToolByName`** (`registry.ts:61`) — registry lookup used by `ToolExecutor`, `approvalGate.ts`, and `load_tools` to resolve a call by name.
- **`ToolExecutor`** (`executor.ts:157`) — turns `(toolName, input)` into a `ToolResult`: the confirmed presence tripwire (`presenceTripwireConfirmed`, awaited, which may wait 1 s on a change it sees), sealed check, immutable-path check, download gate, approval, execute, doom-loop check, redaction/cap. The pre-run checks live in `preRun`, in that order; in a contained run `execute` writes one `refused` audit record for a pre-run refusal, the `start` record (fsynced) right before the tool, and the `end` record after it, and raises `containmentFault` for a containment or integrity refusal (`refusalFaultOf`). `ToolResult.exitCode` (`types.ts`) is carried at both places it rebuilds a result. With a `Grader` set (`setGrader`, projects mode) one grade replaces the download gate and tier approval: `dangerous` is refused with its reason, `risky` asks, `safe` runs.
- **`ToolExecutor.beginModelCall`** (`executor.ts:223`) — the loop calls it before each model call's tool batches; from then on the trust score takes at most one success and one failure per tool per call. A caller that never calls it — a sub-agent's executor, a test — scores every call, as before (F178).
- **`ToolExecutor.runsUnasked`** (`executor.ts:192`) — whether a call to a tool would run here without a question to the user: `shouldAutoApprove` with this executor's trust profile and approve-all, and false for every tool when a grader is set (a project chat grades each call by its input). It is what the loop hands a sub-agent it starts, so a researcher's web tools never exceed the parent run's (`engine/agents/CLAUDE.md`).
- **`bashTool`** (`engine/tools/impl/bash.ts:189`) — the Bash implementation: safety check, shell-dialect translation, timeout clamp, failure formatting.
- **`bashMaxTimeoutMs`** (`engine/tools/impl/bash.ts:151`) — the hard ceiling any Bash timeout is clamped to, env-raisable up to `HARD_MAX_BASH_TIMEOUT_MS`.
- **`bashDefaultTimeoutMs`** (`engine/tools/impl/bash.ts:181`) — the timeout a Bash call gets when the model doesn't ask for one.
- **`codeIndexTool`** (`engine/tools/impl/codeIndex.ts:67`) — semantic/symbol code search; falls back to `regexFallback` when the vector index returns nothing.
- **`verifyAssertion`** (`contractVerify.ts:175`) — checks a contract assertion against actual repo state; the ground truth behind `ContractAssertPass`.
- **`checkBashSafety`** (`bashSafety.ts:43`) — best-effort blocklist for destructive/blocking commands; explicitly not a sandbox.
- **`ContractState`** (`contract.ts:103`) — Definition-of-Done state machine backing the four Contract* tools; distinguishes unreplaceable `harness` contracts from `auto` ones.
- **`secretPathOf`** (`secretPaths.ts:46`) — `{ action: 'refuse' }` for the resolved `~/.cynco/tokens.json`, `{ action: 'approve' }` for `~/.ssh/**`, `.env`/`.env.*` and `/etc/shadow|passwd|sudoers`, null otherwise; Bash is `bashSafety.ts`'s to judge. Consulted in `ToolExecutor.preRun` (`executor.ts:340`), after the tripwire, sealed and immutable checks and before the protected-path check, any tier or grade.
- **`namePaths`** (`toolPaths.ts:617`) — every path one tool call names, with its operation and source (a field of a file tool, exact; or the shell scan, a tripwire); never throws, a caught error is a `faults` entry.
- **`scanShellText`** (`shellPaths.ts:7833`) — the Bash command read as the shells would read it: verbs, operands, redirects, pipelines, assignments, nested payloads and inline programs; marks a command that builds the text it runs (`selfBuilding`) and a mutation whose target cannot be read (`unresolvedMutation`).
- **`scanArgv`** (`shellPaths.ts:7853`) — the Git tool's argv exactly as git receives it, through the same git table as the shell (so `git clean -fdx`, `git config core.hooksPath ...` and `-C` read the same either way).
- **`judgePath`** (`protectedPaths.ts:187`) — pure: one real path and one operation against the run's folders; the always-denied set, the roots, first match wins.
- **`checkProtectedPaths`** (`protectedPaths.ts:761`) — the verdict for one tool call; asked by `ToolExecutor.execute` after the secret check and by the Bash tool before its shell starts.
- **`callTouchesSealed`** (`sealedPaths.ts:199`) — refuses any call whose path or Bash text names a withheld gate instrument, its basename, or its gates directory.
- **`shouldAutoApprove`** (`approvalGate.ts:18`) — decides whether a call skips the human approval prompt, given trust profile / approve-all / tool tier.
- **`DoomLoopDetector`** (`doomLoop.ts:11`) — flags a tool call repeated 3+ times with identical input and no intervening workspace change.

## Data flow
1. The conversation loop calls `ToolExecutor.execute(toolName, input)` for a model's `tool_use` block.
2. `getToolByName` (registry.ts) resolves the `ToolImpl`; an unknown name returns an error result immediately.
2b. `presenceTripwireConfirmed` (`engine/integrity.ts`, awaited): in a contained engine that lost a protected folder, or that met the integrity latch, every call is refused here with `Refused [integrity]: ...` (see "The integrity layer (slice S7)" below). A change of a protected folder counts only when a second look `TRIPWIRE_CONFIRM_MS` (1 s) later sees the same change; the call waits for that look, and a call made meanwhile waits for the same answer. A change the first look saw stands when the confirming look fails; the latch needs no second look; a confirmation that the tripwire's stop overtakes reports nothing (the starter's settle compares what is there). With no tripwire running it answers null at once.
3. `callTouchesSealed` (sealedPaths.ts) refuses the call outright if it names a withheld gate instrument.
4. `immutableTargetOf` refuses a write to a declared brief/gate path (readable, never writable).
4b. `secretPathOf` (secretPaths.ts) refuses the engine's own token file outright; any other secret path forces `requestApproval` in steps 5 and 7 below, and under approve-all is refused instead (there is no user to ask).
4c. In a contained run `checkProtectedPaths` (protectedPaths.ts) refuses a write, delete, move or link that lands outside the mission folder, the run's extra roots and its sandbox, anything handed to an unknown program inside the home's dot-entries, CynCo's own folders or a volume Windows cannot protect, and a mutation whose target it cannot read (see "Where the path check stands" below); `escalate` is logged (`[paths] escalate ...`) and allowed. It runs before any grade or approval, so approve-all does not open it. With no run context it answers allow at once.
5. If a `Grader` is set (projects mode, `setGrader`), it alone decides what happens next — `dangerous` refuses with its reason, `risky` (or a secret path, 4b) goes straight to `requestApproval`, `safe` proceeds — and steps 6-7 below are skipped entirely.
6. A download command (`isDownloadCommand`) is refused under approve-all, or forced through interactive approval.
7. `shouldAutoApprove` decides tier/trust; if not auto, `requestApproval` blocks on the human/UI before proceeding.
7b. In a contained run the call's full input is appended to the tool-call audit and fsynced (`audit.start`); a record that cannot be written ends the call here with `Refused [audit]: ...` and nothing runs.
8. `tool.execute(input, cwd)` runs the tool's own implementation (e.g. `bashTool`, `editTool`, `codeIndexTool`).
9. A successful workspace-mutating call clears `DoomLoopDetector` state; a failed repeat is checked via `doomLoop.check`.
10. Output is redacted (`redactSealed`), capped (`capToolResult`), and given a CodeIndex-adoption nudge before returning as the final `ToolResult`; `arbiterVerdict` passes through unchanged.
11. `toolScorer.record` logs success/failure for later demotion/probation decisions — except a file tool's answer to a path that does not exist (`isWrongPathAnswer`, `engine/tools/impl/pathHint.ts:51`), which is recorded neither way (F178); once the loop has marked a model call (`beginModelCall`), a second success or a second failure of the same tool in that call is not recorded either (F178).

## Containment of unattended runs

A dispatched mission starts every command the Bash tool runs through `engine/containment.ts` (F242); on 2026-11-22 one Bash call of an unattended mission deleted every dot-folder of the owner's home and then the application folders of `AppData\Local` up to `pip`, and this is the layer that makes that command fail. Who does what: `scripts/dispatch-mission.sh` mints a run id (`bun --no-install scripts/cynco-sandbox.mjs mint`) and, after its exit trap is armed and before it stops anything, creates the run's sandbox (`cynco-sandbox.mjs create`, which calls `establishContainment`): `<LOCALCODE_SANDBOX_ROOT>/<run id>/{home,tmp,scratch}` (the root, default `C:/cynco-sandbox`, is never created by the engine, a dispatch or a test: a root that does not exist is a refusal), a record `containment.json` in the run folder, written before any label, and on Windows a low label on `home`, `tmp`, `scratch` and the mission folder; the run folder itself stays medium, so the run cannot change its own record. The engine's boot block (`engine/main.ts`, after the job object, before the sibling hand-off and the model load) adopts that sandbox from `LOCALCODE_MISSION_RUN_ID` and `LOCALCODE_MISSION_CWD` (`adoptContainment`: it verifies, never creates, and on Windows runs the launcher probe in this process) and sets the run context. An unattended boot (`isContainedRun`, `engine/missionEnv.ts`: a mission key or `--run-task`) that cannot adopt one, or that finds `LOCALCODE_CONTAINMENT_OFF` set, prints `[containment] refused: containment: <reason>`, exits 1 and loads no model, and the dispatch stops on that line. The driver adopts the same record (exit 2 when it cannot) and dispatches only to an engine whose `session.ready` says `contained-tools` (`contained-overlay` off Windows; `containmentDispatchRefusal`, `scripts/cynco-contract.mjs`, exit 4). The mission folder is set back to medium when the run is released: by the dispatch's watcher after the mission engine is gone, by `dispatch_abandoned` when the dispatch stops early, or by `release-dead` at the next dispatch. A release relabels the folder's root and then walks it (never entering a link, one `icacls "<dir>\*" /L` per folder) and sets back every low label the run set on something under it itself, which the root relabel alone leaves in place (measured). A folder the run worked in is walked to its end, with no budget, one `icacls` start per folder, synchronously on the dispatch's watcher or, for a daemon task, on the daemon's event loop: minutes for a folder the size of the CynCo checkout (measured: the decision record, "Measurements for the owner"). The release then sets the sandbox's own `home`, `tmp` and `scratch` back to medium (`resetSandboxLabels`): the three tops first, then the same walk within a budget of its own, whoever releases (`SANDBOX_SET_BACK_BUDGET`: 200 folders, 2,000 calls for single entries or 5 s, whichever comes first, asked before every folder and before every call inside one; a folder's listing is read through an index of its entries). A sandbox that installs packages, whose caches land in its home, will usually pass the budget (the same record). Past the budget the rest stays labelled low, as every release left it before wave 15, the record keeps `sandboxLeftLow`, and the note says "the sandbox was not set back past <n> folders; the sweep removes it"; the sweep then removes it by its listing walk without walking it again. A release that set the whole sandbox back records `sandboxSetBackAt`, and the sweep removes that sandbox without walking it again either. Inheritance is turned back on (`icacls /reset /L`, after the label) for every entry of the sandbox that has it off; in a folder the run worked in, only for an entry that was not on the list the establish read before any label or grant (`<run folder>\inheritance-<i>.before`, one Windows PowerShell walk per work folder, capped at 300 s: entries with inheritance off, links, unreadable entries; record field `inheritanceBefore`). Those are left and named ("inheritance left off for K, which had it off before this run"); with no list (the read failed, was cut at its cap or did not say it finished, or the record is from an older engine) nothing under that folder is reset, and the note says why. An entry whose name is a device's (`nul`, `con`, `aux`, `com1` ...) or ends in a dot or a space is read, set and reset through its `\\?\` form (`asEntry`), because Win32 reads the device's own descriptor (an explicit Low label) for the one and drops the trailing dot or space of the other (measured 2026-11-25: `icacls <dir>\foo. /reset /L` turned the owner's `foo`'s inheritance back on, and .NET read `foo.` as `foo`); through `\\?\` a set and a reset succeed where the run has the rights, as in the sandbox and a granted folder (measured 2026-11-25; the denial measured on 2026-11-24 was in a folder that gave no more than Modify). ## Gotchas
- The audit's refusal returns BEFORE the `try` that holds the tool on purpose (`ToolExecutor.execute`): a call that was not recorded must not pass the doom-loop check, the scorer or the rebuild, and it is a result, never a throw. There is exactly one `tool.execute(` in `executor.ts`, and every pre-run refusal comes back from `preRun` so it is recorded in one place; both are pinned by `guards/containmentWiring.test.ts`.
- A result that carries an `exitCode` key came from a process that ran and is never read as a containment or integrity refusal (`refusalFaultOf`), so only a refusal made before a process started (no key) ends a run as a harness fault. A tool that adds a process must set the key on every result it builds after the process started, `null` when it ended with no status.
- Stop and the timeout kill a running command and what it started (F201, F210): `ToolExecutor.execute` takes the turn's abort signal as a third argument and passes it to `ToolImpl.execute`; Bash and Git act on it (Git since slice S2, `tools/gitStop.test.ts`). Bash takes ownership of its shell's process tree the moment the shell exists (`ownProcessTree(child)`, `engine/processTree.ts`: a Job Object on Windows under Bun, so a kill cannot miss a child started mid-kill; elsewhere, and under vitest's Node, the tree is found when it is killed, from the started shell the handle was given and never from its pid alone: only while the runtime has not handled the shell's exit, on Windows by a `taskkill` in the same turn of the event loop as that look (off Windows the look is made when the kill starts, and the `pgrep -P` walk after it still signals by number what it found: `docs/NOW.md` backlog); once the exit was handled the number may be another process's, so the kill starts nothing and logs `[process-tree] pid N was not killed: ...`, F255) and kills it on Stop and on its own timeout: `exec` is given no `timeout`, because exec's kill ends the shell alone. A command that ends on its own releases the handle and kills nothing, so a background process it left on purpose lives on. The result says `command stopped` or `command timeout after Nms`, never the other, and carries the output collected so far; if a survivor holds the pipes the call returns after `STOP_GRACE_MS` anyway. A call that arrives after the Stop is not started. Pinned by `engine/__tests__/tools/bashAbort.test.ts`, `engine/__tests__/processTree.test.ts` and, for the Job Object under Bun, `engine/__tests__/processTreeJob.test.ts`. The same holds since wave 15 for the sites that start workspace code without the executor (`runCommandDetailed` for a contract check and verify-first, best-of-N's `runTests`, LSP diagnostics, the daemon precheck): exec gets no timeout, and since wave 19 the four share one helper, `ownedExec` (slice S2 above), with the driver's own run of the authoring check; pinned by the `ownedExec` describe of `processTree.test.ts`, under Bun by `bypassTreesJob.test.ts`, the grace by `tools/bypassGrace.test.ts`.
