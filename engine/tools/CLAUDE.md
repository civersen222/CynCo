# engine/tools

## Purpose
Defines every tool the model can call in an agent turn — file I/O, Bash, Git, search, contract/Definition-of-Done bookkeeping, sub-agents — plus the registry, approval/safety/sealing gates, and the `ToolExecutor` that sits between a model's `tool_use` block and the filesystem/shell. The primary caller is `engine/bridge/conversationLoop.ts`; policy layers (`s5/ruleBasedS5.ts`, `vsm/*`, `agents/trustTier.ts`) narrow which tools are offered but never bypass this package's checks. It must never let a call reach a sealed gate instrument, replace a tool's own error output with engine commentary instead of appending to it, or let the model rewrite the harness contract it is measured against. Shaped directly by F34/F35/F37 (withheld/held-out gate handling), F60 (PowerShell `2>&1`), F136 (missing-file "did you mean"), and F142 (Bash timeout ceiling vs default).

## Important types & functions
- **`ToolImpl`** (`types.ts:39`) — the contract every tool exports: name, description, input schema, approval tier, core/extended flag, `execute`. Implemented by every file under `impl/`.
- **`ALL_TOOLS`** (`registry.ts:34`) — the flat tool registry every lookup/filter function in this file reads.
- **`getToolByName`** (`registry.ts:61`) — registry lookup used by `ToolExecutor`, `approvalGate.ts`, and `load_tools` to resolve a call by name.
- **`ToolExecutor`** (`executor.ts:139`) — turns `(toolName, input)` into a `ToolResult`: sealed check, immutable-path check, download gate, approval, execute, doom-loop check, redaction/cap. With a `Grader` set (`setGrader`, projects mode) one grade replaces the download gate and tier approval: `dangerous` is refused with its reason, `risky` asks, `safe` runs.
- **`ToolExecutor.beginModelCall`** (`executor.ts:203`) — the loop calls it before each model call's tool batches; from then on the trust score takes at most one success and one failure per tool per call. A caller that never calls it — a sub-agent's executor, a test — scores every call, as before (F178).
- **`ToolExecutor.runsUnasked`** (`executor.ts:172`) — whether a call to a tool would run here without a question to the user: `shouldAutoApprove` with this executor's trust profile and approve-all, and false for every tool when a grader is set (a project chat grades each call by its input). It is what the loop hands a sub-agent it starts, so a researcher's web tools never exceed the parent run's (`engine/agents/CLAUDE.md`).
- **`bashTool`** (`engine/tools/impl/bash.ts:134`) — the Bash implementation: safety check, shell-dialect translation, timeout clamp, failure formatting.
- **`bashMaxTimeoutMs`** (`engine/tools/impl/bash.ts:96`) — the hard ceiling any Bash timeout is clamped to, env-raisable up to `HARD_MAX_BASH_TIMEOUT_MS`.
- **`bashDefaultTimeoutMs`** (`engine/tools/impl/bash.ts:126`) — the timeout a Bash call gets when the model doesn't ask for one.
- **`codeIndexTool`** (`engine/tools/impl/codeIndex.ts:67`) — semantic/symbol code search; falls back to `regexFallback` when the vector index returns nothing.
- **`verifyAssertion`** (`contractVerify.ts:169`) — checks a contract assertion against actual repo state; the ground truth behind `ContractAssertPass`.
- **`checkBashSafety`** (`bashSafety.ts:43`) — best-effort blocklist for destructive/blocking commands; explicitly not a sandbox.
- **`ContractState`** (`contract.ts:90`) — Definition-of-Done state machine backing the four Contract* tools; distinguishes unreplaceable `harness` contracts from `auto` ones.
- **`secretPathOf`** (`secretPaths.ts:46`) — `{ action: 'refuse' }` for the resolved `~/.cynco/tokens.json`, `{ action: 'approve' }` for `~/.ssh/**`, `.env`/`.env.*` and `/etc/shadow|passwd|sudoers`, null otherwise; Bash is `bashSafety.ts`'s to judge. Consulted at the top of `ToolExecutor.execute` (`executor.ts:207`) before any tier or grade.
- **`namePaths`** (`toolPaths.ts:431`) — every path one tool call names, with its operation and source (a field of a file tool, exact; or the shell scan, a tripwire); never throws, a caught error is a `faults` entry.
- **`scanShellText`** (`shellPaths.ts:2373`) — the Bash command read as the shells would read it: verbs, operands, redirects, pipelines, assignments, nested payloads and inline programs; marks a command that builds the text it runs (`selfBuilding`) and a mutation whose target cannot be read (`unresolvedMutation`).
- **`scanArgv`** (`shellPaths.ts:2392`) — the Git tool's argv exactly as git receives it, through the same git table as the shell (so `git clean -fdx`, `git config core.hooksPath ...` and `-C` read the same either way).
- **`judgePath`** (`protectedPaths.ts:186`) — pure: one real path and one operation against the run's folders; the always-denied set, the roots, first match wins.
- **`checkProtectedPaths`** (`protectedPaths.ts:465`) — the verdict for one tool call; asked by `ToolExecutor.execute` after the secret check and by the Bash tool before its shell starts.
- **`callTouchesSealed`** (`sealedPaths.ts:199`) — refuses any call whose path or Bash text names a withheld gate instrument, its basename, or its gates directory.
- **`shouldAutoApprove`** (`approvalGate.ts:18`) — decides whether a call skips the human approval prompt, given trust profile / approve-all / tool tier.
- **`DoomLoopDetector`** (`doomLoop.ts:11`) — flags a tool call repeated 3+ times with identical input and no intervening workspace change.

## Data flow
1. The conversation loop calls `ToolExecutor.execute(toolName, input)` for a model's `tool_use` block.
2. `getToolByName` (registry.ts) resolves the `ToolImpl`; an unknown name returns an error result immediately.
3. `callTouchesSealed` (sealedPaths.ts) refuses the call outright if it names a withheld gate instrument.
4. `immutableTargetOf` refuses a write to a declared brief/gate path (readable, never writable).
4b. `secretPathOf` (secretPaths.ts) refuses the engine's own token file outright; any other secret path forces `requestApproval` in steps 5 and 7 below, and under approve-all is refused instead (there is no user to ask).
4c. In a contained run `checkProtectedPaths` (protectedPaths.ts) refuses a write, delete, move or link that lands outside the mission folder, the run's extra roots and its sandbox, and anything handed to an unknown program inside the home's dot-entries, CynCo's own folders or a volume Windows cannot protect; `escalate` is logged (`[paths] escalate ...`) and allowed. It runs before any grade or approval, so approve-all does not open it. With no run context it answers allow at once.
5. If a `Grader` is set (projects mode, `setGrader`), it alone decides what happens next — `dangerous` refuses with its reason, `risky` (or a secret path, 4b) goes straight to `requestApproval`, `safe` proceeds — and steps 6-7 below are skipped entirely.
6. A download command (`isDownloadCommand`) is refused under approve-all, or forced through interactive approval.
7. `shouldAutoApprove` decides tier/trust; if not auto, `requestApproval` blocks on the human/UI before proceeding.
8. `tool.execute(input, cwd)` runs the tool's own implementation (e.g. `bashTool`, `editTool`, `codeIndexTool`).
9. A successful workspace-mutating call clears `DoomLoopDetector` state; a failed repeat is checked via `doomLoop.check`.
10. Output is redacted (`redactSealed`), capped (`capToolResult`), and given a CodeIndex-adoption nudge before returning as the final `ToolResult`; `arbiterVerdict` passes through unchanged.
11. `toolScorer.record` logs success/failure for later demotion/probation decisions — except a file tool's answer to a path that does not exist (`isWrongPathAnswer`, `engine/tools/impl/pathHint.ts:51`), which is recorded neither way (F178); once the loop has marked a model call (`beginModelCall`), a second success or a second failure of the same tool in that call is not recorded either (F178).

## Containment of unattended runs

A dispatched mission starts every command the Bash tool runs through `engine/containment.ts` (F242); on 2026-11-22 one Bash call of an unattended mission deleted every dot-folder of the owner's home, and this is the layer that makes that command fail. Who does what: `scripts/dispatch-mission.sh` mints a run id (`bun scripts/cynco-sandbox.mjs mint`) and, after its exit trap is armed and before it stops anything, creates the run's sandbox (`cynco-sandbox.mjs create`, which calls `establishContainment`): `<LOCALCODE_SANDBOX_ROOT>/<run id>/{home,tmp,scratch}` (the root, default `C:/cynco-sandbox`, is never created by the engine, a dispatch or a test: a root that does not exist is a refusal), a record `containment.json` in the run folder, written before any label, and on Windows a low label on `home`, `tmp`, `scratch` and the mission folder; the run folder itself stays medium, so the run cannot change its own record. The engine's boot block (`engine/main.ts`, after the job object, before the sibling hand-off and the model load) adopts that sandbox from `LOCALCODE_MISSION_RUN_ID` and `LOCALCODE_MISSION_CWD` (`adoptContainment`: it verifies, never creates, and on Windows runs the launcher probe in this process) and sets the run context. An unattended boot (`isContainedRun`, `engine/missionEnv.ts`: a mission key or `--run-task`) that cannot adopt one, or that finds `LOCALCODE_CONTAINMENT_OFF` set, prints `[containment] refused: containment: <reason>`, exits 1 and loads no model, and the dispatch stops on that line. The driver adopts the same record (exit 2 when it cannot) and dispatches only to an engine whose `session.ready` says `contained-tools` (`contained-overlay` off Windows; `containmentDispatchRefusal`, `scripts/cynco-contract.mjs`, exit 4). The mission folder is set back to medium when the run is released: by the dispatch's watcher after the mission engine is gone, by `dispatch_abandoned` when the dispatch stops early, or by `release-dead` at the next dispatch. A release relabels the folder's root and then walks it (never entering a link, one `icacls "<dir>\*" /L` per folder) and sets back every low label the run set on something under it itself, which the root relabel alone leaves in place (measured). A release that could not set everything back says so in its note and, from `cynco-sandbox.mjs`, on stderr as `[sandbox] NOT SET BACK:` with exit 3 (the watcher writes it to the driver log); the next `create` for that folder then refuses while it still reads low and no live run holds it. A folder holding a file with a second name (a hard link) is refused before it is labelled, because a label set on that file would reach its other names. A sandbox folder is deleted only by the sweep, seven days after it was created, and the sweep never follows a link.

From boot on, the run context decides, never a message's `unattended` flag: a note typed into the dashboard during a mission runs contained too. Three things are done to each child. Its environment is built by `toolEnv`: HOME, USERPROFILE, HOMEDRIVE, HOMEPATH, APPDATA, LOCALAPPDATA, TEMP, TMP and TMPDIR point into the sandbox; `CYNCO_SCRATCH` names the run's scratch folder; PATH is kept; PYTHONUSERBASE names the real user site so installed packages are found; GIT_CONFIG_GLOBAL names a `.gitconfig` in the sandbox home that includes the owner's (which the run cannot write); the containment's own keys and the secrets (`SECRET_ENV`) are dropped. On Windows it is started by `engine/lowIntegrityLauncher.ts` (with `--no-env-file` and its own `bunfig.toml`, in the checkout, so nothing the run wrote is read while it is still medium), which lowers its own token to low integrity through bun:ffi and reads the level back before it builds the child's environment and starts the child, so the child and everything it starts are low. Stop and the timeout end the whole tree through the job taken on the launcher's pid (`ownProcessTree`, F201, F210); a `maxBuffer` overflow kills the launcher, and its child was measured to die with it (`containmentLauncher.test.ts`), which is not guaranteed by construction. And it is refused, by name (`Refused [containment]: <reason>. ...`, no exit code), when the run has no working launcher (not Bun, a launcher file missing, a token that would not lower, a launcher that exited 197): there is no downgrade to the overlay alone on Windows. Each contained command costs the launcher's start, measured on the owner's PC at about 30 ms on top of a PowerShell start and about 90 ms on top of a bare `cmd` one.

**What low integrity blocks (measured on NTFS by the Bun fixture and by hand):** creating, changing, renaming or deleting anything in a folder that is not labelled low, which is everything except the run's sandbox, its mission folder and its extra roots: the home folder and every dot-folder in it, CynCo's own checkout and state folder, the run's own record; and making a junction that leads out of what it may write. A configuration file planted in the mission folder or the sandbox home (`bunfig.toml`, `.env`) is not read by the launcher, nor one in the launcher's own working folder (the fixture shows each of `--no-env-file` and `--config=` is what stops it).

**What it does not block:** (1) reading: the run can read whatever the owner can, `~/.ssh` and `~/.cynco/tokens.json` included, and it has the network; (2) other places labelled low: the mission folder itself, other runs' sandboxes, `AppData\LocalLow`, and a folder a dead run left labelled until it is released; (3) volumes without integrity labels: exFAT and FAT drives and network shares are fully writable to it (a sandbox is refused while one is attached and not acknowledged in `LOCALCODE_UNPROTECTED_VOLUMES_OK`), and a hard link carries a label to every name of the file, which is why a mission on CynCo itself works in a clone made with `git clone --no-hardlinks`; (4) brokers: a service that acts for its caller at its own level (Docker, WSL, WMI, Task Scheduler, a COM server, the engine's own API once the token file is read) was not tested and must be assumed open; (5) what the run leaves behind: code in the mission folder is executed later by whoever runs it, at their level (the harness's own git is the one case that is neutralised, by `harnessGitEnv`); (6) the file tools (Read, Write, Edit and the rest), which run inside the engine at medium (the path check below is the only layer that judges them); (7) anything off Windows beyond the environment overlay; (8) an API that ignores the environment (`[Environment]::GetFolderPath`, `os.userInfo().homedir`) still answers the real home: a write there is denied on Windows, a read is not.

A PowerShell child's non-ASCII output through the launcher came out as UTF-8 in every run measured; the same command run directly (an uncontained Bash call) depends on the console the engine was started in, and was measured garbled in one run.

**What stops working in a contained run on Windows:** nothing that needs Git's msys runtime starts while any other Git Bash is running, which during a dispatched mission is always, because the dispatch itself runs in one: `bash`, `sh`, the programs of Git's `usr\bin` (`grep`, `sed`, `tail`, `head`, `ls`) and a commit in a repository with a shell-script hook fail, and the result carries a `[containment]` hint naming the PowerShell forms (`containmentHint`, also on a pipeline that exits 0 with the error on stderr). A Python program that asks for a temporary file in a folder it may not write spins until its timeout instead of failing, and the timeout result says so (pytest from such a folder needs `-p no:cacheprovider`). `pip install --user` and `git push` over ssh have nowhere to write or no key. Removed uses: a mission in a git worktree, in a subfolder of a repository, in the engine's own checkout or inside a dot-folder of the home folder is refused when its sandbox is created; the driver run by hand against an engine it did not start exits 2. Interactive sessions, the phone engine and project chats are not contained; their Bash children only lose `CYNCO_MISSION_ALSO_LABEL` from the environment. `LOCALCODE_CONTAINMENT_OFF` (`lowil`) is honoured only for a test's context (vitest's Node has no bun:ffi); set at all, it refuses every real run.

**Every other site that runs workspace code (slice S2).** The engine's sites start their child the same way: the Git tool and its after-commit `git status` (`containedCommand` into `Bun.spawn`; the tool's own git, so it keeps the repository's hooks and gets no `harnessGitEnv`; because a hook or a program a setting names can then hold the call, its tree is owned from the start and Stop or a cap of `bashDefaultTimeoutMs()` ends git and what it started, with `git <sub> stopped` or `git <sub> timeout after Nms`, and it is given `GIT_TERMINAL_PROMPT=0`, `GIT_EDITOR=:`, `GIT_SEQUENCE_EDITOR=:` and `GCM_INTERACTIVE=never`, so a commit with no message is refused at once and nothing waits on a person; pinned by `tools/gitStop.test.ts`), ApplyPatch, a contract check command and verify-first (`runCommandDetailed`, `toolExec`), best-of-N test runs (`runTests`, `toolExecSync`) and LSP diagnostics (`tsc`, `py_compile`). When the run's launcher cannot run, each starts nothing: the Git tool and ApplyPatch answer `Refused [containment]: ...` (ApplyPatch writes no patch file; the after-commit check answers `[]`), a contract check is `unrunnable` with that text as its tail (a launcher exit of 197 or 198 is `unrunnable` too, never `failed`), `runTests` returns `refused` and the loop applies no best-of-N candidate (`**Best-of-N:** the candidates' tests could not be run, ...`), and LSP gives no diagnostics and logs `[lsp] diagnostics not run: ...`. In a contained run the best-of-N worktrees are made in the sandbox's scratch folder. Contract commands and verify-first no longer inherit `LOCALCODE_MISSION_*`, `CYNCO_MARKER_CHECK*` or `CYNCO_MISSION_ALSO_LABEL` in any mode, as the Bash tool never did. Every one of these children gets the tool environment (`toolEnv`) in every mode, interactive sessions included, so each now also runs Python in UTF-8 mode (`PYTHONIOENCODING=utf-8`, `PYTHONUTF8=1`), as the Bash tool's child already did. Pinned by `tools/containedSpawnSites.test.ts` (each refusal, the sandbox home, the Git tool's environment through the vitest `Bun.spawn` shim, the best-of-N block) and, under Bun, by the fixture's `throughTheSites`, `sitesLauncherRefused` and `precheck` cases. The daemon's runs are contained too (the flow is in `engine/daemon/CLAUDE.md`): `TaskRunner` refuses a one-shot before it takes the GPU when the sandbox root does not exist, makes a `daemon-task` sandbox after its busy check, hands the run id to the child engine in the task file (which the child adopts at boot) and releases it however the child ended; a trigger's precheck command runs through `toolExec` in a `precheck` sandbox with no label on its folder and answers `skip: precheck not run: <reason>` when it cannot run; and the daemon sweeps the sandbox root once when it starts, which also releases a run whose holder is gone. The scripts' sites are contained too: `runSync` / `runAsync` (`scripts/cynco-spawn.mjs`) take a `contained` option, either a run context or `{ own, extraRoots?, labelOwn? }`, for which a `grader` sandbox is made around `own` and released when the command has ended; a command that could not be started contained is not started and comes back as `fault.code === 'ECONTAINMENT'` (`[spawn] REFUSED: containment: <reason> — nothing was run`), and a launcher exit of 197 or 198 with its line is a fault (`ECONTAINMENT`, `ECHILDGONE`), never the command's own status, so every caller reads "did not run", never a failing gate. So is an exit 1 whose stderr carries Bun's `error: EPERM reading "<file>"` line (`launcherFaultOf`): a Bun the launcher started could not load its script at low integrity (below). A mutation sweep that faulted reads `sweep did not run (...)`, and a suite baseline is written only after a pytest exit of 0 or 1. A grader or calibration run by hand establishes a `grader` sandbox too, so it needs the sandbox root, Bun, and every unprotected volume acknowledged; the root is created once by `scripts/cynco-containment-setup.ps1 -Apply` (`docs/containment-setup.md`), or is another existing folder named in `LOCALCODE_SANDBOX_ROOT`. A caller that is already low integrity (read from its own token) runs the command directly, with no second sandbox. The driver's marker check and probe run under its adopted context (`runCheck` / `runCheckAsync`, `scripts/cynco-verify.mjs`). Every grader run is contained: the sealed gate and the suite gate around the repository, the mutation sweep without a label (it never writes the repository), the mid-wave progress probe's gate without a label on its archive (`labelOwn: false`), and calibration's gate, perturb, positive and suite-baseline runs around the BASE folder; a baseline run that faulted or timed out writes no baseline (entry 1.B2: an empty baseline would read as "no standing failures"). The ideation one-shot gets a `daemon-task` sandbox (no label: its tools only read), its run id and workspace in the task file, and starts in the checkout (rule H1). The authoring dispatch hands its BASE archive to `dispatch-mission.sh` in `CYNCO_MISSION_ALSO_LABEL`, which labels it for the run as an extra root (`cynco-sandbox.mjs create --also`). Pinned by `scripts/__tests__/cynco-spawn.test.mjs`, `cynco-verify-faillines.test.mjs`, `cynco-campaign-calibrate.test.mjs`, `cynco-campaign-grade.test.mjs`, `cynco-campaign-progress.test.mjs`, `cynco-ideation.test.mjs`, `cynco-gate-author.test.mjs`, `cynco-work-snapshot.test.mjs` and `cynco-workspace.test.mjs`; a test that runs a real gate does so under a test context (`scripts/__tests__/fixtures/graderContainment.mjs`).

**Harness git.** The git the harness itself runs in a folder a contained run may have written runs with `harnessGitEnv` (`engine/harnessGit.ts`): no hooks, no `core.fsmonitor`, no filter the repository defines, no pager or editor, and, no signature verification by a program the repository names (`log.showSignature=false`, `gpg.ssh.program` and `gpg.x509.program` pinned, the SSH allowed-signers file a path that is never created: a planted signed commit made a plain `git log` run the repository's program); and, for a call given `{ repo }`, the repository named outright by `GIT_DIR` and `GIT_WORK_TREE` (a `core.worktree` planted in `.git/config` beats a command-scope `-c core.worktree`, measured on git 2.53) after `<repo>/.git` is checked to be the repository's own folder: a `.git` file naming another repository, a `commondir` or `gitdir` file in `.git`, a link as `.git`, among its entries or under its `refs` and `logs`, or a linked worktree whose administrative folder does not name it back refuses the call (git is given a `GIT_DIR` it can neither open nor create, exit 128, logged once as `[harness-git] git refused in <folder>: <why>`), and a folder with no `.git` gets `GIT_CEILING_DIRECTORIES` so git cannot walk up to a repository around it (the indexer passes `nested: true`, since an index may be built for a subfolder: the repository above is found and judged the same way). A `GIT_DIR` the caller names itself (the snapshot's store) is judged the same way; a call whose working folder is the mission folder starts `harnessGitBin()`, so a `git.exe`, `git.cmd` or `git.bat` planted there is never the one run. The sites: the contract's git reads, best-of-N's `git apply`, patch extraction and worktree calls, the loop's `git init`, `rev-parse`, `merge-base` and `status`, the Write tool's `ls-files`, the indexer, the snapshot, the dashboard's mission log and `gitFacts`; the driver's own git in the mission folder (`log`, `rev-parse`, `status`, `checkout -- .`, `reflog`), `scripts/cynco-work-snapshot.mjs`, the workspace purges' `ls-files`, and the campaign runner's, the spec loader's, the smoke campaign's, calibration's `git archive` and the authoring runner's git in a mission repository or staging folder. Pinned by `harnessGit.test.ts`, whose left-behind fixture plants each surface (signed commits and an `export-subst` file included) and calls the engine's sites and the scripts' functions (`purgeBytecodeCaches`, `purgeStaleAgentState`, `snapshotUncommittedWork`, `archiveBase`, `restoreUncommittedWork` with its `commitStaging`) for real, and whose redirect cases show each redirect committing into the other repository without the helper and refused with it. What it does not cover: an external diff or textconv driver is not switched off by configuration, so only the patch-producing `git diff` calls carry `HARNESS_DIFF_FLAGS` (`--no-ext-diff --no-textconv`), and a new patch-producing diff without them would run one; a call without `{ repo }` (`rev-parse`, `ls-files`, `log`) still follows a planted `core.worktree` or `.git` redirect (it runs nothing and writes nothing; the Write tool's `ls-files` then answers "not tracked", which keeps the shrink guard on); an `objects/<xx>` folder inside `.git` that is a link is not checked (a commit then writes object files elsewhere, never a branch tip); and git the harness runs anywhere else (a project chat's history, the CynCo checkout) has no `harnessGitEnv`.

**The path check (slice S4).** In a contained run every tool call that reaches `ToolExecutor.execute` or the Bash tool is judged by `checkProtectedPaths` before it runs, whatever the message's `unattended` flag says and with or without approve-all; a sub-agent's executor is judged the same way. The paths come from `namePaths` (`toolPaths.ts`): a file tool's target is a field and is judged exactly, on its real path (a link or junction inside the mission folder that leads out is judged where it lands); the Bash command and the Git tool's argv are read by `shellPaths.ts`, a tripwire. Home spellings (`~`, `$HOME`, `$env:USERPROFILE`, `%USERPROFILE%`, `[Environment]::GetFolderPath`, `Path.home()`, `os.homedir()` ...) name the REAL home whatever the run's environment says; temp spellings and `CYNCO_SCRATCH` name the sandbox. The refusal is `Refused [protected path]: <reason>. Nothing was run.` followed by the paragraph that names the mission folder and the scratch folder; it never names the audit or guard folder and passes through `redactSealed`; the engine log line is `[paths] refused <rule> <tool>: <real path or ->`. A faulty context refuses every call as layer `containment`, and so does the boot: step 4 of the boot block (`pathGuardFault`, four probe decisions against the live context) refuses the run before the model loads, and `session.ready` says `path-guard` only when the probe passes (`engine/bridge/CLAUDE.md`). An `escalate` verdict (deleting the mission folder itself, a git command that throws away work, a recursive delete through a target that cannot be read) is allowed and logged as `[paths] escalate <rule> <tool>: <targets> (allowed: no decision model is installed)`. Pinned by `tools/shellPaths.test.ts`, `tools/toolPaths.test.ts`, `tools/protectedPaths.test.ts` (the attack and pass tables under a Windows context with literals and under a host context on temp folders), `guards/pathGuardCapability.test.ts` and the S4 block of `guards/containmentWiring.test.ts`.

**What the path check refuses:** a write, delete, move or link outside the mission folder, the run's extra roots and the sandbox's `home`, `tmp` and `scratch`; anything at all, reads included, inside the audit or guard folder, or a call whose text names either; and, as a write-class target, an operand handed to a program it cannot read or a script it would run, or a path beside a mutation through a variable, a pipeline or a computed path: the home folder itself, every dot-entry of it, CynCo's state, models, guard and audit folders, other runs' sandboxes, the run's own containment record, the engine's checkout (write-class only), any folder that contains one of these, a network share, a volume Windows cannot protect and a drive the run has no folder on (judged on the spelling, never touched); a file-tool write under a root's `.git`; a `git config` that sets anything but `user.name` / `user.email`; a link whose target is outside the roots; a command that builds or decodes the text it runs (`iex`, `[scriptblock]::Create`, a call operator or dot-source applied to a group, `$ExecutionContext.InvokeCommand`, `Invoke-Command` / `Start-Job` with `-ArgumentList`, a program fed on standard input by anything but an `echo` or a literal, a code call that starts a shell with a command it cannot read); a recursive delete or move through a word that starts with a name nothing set followed by a separator (`"$EMPTY"/*`, `"$env:UNSET\.cache"`), read as the root of the current drive, so rule `ancestor` (entry 4.M3's incident shape; a loop variable, a `param` and an assigned name are not "nothing set"); a device path; a command it cannot read (over 1 MiB, nested deeper than 4, more than 512 paths with a write-class verb). The brief's seven attacks are refused in mission form and in literal form.

**What the path check does not refuse:** (1) anything that does not spell its target: a script written with `Write` and then run, a module run with `-m`, a path assembled at run time or read from a file (`Get-Content list.txt | Remove-Item` and `Import-Csv` input are an unresolved mutation: refused only beside a protected mention, escalated only when recursive), the registry or WMI, a name assigned in one call and used in the next, a non-recursive delete through an unknown variable (`Remove-Item $env:X\y`: unresolved, no record), `subst` or `net use`, a code call that is not in the table (the table holds Python's `os`, `shutil`, `subprocess` and their import aliases, Node's `fs`, `fs.promises` and `child_process` and their aliases, Bun's `write`, `file().delete`, `spawn`, Perl's `File::Path`, `unlink`, `system`, and .NET's `File`, `Directory`, `MoveTo`, `CopyTo`, `Delete`; anything else, a `pathlib` method on a computed path or another library, is not read), a program's own behaviour (on NTFS the low-integrity token holds there; on D:, exFAT and FAT drives and network shares nothing does: the check is the only layer, so a walk-around there is a real loss); (2) for the file tools it is the only layer: a bug in `namePaths` or a new tool with a wrong `TOOL_PATH_TABLE` row is a direct write anywhere; (3) reads, apart from the audit and guard folders and the sealed and secret checks (the shell can read `~/.ssh` and the token file); (4) a link made between the check and the write; (5) shell idioms the tokenizer does not model (splatting, a script block's own parameters, cmd's delayed expansion `!X!` of a name set in the same line and `for /f` over a command's output, PowerShell 7 syntax, a quoted multi-word argument to `Start-Process -ArgumentList` or `schtasks /tr`; a PowerShell double-quoted string eats backticks, so a JavaScript template literal inside one is read as PowerShell would pass it); (6) brokered execution (`wsl`, `docker`, `schtasks`, `wmic`, `runas`, `ssh`); (7) what is not a file (`setx`, HKCU writes, profile edits, `format D:`, `diskpart`); (8) a junction on the home's drive that leads to a sleeping share still costs a realpath on the event loop (F225); (9) a lexical fallback of `realPathOf` can hide a junction; (10) the engine's own stores (learnings, journals, trajectories); (11) the probe shows the function answers correctly, not that the executor calls it (that is pinned by source text); (12) harness commands (contract, check, probe, grader, test runs), which the launcher contains. Known false refusals the model is told how to work around: a write to `C:\tmp`, a join that spells a mission path through the home, a delete through a variable beside an unrelated outside mention, a script in a home dot-folder run by path, `git -C` outside the roots; and, since the review of 2026-11-23, a command started from code with a command built at run time (`subprocess.run(cmd)`, `os.system(f'...')`), a call operator on a computed program (`& (Join-Path $d python.exe)`), `Invoke-Command` / `Start-Job` with `-ArgumentList`, a program piped into an interpreter from a file (`Get-Content x.ps1 | powershell -`), and a recursive delete through an unset name such as `$PSScriptRoot` (empty in a Bash call) followed by a separator.

**What is still not contained, and why.** The scan in `engine/__tests__/guards/containmentWiring.test.ts` lists every file under `engine/` and `scripts/` that starts a process, with its class and a one-sentence reason; a new process-creating call that nobody classified fails it (`npm run audit:wiring`). The scan is lexical: it sees the spawn names and their aliases (`{ exec as run }`, `import * as proc`, `git = runSync`, `const { spawn } = Bun`), a spawn function handed in (`io.run(`, `this.exec(`), `Bun.$` and a template-literal import of child_process; it does not follow a function into another file, which is why every `io.run(` of the graders and every git spawn of the driver are also pinned call by call. The not-contained rows start no code the run wrote: the one-shot engine itself (`TaskRunner`, the ideation one-shot), which starts in the checkout at the daemon's or runner's integrity and contains its own tools by adopting the sandbox it was handed; the authoring runner's own `bun --check` child, which starts in the checkout and whose gate runs are contained by calibration; Grep and CodeIndex's `rg` / PowerShell / `grep`, which start with no working folder and take the model's pattern after `-e` (until 2026-11-23 a Grep pattern was a bare positional argument, so `--pre=<program>` would have run that program on every file searched, outside the containment); LSP's `which` / `where`; the shell-dialect check (it parses, runs nothing); the audit's `git rev-parse` in the engine's own folder; a project chat's history git; llama-server, the apps, the power helpers, the sweeps and the developer tools. Interactive sessions, the phone engine and project chats are not contained at all. `dispatch-mission.sh`, the `.cmd` and `.ps1` launchers and the Python scripts are outside the scan. The file tools (Read, Write, Edit and the rest) run inside the engine at medium and are stopped only by the path check of slice S4.

**Measured and open (2026-11-23, Bun 1.3.13):** a Bun process at low integrity cannot load any module file from a folder that is not labelled low (`error: EPERM reading "<file>"`). Only module loading fails (the script it is started with, `import()`, `require`): the same low Bun process reads the same file as data (`readFileSync`, `Bun.file`), and node runs the same script. So the gate-authoring check (`bun <checkout>/scripts/cynco-gate-author.mjs --check ...`), run by the model, the contract or the driver inside a contained authoring mission, exits 1 before it reads anything (06 entry A7 does not hold). That exit is read as "did not run" (`launcherFaultOf`: a `Refused [containment]: Bun at low integrity could not read <file> (EPERM) ...` refusal, an `unrunnable` contract check, a driver harness fault), never as a failed check; the Bun fixture's `authoringCheck` case pins it. The gate-authoring mission cannot complete under containment until the owner decides how the check runs (the driver running it as a harness process from the checkout, which is the recommendation, or authoring dispatches refused). With S2 every site that runs workspace code for an unattended run starts contained, and with S4 every tool call is judged by the path check, but the tool-call audit and the integrity latch (slices S5, S7) are not in place: whether a mission is dispatched on this layer is the owner's decision. Recovery commands for the owner: `bun scripts/cynco-sandbox.mjs status | release <id> | release-dead --kind mission | sweep`. Pinned by `engine/__tests__/containment.test.ts` (every refusal, the environment, the argv, the switch, release and sweep), `guards/containedCapability.test.ts`, `guards/containedBootRefusal.test.ts`, `bridge/containedWithoutUnattendedFlag.test.ts`, `guards/containmentWiring.test.ts`, `scripts/__tests__/cynco-sandbox.test.mjs` and, for the Windows layer under Bun (never on CI), `containmentLauncher.test.ts` with `fixtures/containedShell.ts`.

## Gotchas
- Stop and the timeout kill a running command and what it started (F201, F210): `ToolExecutor.execute` takes the turn's abort signal as a third argument and passes it to `ToolImpl.execute`; Bash and Git act on it (Git since slice S2, `tools/gitStop.test.ts`). Bash takes ownership of its shell's process tree the moment the shell exists (`ownProcessTree`, `engine/processTree.ts`: a Job Object on Windows under Bun, so a kill cannot miss a child started mid-kill; elsewhere, and under vitest's Node, the tree is found when it is killed) and kills it on Stop and on its own timeout: `exec` is given no `timeout`, because exec's kill ends the shell alone. A command that ends on its own releases the handle and kills nothing, so a background process it left on purpose lives on. The result says `command stopped` or `command timeout after Nms`, never the other, and carries the output collected so far; if a survivor holds the pipes the call returns after `STOP_GRACE_MS` anyway. A call that arrives after the Stop is not started. Pinned by `engine/__tests__/tools/bashAbort.test.ts`, `engine/__tests__/processTree.test.ts` and, for the Job Object under Bun, `engine/__tests__/processTreeJob.test.ts`.
- The path check is exact for the file tools and a tripwire for shell text (`protectedPaths.ts`, `shellPaths.ts`): a field path is judged where it really lands; a shell command is judged on what it spells, and refuses what it cannot read rather than guess.
- Home spellings name the real home whatever the run's environment says (`currentHomes`, `toolPaths.ts`): under the overlay the shell would expand `$HOME` to the sandbox, but the check must not stand down on the other layer's word, the incident command was exactly this shape, and two spellings (`[Environment]::GetFolderPath`, `os.userInfo().homedir`) were measured to ignore the environment.
- The sealed, immutable and secret checks keep their old arm and gain one fed by `namePaths` (nested `MultiEdit` edits, patch headers, a decoded payload, real paths), in every mode; the sealed check's real-path arm covers the gates directory too, so a `Grep` / `Ls` / `Glob` field or a pattern's fixed folder (a `Grep` `glob`) that really lies in it through a junction of another name is refused (review 2026-11-23); a `Bash` command stays judged on its text alone, so one that reads the gates through such an alias is left to layer 4, which discards the output; a refuse of the secret check now wins over an approve. A new tool therefore needs a `TOOL_PATH_TABLE` row (`toolPaths.ts:250`); `tools/toolPaths.test.ts` fails until it has one.
- `bashSafety.ts` is unchanged by the containment work: its environment rule is pinned as it was (`guards/pathGuardCapability.test.ts`).
- `bashSafety.ts` is explicitly "NOT a sandbox — trivially bypassed... The real protection is Bash tier='approval'" — pinned by `bashSafety.test.ts`.
- `Bash` is deliberately absent from `executor.ts`'s `WORKSPACE_MUTATING_TOOLS` even though the shell can write files — a named, accepted blind spot (finding (f)), not an oversight.
- Downloads never ride on approve-all, including the mission driver's — even unattended runs get a refusal that sends them to the staging folder the brief names by its full path, never to a home spelling, since under containment `~` in a shell is the sandbox home (`approvalGate.ts`, F242), pinned by `approvalGate.test.ts` and the S3 block of `guards/containmentWiring.test.ts`. Secret paths follow the same rule (`secretPaths.ts`, pinned by `secretPaths.test.ts`): a `.env` under approve-all is refused, not read.
- `fetchGuarded` (`impl/webFetch.ts`, used by `WebFetch` and by `AddToKnowledge` by URL) looks every hop's name up before it connects: a name with ANY address in a range a literal address is refused for is refused with `Blocked: <name> resolves to <address> (<range>)`, and the request then goes to the checked address with the name in `Host` and in the TLS handshake (`pinnedFetch`), so a second lookup cannot answer differently. Until 2026-11-17 only the URL was read, and a public name resolving to 127.0.0.1 reached this PC's own dashboard. The ranges are the ones a literal address was already held to, plus three IPv6 forms added the same day with the owner's yes (NAT64 and 6to4 carrying a refused IPv4 address, and site-local); an IPv6 address is read as its eight groups, so every spelling of it is one address. There is no switch, and a test that injects `fetch` injects `resolve` too. Decision: `docs/decisions/2026-11-17-webfetch-resolves-names.md`. Pinned by `impl/__tests__/webFetch.test.ts`.
- A web page or a search snippet is data: `WebFetch` and `WebSearch` return it between the `untrusted.ts` lines, and the one sentence that explains them is `TOOL_RESULTS_ARE_DATA` in `engine/engine/systemPromptText.ts` (pinned by `untrustedContent.test.ts`). The lines shrink the chance of an injection; the approval cards contain it.
- The sealed-gate refusal (F37) is four layers (reference/enumeration/location/content); read-only alone was insufficient because a command can read gate content while spelling no sealed name. Pinned by `sealedPaths.test.ts`. A data instrument named by a `CHK_SUITE_BASELINE=` prefix (the suite baseline's bare node ids) is sealed by path only — `setTaskSealedPaths`' `contentExempt`, from `contractAutoCreate.ts`'s `contentExemptGatePaths` (Phase 7 T6-N1) — or the model's own `pytest --collect-only` output would be discarded.
- A withheld contract assertion's `command` must never appear in a failure message (F34) — naming it would leak every mutation anchor to the model being graded on defeating them.
- A verification command that is killed by its timeout is `unmeasured`, never `contradicted` (F35) — a timeout must not be recorded as a "no". Pinned in `contractVerify.ts`'s own tests.
- `arbiterVerdict: true` marks an honest "not yet" from a declared arbiter so the doom-loop breaker does not fire on a run correctly re-asking the same graded question.
- Windows PowerShell 5.1 has no `&&`/`||`, and a trailing `2>&1` makes a successful command look failed (F60) — `bash.ts` strips it and reports both streams instead. Pinned by `shellInfo.test.ts` and `bash.test.ts`.
- Bash timeouts have two ceilings, not one: `bashDefaultTimeoutMs` (what a call gets unasked) and `bashMaxTimeoutMs` (hard clamp on any override) — F142 was an operator raising one env var while a separate constant still capped it.
- The Bash tool's shell never inherits the harness's keys: `toolEnv` (`engine/containment.ts`, re-exported from `impl/bash.ts` as `bashToolEnv`) drops `LOCALCODE_MISSION_*`, `CYNCO_MARKER_CHECK*` (the driver's marker check, Phase 7 final review I1) and `CYNCO_MISSION_ALSO_LABEL` in every mode, while the engine process keeps them; in a contained run it also drops the containment's own keys and the secrets. Pinned by `bash.test.ts` and `containment.test.ts`.
- `Write` refuses to shrink a git-tracked file below half its size unless the file is untracked; delete-then-write is the deliberate escape hatch. Pinned by `writeShrinkGuard.test.ts`.
- A path that does not exist is the model's guess, not the tool failing: Read, Edit, MultiEdit and ReplaceFunction answer it with `missingFileHint` (the folder's listing and a "did you mean", F136), and `ToolExecutor` leaves that answer out of `ToolScorer` (`isWrongPathAnswer`, `engine/tools/impl/pathHint.ts:51`, keyed on `MISSING_FILE_PREFIX` at `engine/tools/impl/pathHint.ts:39` and checked on the tool's own output, before the cap or a nudge). Scored as a failure, three guessed prompt-file names in one parallel Read batch demoted Read in a live project chat, and with Read withheld the model read its files through Bash `Get-Content` (F178, 2026-10-13). A refusal that is not a wrong path — a folder given to Read, an Edit whose `old_string` is not there — is scored as before. Pinned by `engine/__tests__/tools/wrongPathTrust.test.ts`.
- A batch the model fired together is one decision: once the caller marks model calls (`ToolExecutor.beginModelCall` (`executor.ts:203`), called by the loop where it clears the circuit breaker's per-call strikes), the trust score records at most ONE success and ONE failure per tool per model call (`executor.ts:342`): a call that both succeeded and failed with a tool counts one of each. Scored per call in the batch, three failed Edits in one call made Edit 0/3 (confidence 0.2, under the 0.35 threshold) and `excludeForIteration` withheld it from the calls that followed, the same shape as the wrong-path demotion above (an F178 open item). The unit is the model call on both sides: capping failures alone let a call of three good Reads outweigh three later calls that each failed (3 of 6, 0.5, kept offered; one of each per call it is 1 of 4, 0.33, demoted). A sub-agent's executor and the tests never mark a call and score every call, as before. Pinned by `engine/__tests__/toolScorer.test.ts`.
- `Edit`/`MultiEdit` normalize CRLF to LF before matching and restore CRLF on write — without it a multi-line `old_string` never matches a CRLF file. Pinned by `edit.test.ts`, `editNearMiss.test.ts`, `multiEdit.test.ts`.
