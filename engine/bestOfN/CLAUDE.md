# engine/bestOfN

## Purpose
Implements best-of-N candidate sampling for `engine/bridge/conversationLoop.ts`: when enabled, it runs the model loop N times in isolated git worktrees, scores each attempt by test pass rate, and applies only the winning patch to the real working tree. It exists so a risky turn can be retried under different sampling temperature without corrupting the user's actual repo if a candidate goes off the rails. It must never leave a worktree behind (each candidate's worktree is removed when that candidate is done, and `WorktreeManager.cleanupAll()` in a `finally` removes the rest) and must never apply a patch that fails `git apply --check` first or writes through a link.

## Key files
| File | Role |
|---|---|
| `types.ts` | Shared types: `TestInfo`, `CandidateResult`, `SamplerConfig`, `SamplerResult` |
| `testDetector.ts` | Sniffs the project root to decide which test framework/command to run |
| `worktreeManager.ts` | Creates/tracks/removes detached git worktrees used to sandbox each candidate |
| `patchExtractor.ts` | Captures a unified diff of all changes (tracked + untracked) in a worktree |
| `sampler.ts` | Runs tests, parses their output, picks the winning candidate, applies its patch |

## Important types & functions
- **`extractPatch`** (`patchExtractor.ts:114`) - `extractPatch(cwd, label?)`. Before `git add -A` it walks the candidate's worktree one level at a time by the folders' own listings, never into a link or `.git` (`stagedLinks`), and asks git `ls-files -z` (the index) and `check-ignore -z --stdin` about the folders and links of each level (names; it walks nothing). A folder below the top that lists a `.git` entry is not entered when harness git in that folder is not refused (`isHarnessRefused`) and answers `rev-parse --verify -q HEAD` (`embeddedRepo`): an embedded repository, which `git add -A` stages as one gitlink and never enters (measured on git 2.53, wave 19, check C4-8); any other `.git` (an empty folder, a file naming nothing, one harness git refuses) is walked as before, because `git add -A` enters such a folder and stages what a link in it leads to (measured). These git calls go through `execFileSync` with no shell and a 60 s cap (`GIT_TIMEOUT_MS`); the cap ends git itself wherever `<Git>\mingw64\bin\git.exe` stands beside a `<Git>\cmd\git.exe` launcher that comes first on PATH, because `harnessGitBin` then starts the real one (wave 19b; before, a cap ended the launcher alone and left git running, measured). The `git add -A`, `git diff --cached` and `git reset` that follow are started the same way, one argument vector through `harnessGitBin` under the same cap (wave 19c, check D19b-6; until then they ran through `execSync` with no cap): a git that hangs is ended at the cap and the candidate gives `''`. Pinned by `bestOfN/harnessGitCap.test.ts`. A folder or link is passed over only when git ignores it and the index holds nothing at or under it. A link git would stage, a folder that cannot be listed, more than 200,000 listed entries (`LINK_WALK_LIMIT`), or a git that cannot answer gives `''` and the log line `[bestOfN] candidate N (<worktree>) made a link (...); it is not applied` or `... could not be read whole (...); it is not applied`. A junction under an ignored `node_modules` no longer refuses a candidate; a tracked symbolic link checked out as one (Developer Mode) still does. Then it stages, diffs against HEAD (`--no-ext-diff --no-textconv`) and unstages, and returns the diff byte for byte, never trimmed: `git apply` needs the newline after the last hunk line (F162). Called once per candidate by `conversationLoop.ts` after the candidate's model loop finishes.
- **`selectWinner`** (`sampler.ts:15`) - filters out candidates with empty patches, sorts by `passRate` descending then `totalTurns` ascending, returns the top candidate or `null`. Called by `conversationLoop.ts` after all candidates have run.
- **`runTests`** (`sampler.ts:53`) - `runTests(cwd, testInfo, capMs?, signal?)`, asynchronous since wave 15. It asks `presenceTripwireConfirmed` first (after a loss: nothing runs, a refused record, `containmentFault('integrity')`, `refused`). A command one Windows command line cannot carry, or one over 8,000 characters that names a POSIX shell such as bash or sh, whose `-c` text Git's bash cuts (`longCommandRefusal`, `engine/tools/impl/bash.ts`, wave 19b), is not started: `refused` with that text and a refused audit record with no layer, and no containment fault; a spawn that throws anyway (`ENAMETOOLONG`) is `refused` too. That line is the one measured with the Bash tool's PowerShell (32,000 characters, `MAX_WINDOWS_COMMAND_CHARS`). `runTests` starts the command through cmd (`toolExec`, and the launcher's shell in a contained run), whose own limit is lower: from about 8,185 characters cmd answers `The command line is too long.` with exit 1 and runs nothing (measured through exec, 2026-11-25), so such a command scores 0/0 and is never run cut short (check D19b-4; refusing it here is backlog). Then it asks the containment's spawn refusal and writes the audit start record; it starts `testInfo.command` through `toolExec` with its process tree owned from the moment the root exists (`ownedExec`, `engine/processTree.ts`), ends the tree on its own timer (`TEST_RUN_CAP_MS` = 120 s, `sampler.ts:36`, or `capMs`; logged `[bestOfN] tests cut at their cap of N ms; their process tree is ended`) with a 2 s grace, and, when a Job Object holds the tree, on an output overrun (5 MiB; a walked tree is released then, because exec answers after the root's exit was handled: wave 24, F255); it gives the tree back when the run ends on its own. Its fourth argument, `signal`, is the turn's Stop (wave 19): it ends the tree at once, as the cap does (logged `[bestOfN] tests stopped with the turn; their process tree is ended`), and a run asked after a Stop starts nothing (`refused: 'the turn was stopped'`). A launcher that could not run (exit 197 or 198) is refused with no score and raises the containment fault. stdout and stderr are parsed with `parseTestOutput` even after a non-zero exit or a cut. The event loop is free while the tests run (F225). Pinned by `bestOfN/runTestsTree.test.ts`, `bestOfN/runTestsLauncherRefused.test.ts`, `longCommandSites.test.ts`, `bypassTreesJob.test.ts` (the Job Object), `tools/bypassGrace.test.ts` and `audit/bypassSites.test.ts`.
- **`applyPatch`** (`sampler.ts:290`, `patchPaths` `sampler.ts:135`) - `applyPatch(repoRoot, patch, refused?)` returns false, never throws, and hands `refused` the reason, which the loop's page shows (`... won (p/t tests) but its patch was not applied: <reason>`). Refused: an empty patch; a folder harness git refuses (read by `isHarnessRefused`, any of the refusal's marks, wave 19b; because `git apply` under the refusal's `GIT_DIR` alone ran as outside a repository and applied anyway, measured); a patch whose paths cannot be read (a quoted name with an escape it does not know, an absolute path, `..`, a header that cannot be split, a hunk whose lines do not add up to its header: hunk lines are content, so a removed `-- note` line is never read as a file name); on Windows, a path component that ends in a dot or a space or holds a backslash (Windows reads it as another name, and git's own refusal of those, `core.protectNTFS`, is the repository's to switch off) or holds `:<>"|?*`, judged on every component before the walk, those under a folder that does not exist yet included; a path whose way from the folder crosses a link, a folder that cannot be listed, or an entry that exists and is not listed by that name (another case is matched by folding; an 8.3 short name is not: measured, `git apply` writes through a junction named by its short name); then `git apply --check -` and `git apply -`, each one argument vector through `harnessGitBin` with no shell and the 60 s cap `GIT_TIMEOUT_MS` (wave 19c, check D19b-6; until then a git that hung there held the event loop): a git that hangs there is ended at the cap and the patch is not applied (`git apply --check refused it: ... ETIMEDOUT`, `git apply failed: ... ETIMEDOUT`). Whether an apply ended at its cap can leave part of the patch written was not measured. Only the paths the patch names are walked, so a link elsewhere (an install's junction) no longer refuses an honest winner, and no folder is walked whole. Residual: a link made between the walk and `git apply` is not seen. Pinned by `bestOfN/applyPatchLinks.test.ts` and `bestOfN/harnessGitCap.test.ts`.
- **`detectTests`** (`testDetector.ts:22`) — checks, in order, for pytest config, jest config, vitest config, a non-default `package.json` `scripts.test`, `Cargo.toml`, then `*_test.go` files; returns `{ available: false, ... }` if none match.
- **`WorktreeManager`** (`worktreeManager.ts:173`) — the constructor prunes the repo's stale `cynco-bestofn-*` worktrees, and also lifts the lock on, and prunes, a `cynco-bestofn-*` registration whose folder is gone wherever it was (`isGoneBestOfNWorktree`: unlocked, or its `cynco-bestofn pid=N` lock names a pid that is not running; metadata only: a contained run's worktree lived in its sandbox's scratch, which the sweep deletes), and never throws (a failed scan is logged; every git call has a 60 s cap, `GIT_TIMEOUT_MS`; an early ETIMEDOUT — bun's stale deadline, F155 — is retried once only for the idempotent list/prune/unlock calls, never for `worktree add --lock`; every git call of the manager is one argument vector through `harnessGitBin` with no shell, and `exec`, the test seam, is `(file, args, options)`, by default `execFileSync` (wave 19b, check D19-1: a path git registered, or the folder a link led to, never reaches a shell, where cmd expanded a `%NAME%` in it and a POSIX shell would run a `$(...)`)); `create()` (`worktreeManager.ts:190`) makes a detached worktree from HEAD in the OS tmpdir (via `mkdtempSync` and `git worktree add --detach --lock --reason cynco-bestofn pid=<pid>` into that empty folder; a failed add leaves no empty folder behind: `rmdirSync`, which never recurses, removes it; a folder git wrote into is left as it is, and a link put in its place is removed as an entry on Windows and left on POSIX; wave 19c, check D19b-1). It then refuses a new worktree that its folder does not list as a folder: `git worktree add` checks out into an empty folder that a link made at the path leads to and registers the worktree there (measured), and in a contained run the tmp root is the sandbox scratch, which a low process may write. The link is removed as an entry, the registration git made at the folder it led to is unlocked (nothing there is deleted), the log says `[bestOfN] the new worktree <p> is not a folder at its own path ...`, and `create()` throws, so the loop falls back to a single pass. That is detected after git's checkout, not prevented: git has already written HEAD's checkout into the folder the link led to. `cleanup()`/`cleanupAll()` remove the worktrees: first every link in the worktree is removed as an entry, never entered, by a walk of the folders' own listings with no entry bound (a worktree in which a link cannot be removed, or a folder cannot be listed, is left in place and named in the log), then `git worktree remove --force --force`, falling back to a retried `rmSync` + unlock + `git worktree prune`, logging what it could not remove; `getActive()` returns a copy of the tracked paths, `registered()` parses `git worktree list --porcelain`.
- **`isStaleBestOfNWorktree`** (`worktreeManager.ts:121`) — the prune predicate: basename starts `cynco-bestofn-`, parent is the tmp root, and the worktree is unlocked or its `cynco-bestofn pid=N` lock names a pid that is not running. Any other worktree (the main tree, a phase worktree, one locked for another reason) is never touched.
- **`parseTestOutput`** (`sampler.ts:27`) — thin wrapper over `parseTestSummary` from `../bridge/testSummary.js`, returning `{ passed: 0, total: 0 }` when the framework's output can't be parsed.

## Data flow
1. `conversationLoop.ts` checks `LOCALCODE_BEST_OF_N` and calls `detectTests(cwd)`; if no framework is found, best-of-N is skipped entirely.
2. For each of `bonCount` candidates, `WorktreeManager.create()` makes a fresh detached worktree from HEAD and `conversationLoop` points `this.executor` at it, then runs the model loop with a turn cap and elevated temperature.
3. After the loop, `extractPatch(wtPath, 'candidate N')` captures the diff and `await runTests(wtPath, testInfo, undefined, turnSignal)` scores it; the result is pushed into a `candidates` array (shape matching `CandidateResult`), the `bestOfN.candidate` frame goes out, and the candidate's worktree is removed (`cleanup(wtPath)`) before the next candidate starts. A run whose tests were refused stops the sampling, and no candidate is applied; so does a Stop of the turn, which the loop checks between the steps of each candidate and hands to `runTests` (wave 19: the page says `**Best-of-N:** stopped, so no candidate was applied.`).
4. Once all candidates have run, `selectWinner(candidates)` picks the best one.
5. If a winner exists, `applyPatch(mainCwd, winner.patch, refused)` applies its diff to the real working directory; if apply is refused, the page names why (`... but its patch was not applied: <reason>`, and a `[bestOfN] the winner's patch was not applied: <reason>` log line) and the caller falls through to a normal single-pass turn. Either way the loop emits `bestOfN.selected` (`winner`, `passRate`, `applied`), which the mission driver's collector (`scripts/cynco-ledger.mjs`) records on the ledger row as `bestOfN[]` — so an unapplied winner is readable per mission (F162). The loop's earlier `bestOfN.start` frame is what turns the row's `bestOfN` from `null` (never started) into `[]` (started, no winner selected).
6. `WorktreeManager.cleanupAll()` runs in a `finally` block and removes whatever step 3 did not (a throw, a refusal).

In a contained (unattended) run (F242, `engine/containment.ts`): the worktrees are created under the sandbox's scratch folder (`tmpRoot: runContainment()?.sandbox.scratch`), which the run's low-integrity children may write; `runTests` starts the tests through `toolExec` and owns their tree, and when the run's launcher cannot run it starts nothing and returns `refused`, the loop stops sampling, applies no candidate and says `the candidates' tests could not be run`. Every git this package runs carries `harnessGitEnv` (`engine/harnessGit.ts`), and `extractPatch`'s diff carries `--no-ext-diff --no-textconv`. Pinned by `engine/__tests__/tools/containedSpawnSites.test.ts`.

## Gotchas
- `extractPatch` always runs `git add -A` then `git reset HEAD` even on the read path — a caller that races another git command against the same worktree concurrently will corrupt the diff; this package assumes single-threaded, one-worktree-per-candidate use, as pinned by "leaves the worktree unstaged after extraction" in `engine/__tests__/bestOfN/patchExtractor.test.ts`.
- `applyPatch` never throws on a bad patch — both the check and real apply are wrapped in `try/catch` returning `false` — so callers must check the boolean return rather than relying on exceptions; the reason goes to its third argument. The malformed cases are pinned by "says why when git apply refuses it" and "refuses a patch whose paths it cannot read" in `bestOfN/applyPatchLinks.test.ts`.
- `WorktreeManager.create()` (`worktreeManager.ts:190`) checks git out into the empty folder `mkdtempSync` made: `git worktree add` refuses an existing folder only when it is not empty (measured on git 2.53, 2026-11-25: an empty folder is checked out into, a non-empty one is refused with "already exists"). Until wave 19b the folder was removed first, which opened a window for a link to be made at the path before the checkout (check D19-2). A low process that may delete in the sandbox scratch folder can still swap the empty folder for a link before git checks out; `create()`'s look after the add sees that and refuses the worktree (detected after the checkout, not prevented).
- Two worktrees leaked from 2026-05-28 until Phase 5 although the caller's `finally` ran `cleanupAll()` (F162). Root cause INFERRED from what was left on disk (every root-level file gone, subdirectories and `.git` left), not reproduced: on Windows `git worktree remove` failed while something held a file in the tree, the old fallback's `rmSync` threw partway and the error was swallowed, and `git worktree prune` keeps an entry whose directory still exists. The fix is that failures are logged and every new manager prunes what an earlier one could not; pinned by `engine/__tests__/bestOfN/worktreeManager.test.ts` and `engine/__tests__/bridge/bestOfNCleanup.test.ts`. The caller's `finally` restoring the executor's cwd before `cleanupAll()` is hygiene only (`setCwd` sets a string, holds no handle), not part of the leak fix.
- `WorktreeManager.cleanup()` has a fallback (`git worktree remove --force --force` → retried `rmSync` → `git worktree unlock` → `git worktree prune`); the unlock is load-bearing because every worktree is created locked and a locked entry survives a plain prune. Pinned by the "fallback path" test in `engine/__tests__/bestOfN/worktreeManager.test.ts`.
- The constructor's bare `git worktree prune` drops the admin entry of EVERY unlocked worktree in the repo whose directory is missing, whatever its name — metadata only, never a directory. A worktree on a briefly unreachable drive needs `git worktree repair` afterwards.
- `SamplerConfig` and `SamplerResult` in `types.ts` are exported but not imported anywhere outside this directory — `conversationLoop.ts` builds candidate objects inline instead of constructing a `SamplerResult`, so don't assume those two types reflect the real call shape.
- `detectTests` checks Python/pytest signals before JS/TS ones, so a mixed-language repo with both a `pytest.ini` and a `jest.config.js` will always resolve to pytest.
