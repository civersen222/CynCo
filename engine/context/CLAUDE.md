# engine/context

## Purpose
Compaction of a conversation that is filling the model's context window: a cheap trim of oversized tool results, an LLM summary of the older messages, the most recent messages kept verbatim, and pinned anchors (the contract brief, the original task, recent user requests, the task's commits) so the literal ask is never summarized away. It also keeps the record of which files the task read and changed across compactions (`FileOperationTracker`). The package owns the order of a compaction and its counts; the caller owns the model call and the journal. Its one caller is `ConversationLoop.compactNow` (`engine/bridge/conversationLoop.ts:3151`), which serves every compaction there is: the four a turn makes on its own and the one a person asks for with `/compact`. This document owns compaction as a whole, the loop's two methods that run it (`compactNow`, `compactOnRequest`) included; `engine/bridge/CLAUDE.md` only says where the loop calls it. It must never summarize a message and also keep it, never leave a tool result in the kept tail whose call was summarized, and never drop the source messages before the summary has been handed to the journal (write-before-compact; a journal write that fails is logged and the compaction goes on, Gotchas). Failure-log entries that shaped it: F92, F129, F243 (see `docs/cynco-failure-log.md`).

## Key files
| File | Role |
|---|---|
| `compressor.ts` | The whole package: `FileOperationTracker` (files read and modified, per compaction window and for the whole task) and `ContextCompressor` (when to compress, where the kept tail starts, the tier-0 trim, the summary prompt, the anchors, `runCompaction`). Pure of I/O: the summary call and the journal write are callbacks. |

## Important types & functions
- **`ContextCompressor`** (`compressor.ts:114`) - built once per loop (`engine/bridge/conversationLoop.ts:562`, threshold 0.75, `keepRecent` left at its default of 4 pairs). `shouldCompress` (`compressor.ts:123`) says whether the estimated tokens are at the threshold of the context length and there are more than `keepRecent * 2` messages; the s5-decision and loop-threshold compactions ask it.
- **`runCompaction`** (`compressor.ts:318`) - one compaction: tier-0 trim, one count for both halves (`keptTailStart`), the summary prompt of everything before the tail, `summarize`, `journal`, the summary plus the kept tail (`compressMessages`, `compressor.ts:375`), the anchors spliced in after the summary, the commit log anchor when the caller measured one, and the tracker's window closed. Returns the messages it was given, unchanged, when nothing is left to summarize.
- **`keptTailStart`** (`compressor.ts:142`) - where the verbatim tail starts: `keepRecentPairs * 2` messages from the end, moved back to the `tool_use` of any `tool_result` in the tail, repeated until no result in the tail points before it. The selection (`selectForCompression`) and the kept tail (`compressMessages`) both read it, so they never overlap and never leave a message out.
- **`tier0Trim`** (`compressor.ts:167`) - shrinks every text over 4,000 characters inside a `tool_result` to its first and last 2,000 characters with a `[trimmed N chars]` marker, in the shape the loop builds (`content: [{ type: 'text', text }]`), a string `content` and a top-level `text`; a block of another type (an image) is left as it is.
- **`selectVerbatimAnchors`** (`compressor.ts:265`) - the pinned messages: the contract brief as a system message, the first user message with text as `[Pinned original task]`, and up to six recent user requests as `[Pinned user request]`, both as real `user` turns. `keptFrom` is the start of the kept tail: a request (or the original task) already in the tail is not pinned again. Logs one `[compact] anchors:` line.
- **`buildStructuredSummaryPrompt`** (`compressor.ts:201`) - the summary prompt: Goal, Progress, Files Modified, Files Read, Constraints, Next Steps, the files of this window from the tracker, and the conversation's text blocks, each cut to 500 characters.
- **`FileOperationTracker`** (`compressor.ts:25`) - `record(path, tool)` per file tool call (and `ShellWrite` for a path git saw change across a Bash call). The `...ThisWindow` getters answer the summary prompt (since the last compaction); `getModifiedFiles` / `getReadFiles` answer for the whole task, compactions included. `reset()` archives the window rather than dropping it; `serialize()` is the whole task, journalled with each compaction, and `deserialize` puts it back on resume (`engine/bridge/conversationLoop.ts:1212`).

## Data flow
1. A compaction is asked for at one of five points, all through `compactNow` (`engine/bridge/conversationLoop.ts:3151`): pre-turn (`engine/bridge/conversationLoop.ts:2181`, estimated tokens over the loop config's `contextManagement.warningThreshold`, default 0.4 of the context length), s5-decision (`engine/bridge/conversationLoop.ts:2556`), loop-threshold (`engine/bridge/conversationLoop.ts:3541`), in-loop over 80 % (`engine/bridge/conversationLoop.ts:4379`), and `/compact`. The four in a turn pass the turn's Stop signal.
2. `/compact` (`engine/main.ts:963`) calls `ConversationLoop.compactOnRequest` (`engine/bridge/conversationLoop.ts:1673`), never a private member of the loop. It is refused while a turn or another compaction runs (`processing` or `currentTurn` set). Otherwise it holds `processing` and is the loop's `currentTurn` for the whole compaction, so a project or chat switch aborts it and waits for it, and it runs as a model request for the activity registry. Stop (`abort()`) and a five-minute cap (`compactRequestCapMs`) end it through its own signal (`compactionStop`), which reaches the side query's request. Its `finally` clears all of that on every exit, a throw included, clears a Stop pressed meanwhile, ends its activity and re-dispatches a click queued meanwhile (`redispatchQueuedClick`, `engine/bridge/conversationLoop.ts:1648`). The answer (`CompactAnswer`, `engine/bridge/conversationLoop.ts:349`) says whether it was refused, whether it compacted, and the estimated tokens and messages before and after.
   While it runs, a typed message meets the loop's busy guard and is answered with a `session.error` that starts `busy: a compaction is running` and says to press Stop or wait (behind a turn the same text starts `busy: a turn is still running`); a `ui.action` click is queued, never refused. Pinned by `engine/__tests__/bridge/compactOnRequest.test.ts`.
3. `compactNow` returns false with six messages or fewer. Otherwise it takes the journal of the conversation it compacts, measures the task's commits (`commitsSince` against the contract's baseline), and calls `runCompaction` with `keepRecentPairs: 2`, the summary through the side query (8,000 tokens, F92) with its Stop signal, and a `journal` callback that only holds the entry.
4. `runCompaction` trims, cuts at `keptTailStart`, asks for the summary, hands it to `journal`, then builds `[summary, ...anchors, ...kept tail]`. The summary system message carries the tracker's file operations.
5. Back in `compactNow`: when its signal was aborted, or `this.messages` is no longer the array it started from (a session switch, a resume), nothing is journalled and nothing replaced. Otherwise the held entry goes into that conversation's own journal and then the messages are replaced (write-before-compact).

## The three defects fixed in wave 15 (2026-11-24; found by the review of F243)
F243 itself (one compaction had two counts, so four messages were both summarized and kept) was fixed before them: `runCompaction` computes the count once and hands it to both halves. Its review found three more, listed in `docs/NOW.md` until wave 15 fixed them, each with a test that failed on the code before:
- **(a) The tier-0 trim trimmed nothing real.** It trimmed only a top-level `text` on the `tool_result` block, a shape the loop never builds; every real tool result (`content: [{ type: 'text', text }]`) went into the summary prompt and the kept tail whole. `tier0Trim` now trims the text blocks inside `content`, a string `content` and a top-level `text`. Pinned by "trims a tool_result in the shape the loop builds" and "trims a tool_result whose content is a string" in `__tests__/context/tier0Trim.test.ts`.
- **(b) The cut was positional, not pair-aware.** An in-loop compaction runs with the model's tool calls pushed and their results not yet in, so a cut four messages back could start the kept tail on a result whose call was summarized away, which a strict chat-completions endpoint rejects. `keptTailStart` moves the cut back to the call (not forward past the result: the result is what the model just read). Pinned by "never starts the kept tail on a tool_result whose tool_use was summarized" in `__tests__/context/runCompaction.test.ts`.
- **(c) A recent request was sent twice.** `selectVerbatimAnchors` pinned a user request that was also in the kept tail, so in a text chat it reached the model twice. It takes `keptFrom` and pins neither a recent request nor the original task that the tail holds; the cap still counts them, so the six most recent requests are verbatim somewhere and no more is pinned than before. Pinned by "does not pin a user request that the kept tail already holds" and "does not pin the original task when the kept tail already holds it" in `__tests__/context/runCompaction.test.ts`.

## Gotchas
- **One decision, one number (F243).** The count of kept pairs is computed once in `runCompaction` and passed to both halves; `compressMessages` takes it as its fourth argument and falls back to `keepRecent` (4 pairs) only when called alone. The loop asks for 2 pairs, so a compaction keeps the last four messages verbatim (more when `keptTailStart` moves the cut back to a call). `runCompaction.test.ts` checks that the halves are complementary, not only that the result got smaller.
- **A tool result survives a compaction only in the kept tail.** The summary prompt carries text blocks only, each cut to 500 characters, so a tool result before the tail is gone apart from its path in the tracker. Since F243 a mission keeps two tool results verbatim after a compaction where it kept four; whether that changes the work after a compaction is not measured (`docs/NOW.md`).
- **Anchors are real `user` turns.** A compacted conversation whose only user content is a system message, or a `tool_result`, is the shape Qwen's chat template refuses (llama-server answered 400 mid-run): the original task and the recent requests are pinned as `user` messages, the contract brief and the commit log as `system`. The first user message with text is the mission and is pinned whatever the cap (F129: three CivKings missions drifted from their brief over repeated compactions).
- **Anchors never reach the journal.** They are spliced in memory; the journal holds the summary and the file operations. The `[compact] anchors:` log line is the only record of whether the original task survived (`contract=`, `originalTask=`, `recentUserPins=`).
- **Write-before-compact is split across the two packages.** `runCompaction` calls `journal` before it builds the replacement, and `compactNow` holds that entry and appends it, to the journal it took before the side query, only after its two checks pass and right before it replaces the messages. A journal write that fails is logged and does not stop the compaction.
- **A stopped compaction replaces nothing.** The signal reaches the side query's request; a summary that comes back after a Stop, or for a conversation that was swapped under it, is dropped with a `[compact] <label>: ...; nothing replaced` line. Stop during a compaction a turn makes (pre-turn, s5-decision, loop-threshold, in-loop) aborts that side query too, through the turn's controller; before wave 15 Stop waited for the summary. Pinned by `context/runCompaction.test.ts`, the compactNow test in `tools/conversationLoop.test.ts` and `bridge/compactOnRequest.test.ts`.
- **The tracker has two lifetimes.** `reset()` closes the summary's window but keeps the whole task's record, which `diffClean` and every training row's `filesTouched` read; throwing the window away once lost a whole task's file record after its first compaction. `deserialize` restores the whole log into the current window, so the first summary after a resume may list files from before the last compaction, the safe direction to be wrong in.
