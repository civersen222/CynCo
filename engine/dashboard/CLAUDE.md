# engine/dashboard

## Purpose
The governance dashboard: one Bun server on the bridge port + 1 (`server.ts`) that serves the single-page UI (`index.html`, read once at engine start), the token-gated `/ws` and `/api/*` routes, and the phone-access boundary (`access.ts`). The phone-access model (local vs remote peers, pairing, device tokens) is recorded in `docs/decisions/2026-10-22-phone-access.md`; the mission schedule routes and why they are inference-scoped in `docs/decisions/2026-11-08-mission-schedule-control.md`. The page is a view over files the daemon and the owner already write; the dashboard owns `schedule.json`, the daemon owns `state.json`.

## Important types & functions
- **`classifyClient`** (`access.ts:59`) — a loopback peer on a loopback listener is `local`; everything else is `remote` and gets a page with no token in it.
- **`readMissionsView`** (`missionsApi.ts:158`) — `GET /api/missions`: per mission its triggers with effective cadence in words, `enabled`, `overridden`, `nextFire` (a computed preview with `nextFirePreview: true` until the daemon has seen the new cadence), `lastRun` (newest `runs.jsonl` record per trigger, `kind` from `runKind`), the GPU claim from `gpu-busy.json`, and `scheduleStatus` (`ok`/`absent`/`bad` from `readSchedule`; on `bad` the page shows a warning and locks that card).
- **`patchTrigger`** (`missionsApi.ts:179`) — `PUT /api/missions/<id>/triggers/<tid>`: validates the body (cron must parse and fire within four years, `at` is `HH:MM`, `timeoutMs` 60 000 to 7 200 000), merges it into `schedule.json` atomically (a body naming any cadence field first drops the old override's cadence fields, keeping `enabled` and `timeoutMs`); `{ "reset": true }` removes the override; 409 and no write while `schedule.json` is unreadable.
- **`setPaused`** (`missionsApi.ts:216`) — `POST /api/daemon/pause`: `writeControl` with `by: 'dashboard'`.
- **`readAppsView`** / **`setAppManagedApi`** (`appsApi.ts`), **`DashboardServer.handleApps`** (`server.ts`) — `GET /api/apps` lists each app with how it serves its model, whether it holds the GPU now (`holding` says what), whether CynCo manages it and whether it is owed its server; `PUT /api/apps/<id>` `{ "manage": boolean }` switches one app and answers with the new view (400 for any other body, 404 for an unknown id, nothing written either way). `liveAppsDeps` trusts one reading of the model port's holder for 5 s, because it is a PowerShell call.
- **`MissionHistory.page`** (`missionHistory.ts`) — `?offset=&limit=&campaign=` (an id, or `none` for the missions run under no campaign): `{ total, offset, limit, campaign, groups, missions, errors }`. Each row: missionId, campaignId (`campaignFrom` `ledger` or `waves`), `campaignLink`, cwd, briefFile, dispatchedAt, durationS, outcome, verified, `check` (command and result in words), exitReason, commitRange, turns, graderProbes and `ledger` (`<shard>:<line>`).
- **`DashboardServer.getCampaign`** (`server.ts`) — every campaign under `~/.cynco/campaigns`, any repository. A row reads its spec from the absolute `specPath` the runner records in state.json, else from the CivKings briefs folder (`spec.from`: `state` or `legacy`; `spec.missing` names a recorded spec that is gone), and its `home` (repository, held-out family, briefs folder, roadmap) through `scripts/cynco-campaign-home.mjs`, loaded lazily like the scoreboard; `budgetWaves`, `roadmapLine` and each proposal's `approveCommand` come from that spec. The top-level `roadmap` is still the CivKings one.
- **`DashboardServer.handleMissions`** (`server.ts:1591`) — the three routes' handler.
- **`DashboardDeps.getIntegrity`** (`server.ts:138`) - the integrity latch on `/api/session`, as `integrity: { state, summary, at? }` (`clear`, `latched` or `unusable`), read through `deskIntegrity` (`engine/integrity.ts`, wired in `engine/main.ts`): the latch's public summary, when, by whom and why it was set and what it stops, never a path. Absent from the deps, the field is absent. The Missions tab, on the desk and on the phone, draws `Integrity latch: <summary>` (or `Integrity: <summary>` when the guard folder cannot be used) above the daemon line (`missionsHeaderHtml`), and `loadMissions` asks `/api/session` on each of its polls for it; a failed ask keeps the last answer (wave 15). Pinned by `dashboard/integrityLatch.test.ts`.
- **`DashboardServer.proxyListener`** (`server.ts:1189`) — the HTTPS proxy's listener (`LOCALCODE_DASHBOARD_PROXY_PORT`, unset by default): `127.0.0.1` on its own port, the same routes, and every client on it `remote` (the handler is called with `forceRemote`, so the peer's address is never asked). `tailscale serve` forwards the tailnet's HTTPS name to it; it must never be pointed at the desk's port.
- **`parseProxyPort`** (`access.ts:139`) — the variable as a port (1-65535) or null; anything malformed is no listener.
- **`parseWakeUrl`** (`wake.ts:52`) — `LOCALCODE_DASHBOARD_WAKE_URL` as `{ url, origin }`, or null for anything that is not https, carries a user or password, or has a fragment; the constructor warns when a set value is refused. **`wakeAssets`** (`wake.ts:224`) — the worker's and the waking page's bodies and headers; the page's CSP names its own script and style by hash and allows `connect-src` to this origin and the doorman's only.
- **`ReplayBuffer`** (`replay.ts:118`) — `record(event)` numbers a frame that draws the Chat pane and returns the JSON to send (consecutive `stream.token`/`stream.thinking` frames join one entry and share a `seq`, `off` says how far into it a frame reaches); `since(cursor)` is what a returning page has not seen, all of it or none (`gap`); `reset()` starts a new epoch.
- **`DashboardServer.broadcast`** (`server.ts:2566`) — every engine event to every dashboard socket. A `project.opened` resets the replay buffer and tells connected pages (`replay.state`, `reason: 'reset'`) before the frame goes out; a replayed type is numbered and kept even with nobody connected.
- **`DashboardServer.handlePhoneAdmin`** (`server.ts:1260`) — `/api/phone*`, management scope and so desk-only: the pairing code, the listeners, each device with `lastSeenAt` and `expiresAt`, `revoke`, `revoke-all` (also rotates the code) and `rotate`. One route is gated before it and is not management: `GET /api/phone/code` answers the code, the lockout, the listeners and the proxy target to a client that is local **and** holds the inference token (the desk page), so pairing a phone needs no token hunt; a paired phone is refused there with 403, because a device that could read the code could pair more devices (owner's decision of 2026-11-17, amendment in `docs/decisions/2026-10-22-phone-access.md`). The device records and their idle expiry live in `engine/security/localToken.ts` (`touchDevice`, `expireIdleDevices`, `revokeAllDevices`).
- **`DashboardServer.authenticate`** (`server.ts:1379`) — who presented the token. Off this machine only a `device-*` record authenticates; it first forgets devices idle past `DEVICE_IDLE_EXPIRY_MS` and then marks the holder seen.

## Data flow
1. The Missions tab polls `GET /api/missions` every 10 s while visible. A save sends `PUT`, which returns the trigger as `GET` would show it.
2. `schedule.json` changes reach the running daemon on its next 30 s tick; the row's next fire turns from preview to real after that. No restart. See `engine/daemon/CLAUDE.md` § Schedule overrides.
3. Pause and Resume write `daemon-control.json`; the daemon and the desk widget read the same file.
4. Reconnect: the page puts its cursor on the socket URL (`replayQuery`), the server's `open` sends the frames after it and then `replay.state`, the page drops any numbered frame at or before its cursor (`replayAccept`) and applies `/api/session`'s run state only after `replay.state` (`whenReplayed`). Decisions still open come from `/api/session` `pending`, never from the replay.

## Gotchas
- The three mission routes gate at the `inference` scope for every method, before the generic method-based split in `server.ts` (the comment at `server.ts:799`). They are operational switches, not configuration: a paired phone and the desk page hold only the inference token. `scopes.test.ts` pins both rules.
- `/api/apps` gates by method before the generic split: `GET` at `inference`, so a paired phone can read which app holds the GPU; anything else at `management`, which the remote rule makes desk-only. The page shows a remote client the same rows with no switch (`appRowModel`), and the engine refuses the `PUT` from off this machine whatever token is sent. Pinned by `engine/__tests__/dashboard/appsApi.test.ts`. Reading can register an app: asking who holds the model port runs the same discovery the engine uses, which writes what it finds to `apps.json`.
- `missionsApi.ts` never writes `mission.json` or `state.json`, and `nextFire` shown for a disabled trigger is the daemon's advancing value; the page shows "off" instead.
- The dashboard is the long-running "CynCo headless engine" Task Scheduler job, not a per-pass process: after a change to `server.ts` or `missionsApi.ts`, restart that job (`cynco-services.ps1`) or the old code keeps serving.
- No request body is read before it is bounded: `maxRequestBodySize: MAX_REQUEST_BODY_BYTES` (`server.ts:57`, one upload plus its multipart framing) makes Bun refuse a declared length over it, and the handler refuses a `Transfer-Encoding` body with 411 on every route, before the token check, because Bun's cap does not cover a chunked body (measured under Bun 1.3.13: 60 MB chunked reached the handler). The suite's `Bun.serve` shim does not take the option; `requestBodyBound.test.ts` pins the 411 and the option's presence.
- `GET /`, `/manifest.webmanifest`, `/icon-192.png` and `/icon-512.png` are the only routes that answer without a token, on every listener, and `/sw.js` and `/waking` join them while a wake address is set (`wake.ts`; unset, they meet the token check like any unknown path). Nothing else may join them without a reason of the same kind: static, nothing about the engine in it, and fetched by the browser with no Authorization header.
- **The phone's wake** (`wake.ts`, index.html "Waking the PC", F256). Only a remote page on https with a wake address registers the worker (`registerWakeWorker`); the desk never does and is never sent the address (`window.__CYNCO_WAKE_URL` is null there). The worker handles GET page loads of its own origin and stores `/waking` and nothing else; its `VERSION` is a hash of the waking page and its own text, so a new address reaches a phone at its next open. A knock is a GET with `mode: 'no-cors'`, no credentials and no referrer, and is never read; the injected fetch wrapper sends the device token to this origin only (`sameOrigin`), which `phoneWake.test.ts` pins for the knock. An open page asks the PC (`wakeAnswers`: `up`, `awake` for any answer that is not 200, `asleep` for none) before it trusts a socket that is not open or has carried nothing for 45 s (`wakeNeedsAsk`), and knocks only for `asleep`. Asked from a close, an awake PC keeps the socket's backoff, so a refused socket cannot storm; a socket that came back or carried a frame during the ask is kept; a wake that gives up (`gaveUp`) starts no other from a close, only from Send or the page coming into view, so a PC that cannot be woken is not knocked on for ever. A held message is sent only as typed and only into the chat it was typed in (`wakeSameChat`; the reconnect may unbind the pane), and the wait for the binding asks `wakeBindingSettled`, never `projectChatUnsettled`, which writes a line each time. On a remote https page with no wake address, `registerWakeWorker` removes the worker and its stored page, so unsetting the variable takes it off the phone at the next open; the page also drops `?direct=1` from the address.
- `tailscale serve` proxies to `127.0.0.1` only. Its target is the proxy listener; on the desk's listener a forwarded request is a loopback peer and would be served the shared token. `/pair` answers 200 on the proxy listener and 404 on a desk listener from this machine, which is how `scripts/phone-https.ps1` tells them apart before it sets anything.
- `DashboardServer.phoneOrigin` (the wait push's link) reads the device records (`TokenSet.lastDeviceOrigin`), not a field of its own: revoking a device removes its address too.
- `governance.recommendation` is drawn and never acted on (owner's decision of 2026-11-17, row 21): `recommendationEntry` in the page turns the frame into one Governance-tab row that ends "not applied", and into a chat line when the action is a revert. The case makes no request and starts no timer; the frame's `autoApplyAfterMs` is read by nothing. Pinned by `dashboard/recommendation.test.ts`.
- **A silent model is said in the chat** (work order D4f, 2026-11-17). `/api/session` carries `modelSilence` when the engine wires `getModelSilence` (the stall clock's reading, `engine/providers/CLAUDE.md`): the request in flight, how long its server has sent nothing, and the limit. While a turn is open the page asks every five seconds (`pollModelWait`) and writes one line under the chat (`modelWaitLine`: nothing under fifteen seconds, then "Waiting for the model's first token: 1m 20s so far. The engine ends the request after 20m of silence."); a `stream.token` or `stream.thinking` frame takes it down at once. The timer in `fetchSessionState` names `pollModelWait` inside a closure on purpose: several tests lift `fetchSessionState` into their own scope, and an identifier evaluated when the timer is started would have to be stubbed in each. Pinned by `dashboard/modelWait.test.ts` and `sessionRoute.test.ts`.
- **The outcome ledger on the phone** (work order D4g, 2026-11-17). The Missions-history panel (`#panelMissionHistory`, `GET /api/mission-history`) lives on the Governance tab, which the phone layout does not show. `applyRemoteLayout` moves that one node under the Away tab (`moveMissionHistoryForRemote`; moved, not copied, because its controls are found by id and its poll already runs on every page) and renames it, since the phone's Missions tab is the schedules. A mission's campaign link, which on the desk opens the Campaign panel, narrows the list to that campaign on the phone.
- A new frame type the page handles (`case '…'` in `handleEvent`) must be put on `REPLAYED_TYPES` or `NOT_REPLAYED_TYPES` in `replay.ts`, or `replay.test.ts` fails. Replay a type only if handling it twice in a row is impossible by construction (the cursor guarantees once) and handling it late is still right; a request for a decision is neither.
- The replay buffer is per engine process and per conversation: a restart, a dispatch swap or a `project.opened` empties it, and a returning page then loads as a fresh one. It is memory only (4,000 entries or 8,000,000 characters).
- No empty `catch` blocks (`engine/__tests__/guards/emptyCatch.test.ts` ratchet): `missionsApi.ts` returns a value or logs.
- The ledger is about 170 MB of full trajectories. `MissionHistory` parses each shard once and re-reads one only when its size or mtime moves (once per mission, for the active shard); the first `/api/mission-history` after an engine start parses them all (about 0.4 s under Bun on this PC, yielding between shards, F225). A shard caught mid-append keeps the rows read before and is named in `errors`.
- A dashboard server started by hand from the owner's shell (a scratch look at the page) picks up the permanent `LOCALCODE_DASHBOARD_HOST` and `LOCALCODE_DASHBOARD_PROXY_PORT`: it binds a phone listener on the tailnet address and retries the HTTPS proxy port every 15 s, competing with the live engine for it. Unset both for anything that is not the phone engine (seen 2026-11-13).
