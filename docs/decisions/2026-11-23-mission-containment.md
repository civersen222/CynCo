## What was there

A mission ran with approve-all, a shell holding the owner's environment and token, file tools that wrote wherever a path pointed, one deletion pattern in a text check that calls itself "NOT a sandbox", and its only record of tool input inside the home folder. On 2026-11-22 one Bash call deleted the 25 dot-folders of the home folder, about 285 GB, and the record of the command with them, then walked `AppData\Local` in alphabetical order and deleted what was not held open, until it stopped at `pip` at 00:16:45: about twenty top-level application folders gone, `Packages` down from 110 folders to 14. The mission then ran 108 more turns, about 2 hours 10 minutes, and nothing noticed. ## What the owner can do afterwards

Leave a campaign or a daemon mission running unattended and know that (a) a command aimed at the home folder is refused before it runs and, if the refusal misses it, is denied by Windows on NTFS or lands in a throwaway folder; (b) if a protected folder changes anyway, the run stops within about a minute (a lost folder) or the latch is written at its end (any change), and nothing more unattended starts; the latch pages the owner when the process that writes it holds `CYNCO_NTFY_URL`, and otherwise the page waits in the guard folder until the daemon sends it, which the services script does not start under a latch (decision sheet items 22 and 26); (c) what every tool call was asked to run can be read afterwards from a log outside the home folder, written before the call ran. ## Scope

Unattended runs only: a dispatched mission, a daemon one-shot (`--run-task`), the daemon's precheck, the campaign runner's ideation one-shot and its graders, calibration and the authoring runner's gate runs. One predicate says whether a process must become a contained run (`isContainedRun`, `engine/missionEnv.ts`); whether it is one is the run context (`runContainment()`, `engine/containment.ts`), which is the only thing any layer consults, so a message typed into a mission engine's chat box without the `unattended` flag runs contained too. Interactive sessions, the phone engine and project chats are not contained, by design; three things reach them anyway (decision sheet item 15): the sealed, immutable and secret checks now read nested path keys, patch headers, decoded payloads and real paths in every mode (a commit message that spells a sealed gate's file name is refused; a secret refusal now wins over an approval); a profile save is refused while an unattended run is open; and `scripts\cynco-services.ps1 start daemon` is refused under the integrity latch. An unattended run that cannot be given every layer is refused with a named reason before any model call (the F140 shape). There is one switch, `LOCALCODE_CONTAINMENT_OFF`, with the words `lowil` and `paths`; it is honoured only for a context a test built, and a real run in which it is set at all is refused. One variable widens what a run may write: `CYNCO_MISSION_ALSO_LABEL`, a `;` list `scripts/dispatch-mission.sh` hands to `cynco-sandbox.mjs create` as `--also` (extra roots labelled low for the run). Only `scripts/cynco-gate-author.mjs` sets it (the BASE archive of an authoring mission), but any shell that runs the dispatch script can; every folder it names passes the same refusals of `establishContainment` as a mission folder (below), and no tool child ever holds it (`toolEnv` drops it in every mode). The audit and the integrity layer cannot be switched off. Since wave 19 (2026-11-25) one more variable turns a capability back on, never a layer off: `LOCALCODE_CONTAINMENT_MSYS`, the Git-tools switch, read by the starter in `establishContainment` only and carried in the run's record; and the authoring dispatch carries one mark, `LOCALCODE_MISSION_AUTHOR_CHECK`, which the dispatch reads, refuses unless it is `1` and hands to the driver alone, and on which only the driver runs anything (both under "Added in waves 19 to 19c" below).

## What it adds, and the six questions

**The run context, the per-run sandbox and the low-integrity launcher** (`engine/containment.ts`, `engine/lowIntegrityLauncher.ts` with its own `engine/lowIntegrityLauncher.bunfig.toml`, `scripts/cynco-sandbox.mjs`; `<LOCALCODE_SANDBOX_ROOT, default C:/cynco-sandbox>/<run id>/{home,tmp,scratch}` and a `containment.json` record per run).
- *Problem*: a tool process needed somewhere to write that is not the owner's home and a token that cannot write the owner's files; every layer needs one answer to "is this a contained run".
- *Why the existing thing is insufficient*: `CYNCO_HOME` moves the engine's state, not a tool's `~` (and redirecting `HOME` for the engine itself moves its tokens, profiles and binary: F161, F241); `C:\tmp` is shared by every mission and by the owner; the per-message `unattended` flag is absent on a message typed into a mission engine's chat box; the engine's Job Object ends processes, it does not limit what they write.
- *State, dependencies, failure modes*: one folder and one record per run, written by the starter at the engine's integrity; `icacls` and `bun:ffi` on Windows (part of Bun, no new package). `toolEnv` sets `HOME`, `USERPROFILE`, `HOMEDRIVE`, `HOMEPATH`, `APPDATA`, `LOCALAPPDATA`, `TEMP`, `TMP`, `TMPDIR` and `CYNCO_SCRATCH` into the sandbox and never deletes them (with the keys absent node's `os.homedir()` answers the real home, measured); `GIT_CONFIG_GLOBAL` is a file in the sandbox that includes the owner's, so commits keep an identity and `git config --global` cannot touch the owner's file. The launcher lowers its own token, reads the level back, makes every inherited handle but its three standard ones non-inheritable (a child could read a medium Git Bash's environment through one, measured), then starts the child; it is started from the checkout with `--no-env-file` and its own config, so a `bunfig.toml` or `.env` planted in a mission folder runs nothing at the engine's integrity. A launcher that cannot run exits 197 and a vanished child 198, each followed by a per-spawn seal line only the launcher holds (`CYNCO_LAUNCHER_SEAL`, an environment key that is not a switch); a launcher that could not run reads as "did not run", never as a failed check (F35). That a low child cannot read the seal from the launcher's memory was measured (it cannot open the launcher or its starter with any right that reads memory). Each contained command costs the launcher's start, measured at about 30 ms on top of a PowerShell start. A label is set on a folder root with inheritance and never with `/T` (measured: `icacls /T` carried the Low label through a junction into a folder outside). Release relabels the root and walks the folder, never entering a link, resetting every label the run set itself (measured at about 32 ms per non-empty folder, so a repository of a few hundred folders adds seconds to each release; measured again on 2026-11-24 on large folders, the walk of a mission folder has no budget and takes minutes on the CynCo checkout: "Measurements for the owner" below); a folder still reading low with no live run holding it, and a folder holding a file with more than one name (a hard link carries the label to every name), are refused. Since wave 15 (2026-11-24) the release also sets the sandbox's own `home`, `tmp` and `scratch` back to medium within a budget (`SANDBOX_SET_BACK_BUDGET`, `engine/containment.ts`: 200 folders, 2,000 label calls or 5 s, whichever comes first; the call limit since wave 19), puts back an access list the establish had to widen, and keeps in the record what it could not undo. What each step does, what the sweep then does with such a sandbox and the commands that put it right are in the package document of `engine/tools` ("Containment of unattended runs"); what they cost is under "Measurements for the owner" below. A run that dies keeps its label until the next dispatch or daemon start releases it. The sweep is the one recursive delete this change adds to the engine: sandboxes older than seven days, direct children of the sandbox root that carry their own record only, a link removed without being entered.

**The integrity manifest, the latch, the guard folder and the in-run tripwire** (`engine/integrity.ts`, `scripts/cynco-guard.mjs`; `<LOCALCODE_GUARD_DIR, default C:/cynco-guard>`).
- *Problem*: a wave that destroyed the home folder would have been followed by the next wave, and the mission itself ran on for two hours.
- *Why insufficient*: a fault spends one wave; the daemon's pause file is cleared by one tap and lived in the folder the incident deleted.
- *State, failure modes*: a persistent store outside the home folder: the latch `HALT.json`, one baseline per run, the models hash record, unsent pages, the latch log. FROZEN folders must not change at all during a run: the models folder, `profiles` and `heldout` of the state folder (the default and a redirected one), and `~/.ssh` except `known_hosts` and `known_hosts.old`; any change there, by anyone, latches (so no profile edit and no new model file while a run is open; CynCo's own writers into them refuse instead). PRESENCE folders must not lose anything: the home's top level (every folder by name and child count, dot or not, and the dot-files; until 2026-11-24 the dot-entries alone, which is why the walk through `AppData\Local` would have gone unseen), the top-level folders of `AppData\Local`, `AppData\Roaming` and `AppData\LocalLow` (counted, but `Temp` and `D3DSCache` by name only, which Windows' own cleanup empties) and the folders of `AppData\Local\Packages` (by name), the folders of `OneDrive` (counted; this PC's Desktop, Documents and Pictures are there), the desk tools' folder, `~/.ollama/models` (counted; it was FROZEN until the fifth review, when a model pull by another process latched), the state folder and its authoring and campaign folders, and the top of every volume Windows cannot protect. In the four application roots one or two entries gone or emptied in a run are a note and three are a loss (`APPDATA_LOSS_AT`): applications drop a folder of their own now and then, and the price is that a deletion of one or two application folders per root latches nothing. A contained engine re-lists its PRESENCE folders every 60 s and, at most once a second, before a tool call, the application roots by name only (a look costs about 48 ms on this PC; the measured figures are in the integrity paragraph of the package document of `engine/tools`), so an application folder emptied in place is seen at the run's end; during one long call the only look is the 60 s timer, so a call that deletes runs on for up to a minute after its first loss; volume roots only at the baseline and the settling compare. Since wave 15 (2026-11-24) the timer looks every 10 s, a change counts only when a second look 1 s later sees it too (`presenceTripwireConfirmed`, which the executor awaits before every tool call), the application roots are counted in every look with the same allowance, the settle walks until two walks in a row agree (at most five), and the known folders are read where Windows says they are; how each works is the integrity paragraph of the package document of `engine/tools`. What it costs and leaves: a look lists what the baseline lists, about 61 ms on this PC (by the medians of 2026-11-24, not measured again), an application folder emptied in place now counts toward the allowance during the run, a call that deletes runs on for up to about eleven seconds after its first loss, and a known folder outside the home or on another drive is a note in the baseline and is not watched ("What it does not cover" 9). A baseline taken before 2026-11-24 settles against the roots it recorded. The owner's own rename, deletion or emptying of a top-level folder of the home or a folder of `OneDrive` while a run is open ends the run and latches; a program's uninstall that takes three folders of one application root latches, and so can a disk cleanup together with one or two updaters (`docs/containment-setup.md`, section 13). Two rarer costs: a run open across a restart (a Windows Update reboot) is settled as an orphan after it, over a window of any length, with the same allowance, so a feature update that removes three inbox applications' package folders latches there; and an engine older than this change, reading a baseline written by it, ignores the by-name-only and allowance fields, counts every folder of `AppData\Local` (`Temp` included, about 0.6 s a look on its event loop) and reads one application folder gone as a loss, so after a rollback settle or clear the open baselines before starting an engine. The daemon loads `engine/integrity.ts` once at its start: restart it with the engine after this change is merged, or it settles the new baselines with the old rules. A baseline whose starter died before its compare is an orphan: nothing new starts until it is compared, and the daemon compares it on its next tick. A false trip stops every campaign and daemon mission until the owner clears it; the tripped wave keeps its ledger row. A page that cannot be sent is kept and the latch does not depend on it. A guard folder that is missing or unreadable refuses like a latch. The owner sees: `the integrity latch is present at <guard>/HALT.json (<summary>, set <at> by <by>); only the owner clears it, at a terminal, with: bun scripts/cynco-guard.mjs clear`.

## A mission folder that is refused

`establishContainment` refuses, each with a named reason, a mission folder (or a folder handed in with it) that does not exist; is, contains or is inside the checkout the engine runs from; is the home folder or contains it; is a volume root, on a network share, or on a volume integrity labels cannot protect; is, contains or is inside the guard, audit, models or sandbox-root folder or CynCo's state folder (except below `<state>/authoring`, the authoring mission's staging folder); is inside a dot-folder of the home folder (same exception); holds, anywhere in its tree, a link to a place outside itself or a link whose target cannot be resolved, a folder that cannot be listed, or more than 200,000 entries (`linkLeadingOut`, `RULE_M_MAX_ENTRIES`; since wave 15, 2026-11-24: until then only a link that leads outside, in the top two levels, was refused, and a folder that could not be listed was passed); holds a file with more than one name; still reads low with no live run holding it; or, for a mission, is not the top of its own git repository. A sandbox is refused while a volume without integrity labels is attached and not named in `LOCALCODE_UNPROTECTED_VOLUMES_OK`. A daemon task that names no `cwd` is refused. The daemon's two-hourly precheck never labels the mission folder. `establishContainment` does not ask Task Scheduler what runs from a folder: the setup script does, once, and prints STOP for every scheduled action inside a daemon mission's folder (decision sheet item 5).

## New authority

CynCo stops its own campaigns, dispatches and daemon missions by itself, kills a running one-shot, ends a mission's turn, and pages the owner, when a protected folder changes. It sets and removes an integrity label on a mission's repository. It refuses a model's tool call on its own judgement of a path. It deletes sandboxes older than seven days, mission logs older than 90 days in `C:/tmp`, and the previous `.1` of a service log at rotation. Since wave 19 (2026-11-25) the mission driver also runs CynCo's own gate-authoring check at normal privilege for an authoring dispatch that carries the mark (decision sheet item 25), and its teardown ends only the confirmed mission engine's tree (the pid and creation time the dispatch hands it), never every engine or model server on the box.

## Where the requirements were narrowed, and why

- "Executions must land inside the roots" became: a script or program operand outside the roots is refused only when it lies in the always-denied set. A script outside the roots is one the run could not have written, and the authoring check is such a script. The stricter rule (an unclassified operand outside the roots, T6a and T6aExec) was measured by the reviewer at 9 and 3 of the owner's 3,342 past commands and would refuse two must-pass rows of the specification (scan.py over site-packages, the authoring check); it was not adopted. A lexical net over inline calls that look like mutations was measured at 111 refusals and not adopted.
- `GIT_CONFIG_GLOBAL` is an include file in the sandbox, not the owner's file (decided for the owner, item 4).
- Under the latch only the daemon is refused a start by the services script; the phone engine and the dashboard keep working, because the owner needs them then (decided for the owner, item 10). Whether the daemon, the one process here that holds the doorman's page address, may start under a latch is the owner's (decision sheet item 26, review finding 4.M1; as built, it may not).
- `~/.ollama/models` is watched for loss only, not frozen: processes outside any run add to it.
- The copy of the audit log on the NAS is cut from this change.
- The `env` rule of `bashSafety.ts` is left exactly as it is.
- The stream debug log stays in the run's working folder, capped and refusing links; a review recommended moving it out, and that is open.
- The OneDrive spellings (`$env:OneDrive`, `OneDriveConsumer`, `OneDriveCommercial`, `%OneDrive%`) name the real profile's `OneDrive` to the path check (`ANCHOR_NAMES`, `engine/tools/shellPaths.ts`), although `toolEnv` points them at `<sandbox home>\OneDrive`, as the home spellings name the real home (wave 19, 2026-11-25, against that wave's brief, which asked for the sandbox's: the check does not stand down on another layer's word, and this is the form that refuses more). ## Rejected alternatives

- **More patterns in `bashSafety.ts`.** The failure mode the 2026-11-06 record already names: it judges spelling.
- **A separate Windows user for missions.** A stronger boundary than a label, and exFAT would still be open to it; it needs a second profile, credentials and a logon for every tool call. Kept as the next step if low integrity proves too weak.

## What the first live-fire run found (2026-11-24)

The acceptance was run by hand with live fire for the first time (`--stage fake`, test root `C:\cynco-recovery-2026-11-22\acceptance\live-1`). Reading what the run left behind found that one of its attacks had made a junction from a run's scratch folder to that run's home, and that the code meant to clean such things up could not see it. Measured afterwards on this PC (Windows 11 26200, Bun 1.3.13, Node 24.14.1, git 2.53.0.windows.2), with a copy of `cmd.exe` labelled low:

- F1. A junction made by a low-integrity process is stored in another form than the same junction made at medium: its target is written `\??\Global\C:\...` instead of `\??\C:\...`. Windows does this, not the tool.
- F2. A low process can make a junction only to a folder it could write at that moment: one to a medium folder, a directory symbolic link and a hard link to a medium file were all refused.
- F3. That moment passes. A mission folder is labelled low during the run and set back to medium at release, so a junction made during the run from the sandbox to the mission folder then points at a medium folder, the owner's repository, and stays in the sandbox until the seven-day sweep. A low process can also write another live run's folders and, in the real home, `AppData\LocalLow`, `AppData\Local\Temp\Low` and some `AppData\Local\Packages\*\AC` folders.
- F4. For the low form, Bun and Node alike: `lstat` says it is a folder, not a link, and answers with the target's identity (dev and ino), because it follows it; `readlink` throws; the JavaScript `realpath` returns the junction's own path. The folder's own listing (`readdirSync(parent, { withFileTypes: true })`) calls it a link, and `realpathSync.native` resolves it to its target. Removing it with `rmdirSync` removes the junction alone.
- F5. Deleting a folder that holds such a junction: Bun's and Node's `rmSync(recursive)`, `rd /s /q` and PowerShell 5.1's `Remove-Item -Recurse -Force` removed the junction and left the target alone; Git Bash `rm -rf` deleted the file behind it.
- F6. git treats every junction, of either form, as a folder: `status` and `add -A` list and stage the files behind it, and `clean -fdx` deleted an untracked file behind one.

What that meant for this change: every walk in `engine/containment.ts` asked `lstat` whether an entry was a link. The seven-day sweep, which deletes at medium integrity, would have entered a low-made junction and deleted the contents of whatever it pointed at, the owner's repository included, and its swap guard was blind to it (both of its `lstat` reads return the target's identity); a run folder whose junction pointed at its own home was never swept at all. The release's label walk would have walked the target, set back low labels that belong to other folders, and never ended on a junction that loops back. The hard-link walk at create would have descended through one and hung or refused for a file that is not in the folder. Rule M did not report one that leads out.

What this change fixes (the engine part, `engine/containment.ts` with the shared helpers in `engine/realPath.ts`): each of these walks now takes an entry's kind from the folder's listing, never from `lstat` (E1 the sweep, E2 the release walk, E3 the hard-link walk, E4 rule M; also the sweep's own check of a run folder and the root listing of `containmentRecords`), and enters a folder only where its native real path is its parent's joined with its name. A link is removed as an entry by the sweep, has only its own label set back by the release, is not entered or counted by the hard-link walk, and is judged by rule M where it really lands. The package document of `engine/tools` (section "Containment of unattended runs") says what each walk does at a link. Each is pinned in `engine/__tests__/containment.test.ts` by a case with a junction a low-integrity `cmd` made in the test's own temp folder (checked with `fsutil` to be stored in the low form), and by a case with a listing that disagrees with `lstat`, which runs on every system. The acceptance runner's own blind spots (fifteen items, R1 to R15, among them its link checks, outcomes printed without the thing having happened, and new live-fire proofs of the four fixes above) are fixed in the same wave by a separate change to `scripts/cynco-containment-acceptance.mjs` and `scripts/cynco-containment-attacks.mjs`.

Five reviewers then read the change, and the engine part was corrected before it was committed (each with a case that failed first): a link `rmdirSync` cannot remove is now unlinked whatever `rmdirSync` answered (on Windows it answers ENOENT, not ENOTDIR, for an entry that is not a folder, so a file carrying a reparse tag, which any process may set on a file it can write, stopped the sweep for good); the run's record is removed last, so a run folder whose sweep stopped is visited and logged again on every later pass instead of being forgotten with its Low label; the sweep checks a folder's real path again before each delete in it, and the release again when it takes a folder from its queue; the hard-link walk asks a link with `lstat` (which enters nothing), so a file with a second name that also carries a reparse tag is refused again, as before the change; a link that resolves to its own path and is a folder is walked by the release, the hard-link walk and rule M as the folder it is (none is known on this PC); and a folder that is not where its path says is refused at create for that, without the advice about clones. ## What it does not cover

1. Reading is not restricted, and the network is open. A contained run can read `~/.ssh`, `.env` files, every log and `~/.cynco/tokens.json`, and can send them anywhere; with the token file it can ask the engine's own loopback API, a process at the engine's integrity, to act for it. A contained child's environment also keeps the owner's other `LOCALCODE_*` variables, the addresses of local services among them: `toolEnv` drops only the harness's own keys (`ALWAYS_STRIP`: `LOCALCODE_MISSION_*` and the marker, label and seal keys), the containment's own keys (`CONTEXT_STRIP`) and the secrets (`SECRET_ENV`, `engine/containment.ts`; since wave 19 a rule over names, and since wave 19b an address passes by decision: "Added in waves 19 to 19c"; a contained gate printed eight such keys on 2026-11-24). A contained child's own Bun does not fetch a missing package by itself since wave 19b (`BUN_OPTIONS=--no-install`), but an explicit `bun install` or `bun add`, `npm`, `pip` or any other package manager the run calls still reaches the network. This change protects against destruction, not against disclosure.
2. The file tools have one layer. Write, Edit, MultiEdit, NotebookEdit, ReplaceFunction and ApplyPatch's own writes run inside the engine with its token and the real home. Only the path check stands in front of them; it is exact for them, but a bug in it is a direct write anywhere.
3. Drive `D:` and the NAS are not protected by Windows. Integrity labels exist on NTFS only. What stands in front of them: the path check (it reads text), the manifest of their top level (detection afterwards, at the end of the run), and the refusal to dispatch while such a volume is attached and not acknowledged by name. Acknowledging it does not protect it: in a run with such a volume acknowledged, an inline program's write through a path it computes (`open(chr(68) + ':/DCIM/a.jpg', 'w')`) is only escalated, run and logged, because the drive is not in its text. A real block is the owner's to choose: a second copy of the videos, the volume read-only or detached while unattended runs are enabled, or NTFS (decision sheet item 1).
4. The shell half of the path check reads text and can be walked around by anything that does not spell its target: a script written and then run, a module run with `-m`, a path a program computes, a name set in one call and used in the next.
