## What was there

A mission ran with approve-all, a shell holding the owner's environment and token, file tools that wrote wherever a path pointed, one deletion pattern in a text check that calls itself "NOT a sandbox", and its only record of tool input inside the home folder. On 2026-11-22 one Bash call deleted the 25 dot-folders of the home folder, about 285 GB, and the record of the command with them, then walked `AppData\Local` in alphabetical order and deleted what was not held open, until it stopped at `pip` at 00:16:45: about twenty top-level application folders gone, `Packages` down from 110 folders to 14. Measured against the snapshot two days later, about 34 GB under `AppData` was not on disk (ordinary turnover since the snapshot included: `Temp`, 5.3 GB of it, was not reached by the call), about 2 GB of it application state. The mission then ran 108 more turns, about 2 hours 10 minutes, and nothing noticed. ## What the owner can do afterwards

Leave a campaign or a daemon mission running unattended and know that (a) a command aimed at the home folder is refused before it runs and, if the refusal misses it, is denied by Windows on NTFS or lands in a throwaway folder; (b) if a protected folder changes anyway, the run stops within about a minute (a lost folder) or the latch is written at its end (any change), and nothing more unattended starts; the latch pages the owner when the process that writes it holds `CYNCO_NTFY_URL`, and otherwise the page waits in the guard folder until the daemon sends it, which the services script does not start under a latch (decision sheet items 22 and 26); (c) what every tool call was asked to run can be read afterwards from a log outside the home folder, written before the call ran. To be shown on this PC by `bun scripts/cynco-containment-acceptance.mjs --stage fake` and its real-profile stage, with their printed evidence. **None of this has been shown on this PC yet** (see Verification).

## Scope

Unattended runs only: a dispatched mission, a daemon one-shot (`--run-task`), the daemon's precheck, the campaign runner's ideation one-shot and its graders, calibration and the authoring runner's gate runs. One predicate says whether a process must become a contained run (`isContainedRun`, `engine/missionEnv.ts`); whether it is one is the run context (`runContainment()`, `engine/containment.ts`), which is the only thing any layer consults, so a message typed into a mission engine's chat box without the `unattended` flag runs contained too. Interactive sessions, the phone engine and project chats are not contained, by design; three things reach them anyway (decision sheet item 15): the sealed, immutable and secret checks now read nested path keys, patch headers, decoded payloads and real paths in every mode (a commit message that spells a sealed gate's file name is refused; a secret refusal now wins over an approval); a profile save is refused while an unattended run is open; and `scripts\cynco-services.ps1 start daemon` is refused under the integrity latch. An unattended run that cannot be given every layer is refused with a named reason before any model call (the F140 shape). There is one switch, `LOCALCODE_CONTAINMENT_OFF`, with the words `lowil` and `paths`; it is honoured only for a context a test built, and a real run in which it is set at all is refused. One variable widens what a run may write: `CYNCO_MISSION_ALSO_LABEL`, a `;` list `scripts/dispatch-mission.sh` hands to `cynco-sandbox.mjs create` as `--also` (extra roots labelled low for the run). Only `scripts/cynco-gate-author.mjs` sets it (the BASE archive of an authoring mission), but any shell that runs the dispatch script can; every folder it names passes the same refusals of `establishContainment` as a mission folder (below), and no tool child ever holds it (`toolEnv` drops it in every mode). The audit and the integrity layer cannot be switched off.

## What it adds, and the six questions

**The run context, the per-run sandbox and the low-integrity launcher** (`engine/containment.ts`, `engine/lowIntegrityLauncher.ts` with its own `engine/lowIntegrityLauncher.bunfig.toml`, `scripts/cynco-sandbox.mjs`; `<LOCALCODE_SANDBOX_ROOT, default C:/cynco-sandbox>/<run id>/{home,tmp,scratch}` and a `containment.json` record per run).
- *Problem*: a tool process needed somewhere to write that is not the owner's home and a token that cannot write the owner's files; every layer needs one answer to "is this a contained run".
- *Why the existing thing is insufficient*: `CYNCO_HOME` moves the engine's state, not a tool's `~` (and redirecting `HOME` for the engine itself moves its tokens, profiles and binary: F161, F241); `C:\tmp` is shared by every mission and by the owner; the per-message `unattended` flag is absent on a message typed into a mission engine's chat box; the engine's Job Object ends processes, it does not limit what they write.
- *State, dependencies, failure modes*: one folder and one record per run, written by the starter at the engine's integrity; `icacls` and `bun:ffi` on Windows (part of Bun, no new package). `toolEnv` sets `HOME`, `USERPROFILE`, `HOMEDRIVE`, `HOMEPATH`, `APPDATA`, `LOCALAPPDATA`, `TEMP`, `TMP`, `TMPDIR` and `CYNCO_SCRATCH` into the sandbox and never deletes them (with the keys absent node's `os.homedir()` answers the real home, measured); `GIT_CONFIG_GLOBAL` is a file in the sandbox that includes the owner's, so commits keep an identity and `git config --global` cannot touch the owner's file. The launcher lowers its own token, reads the level back, makes every inherited handle but its three standard ones non-inheritable (a child could read a medium Git Bash's environment through one, measured), then starts the child; it is started from the checkout with `--no-env-file` and its own config, so a `bunfig.toml` or `.env` planted in a mission folder runs nothing at the engine's integrity. A launcher that cannot run exits 197 and a vanished child 198, each followed by a per-spawn seal line only the launcher holds (`CYNCO_LAUNCHER_SEAL`, an environment key that is not a switch); a launcher that could not run reads as "did not run", never as a failed check (F35). That a low child cannot read the seal from the launcher's memory was measured (it cannot open the launcher or its starter with any right that reads memory). Each contained command costs the launcher's start, measured at about 30 ms on top of a PowerShell start. A label is set on a folder root with inheritance and never with `/T` (measured: `icacls /T` carried the Low label through a junction into a folder outside). Release relabels the root and walks the folder, never entering a link, resetting every label the run set itself (measured at about 32 ms per non-empty folder, so a repository of a few hundred folders adds seconds to each release); a folder still reading low with no live run holding it, and a folder holding a file with more than one name (a hard link carries the label to every name), are refused. A run that dies keeps its label until the next dispatch or daemon start releases it. The sweep is the one recursive delete this change adds to the engine: sandboxes older than seven days, direct children of the sandbox root that carry their own record only, a link removed without being entered.

**The integrity manifest, the latch, the guard folder and the in-run tripwire** (`engine/integrity.ts`, `scripts/cynco-guard.mjs`; `<LOCALCODE_GUARD_DIR, default C:/cynco-guard>`).
- *Problem*: a wave that destroyed the home folder would have been followed by the next wave, and the mission itself ran on for two hours.
- *Why insufficient*: a fault spends one wave; the daemon's pause file is cleared by one tap and lived in the folder the incident deleted.
- *State, failure modes*: a persistent store outside the home folder: the latch `HALT.json`, one baseline per run, the models hash record, unsent pages, the latch log. FROZEN folders must not change at all during a run: the models folder, `profiles` and `heldout` of the state folder (the default and a redirected one), and `~/.ssh` except `known_hosts` and `known_hosts.old`; any change there, by anyone, latches (so no profile edit and no new model file while a run is open; CynCo's own writers into them refuse instead). PRESENCE folders must not lose anything: the home's top level (every folder by name and child count, dot or not, and the dot-files; until 2026-11-24 the dot-entries alone, which is why the walk through `AppData\Local` would have gone unseen), the top-level folders of `AppData\Local`, `AppData\Roaming` and `AppData\LocalLow` (counted, but `Temp` and `D3DSCache` by name only, which Windows' own cleanup empties) and the folders of `AppData\Local\Packages` (by name), the folders of `OneDrive` (counted; this PC's Desktop, Documents and Pictures are there), the desk tools' folder, `~/.ollama/models` (counted; it was FROZEN until the fifth review, when a model pull by another process latched), the state folder and its authoring and campaign folders, and the top of every volume Windows cannot protect. In the four application roots one or two entries gone or emptied in a run are a note and three are a loss (`APPDATA_LOSS_AT`): applications drop a folder of their own now and then, and the price is that a deletion of one or two application folders per root latches nothing. A contained engine re-lists its PRESENCE folders every 60 s and, at most once a second, before a tool call, the application roots by name only (a look costs about 48 ms on this PC; the measured figures are in the integrity paragraph of the package document of `engine/tools`), so an application folder emptied in place is seen at the run's end; during one long call the only look is the 60 s timer, so a call that deletes runs on for up to a minute after its first loss; volume roots only at the baseline and the settling compare. A baseline taken before 2026-11-24 settles against the roots it recorded. The owner's own rename, deletion or emptying of a top-level folder of the home or a folder of `OneDrive` while a run is open ends the run and latches; a program's uninstall that takes three folders of one application root latches, and so can a disk cleanup together with one or two updaters (`docs/containment-setup.md`, section 13). Two rarer costs: a run open across a restart (a Windows Update reboot) is settled as an orphan after it, over a window of any length, with the same allowance, so a feature update that removes three inbox applications' package folders latches there; and an engine older than this change, reading a baseline written by it, ignores the by-name-only and allowance fields, counts every folder of `AppData\Local` (`Temp` included, about 0.6 s a look on its event loop) and reads one application folder gone as a loss, so after a rollback settle or clear the open baselines before starting an engine. The daemon loads `engine/integrity.ts` once at its start: restart it with the engine after this change is merged, or it settles the new baselines with the old rules. A baseline whose starter died before its compare is an orphan: nothing new starts until it is compared, and the daemon compares it on its next tick. A false trip stops every campaign and daemon mission until the owner clears it; the tripped wave keeps its ledger row. A page that cannot be sent is kept and the latch does not depend on it. A guard folder that is missing or unreadable refuses like a latch. The owner sees: `the integrity latch is present at <guard>/HALT.json (<summary>, set <at> by <by>); only the owner clears it, at a terminal, with: bun scripts/cynco-guard.mjs clear`.

Measured afterwards on this PC (Windows 11 26200, Bun 1.3.13, Node 24.14.1, git 2.53.0.windows.2), with a copy of `cmd.exe` labelled low:

- F1. A junction made by a low-integrity process is stored in another form than the same junction made at medium: its target is written `\??\Global\C:\...` instead of `\??\C:\...`. Windows does this, not the tool.
- F2. A low process can make a junction only to a folder it could write at that moment: one to a medium folder, a directory symbolic link and a hard link to a medium file were all refused.
- F3. That moment passes. A mission folder is labelled low during the run and set back to medium at release, so a junction made during the run from the sandbox to the mission folder then points at a medium folder, the owner's repository, and stays in the sandbox until the seven-day sweep. A low process can also write another live run's folders and, in the real home, `AppData\LocalLow`, `AppData\Local\Temp\Low` and some `AppData\Local\Packages\*\AC` folders.
- F4. For the low form, Bun and Node alike: `lstat` says it is a folder, not a link, and answers with the target's identity (dev and ino), because it follows it; `readlink` throws; the JavaScript `realpath` returns the junction's own path. The folder's own listing (`readdirSync(parent, { withFileTypes: true })`) calls it a link, and `realpathSync.native` resolves it to its target. Removing it with `rmdirSync` removes the junction alone.
- F5. Deleting a folder that holds such a junction: Bun's and Node's `rmSync(recursive)`, `rd /s /q` and PowerShell 5.1's `Remove-Item -Recurse -Force` removed the junction and left the target alone; Git Bash `rm -rf` deleted the file behind it.
- F6. git treats every junction, of either form, as a folder: `status` and `add -A` list and stage the files behind it, and `clean -fdx` deleted an untracked file behind one.

What that meant for this change: every walk in `engine/containment.ts` asked `lstat` whether an entry was a link. The seven-day sweep, which deletes at medium integrity, would have entered a low-made junction and deleted the contents of whatever it pointed at, the owner's repository included, and its swap guard was blind to it (both of its `lstat` reads return the target's identity); a run folder whose junction pointed at its own home was never swept at all. The release's label walk would have walked the target, set back low labels that belong to other folders, and never ended on a junction that loops back. The hard-link walk at create would have descended through one and hung or refused for a file that is not in the folder. Rule M did not report one that leads out.

What this change fixes (the engine part, `engine/containment.ts` with the shared helpers in `engine/realPath.ts`): each of these walks now takes an entry's kind from the folder's listing, never from `lstat` (E1 the sweep, E2 the release walk, E3 the hard-link walk, E4 rule M; also the sweep's own check of a run folder and the root listing of `containmentRecords`), and enters a folder only where its native real path is its parent's joined with its name. A link is removed as an entry by the sweep, has only its own label set back by the release, is not entered or counted by the hard-link walk, and is judged by rule M where it really lands. The package document of `engine/tools` (section "Containment of unattended runs") says what each walk does at a link. Each is pinned in `engine/__tests__/containment.test.ts` by a case with a junction a low-integrity `cmd` made in the test's own temp folder (checked with `fsutil` to be stored in the low form), and by a case with a listing that disagrees with `lstat`, which runs on every system. ## What it does not cover

1. Reading is not restricted, and the network is open. A contained run can read `~/.ssh`, `.env` files, every log and `~/.cynco/tokens.json`, and can send them anywhere; with the token file it can ask the engine's own loopback API, a process at the engine's integrity, to act for it. This change protects against destruction, not against disclosure.
2. The file tools have one layer. Write, Edit, MultiEdit, NotebookEdit, ReplaceFunction and ApplyPatch's own writes run inside the engine with its token and the real home. Only the path check stands in front of them; it is exact for them, but a bug in it is a direct write anywhere.
3. Drive `D:` and the NAS are not protected by Windows. Integrity labels exist on NTFS only. What stands in front of them: the path check (it reads text), the manifest of their top level (detection afterwards, at the end of the run), and the refusal to dispatch while such a volume is attached and not acknowledged by name. Acknowledging it does not protect it: in a run with such a volume acknowledged, an inline program's write through a path it computes (`open(chr(68) + ':/DCIM/a.jpg', 'w')`) is only escalated, run and logged, because the drive is not in its text. A real block is the owner's to choose: a second copy of the videos, the volume read-only or detached while unattended runs are enabled, or NTFS (decision sheet item 1).
4. The shell half of the path check reads text and can be walked around by anything that does not spell its target: a script written and then run, a module run with `-m`, a path a program computes, a name set in one call and used in the next. On NTFS the overlay and the token stand behind it; on `D:` and network shares nothing does. It has been attacked in nine review rounds, each of which found walk-arounds; the rule since the sixth is under "The protected-path check" above.
5. Programs that act for a caller at their own level were not tested: Docker, WSL, Task Scheduler, WMI process creation, out-of-process COM servers (decision sheet item 12).
6. Unattended is narrower than "nobody is watching". Not contained: `bun engine/main.ts --run-ablation`, the benchmark harness loops, and any engine a person starts with `LOCALCODE_APPROVE_ALL=true` (decision sheet item 10).
7. Code a run leaves behind is run later by others. Tests, scripts and launchers the run wrote are executed afterwards by the owner with the real home, and the fantasyman launchers by Task Scheduler at logon (decision sheet item 5). The harness's own git is neutralised by a list, which is a list.
8. One contained run can write another run's sandbox, and any folder labelled low at that moment; only the path check stands in front of that. Inside the real profile three places are labelled Low by Windows itself, so a contained process can write and delete in them: `AppData\LocalLow`, `AppData\Local\Temp\Low`, and the `AC` folder of some packages under `AppData\Local\Packages`. The integrity check sees a loss there only as far as its roots reach: the top-level folders of `LocalLow` (with the allowance of two), and a package folder gone by name; not `Temp\Low`, and not what is inside an `AC` folder.
9. The integrity check detects, after the fact, and coarsely. Not seen: a file lost or altered outside the FROZEN folders, the owner's loose files at the home's top level, a folder emptied below its first level (the known folders `OneDrive` holds on this PC, Desktop, Documents and Pictures, are one level below the home's top level and are counted as folders of `OneDrive`, nothing below that; a `OneDrive` folder of another name is not watched), a folder that loses one of two entries or keeps half of them, one or two application folders per application root in a run (a note, not a loss: an application's whole state is one entry, the browser profile under `Roaming` included, and `LocalLow`, where a contained process can write, has the same allowance of two), an application folder emptied in place before the settle (the tripwire looks at the application roots by name only), the rest of `AppData` below the four roots' first level (Windows' saved-credential stores `Local\Microsoft\Credentials` and `Vault`, the office suite's `Local\Microsoft\Office` and the data-protection master keys `Roaming\Microsoft\Protect` going leave `Microsoft` with most of its entries; a package's `LocalState`, `Settings`, `AC` and `LocalCache` emptied with its folder kept; `Temp` and `D3DSCache` emptied), a FROZEN file rewritten with its size and time restored (`verify --deep` sees that for the models only), anything in a `.git` or `__pycache__` folder inside a FROZEN root, anything that happens while no run is open, who did it, and up to a minute (or one second of tool calls) between two looks of the tripwire. Volume roots are keyed by drive letter, so another volume at `D:` reads as the camera drive's entries gone.
10. Evidence can still be destroyed by an uncontained process: `C:\cynco-audit` and `C:\cynco-guard` are ordinary folders, and the audit has no copy off this machine.
11. A low child holds terminate rights on its launcher and on the engine (measured): it can kill them. A launcher killed that way leaves no seal line and reads as the command's own status, never as a forged "did not run"; it is a denial of service, not a way out.
12. The Windows layer is proved by hand, not by CI: both stages passed by hand on 2026-11-24, on commit `00a2b0ec`, and a later change to a layer is not covered until they are run again. The real-profile stage proves refusal, not survival: no deletion is ever executed against the real profile.
13. Off Windows there is no kernel layer; the engine says `contained-overlay`.
14. PowerShell 7 is not installed and was not measured. The Bash tool prefers it when present, and it may resolve `~` and `$HOME` without the variables. Run the acceptance again before installing it (decision sheet item 24).
15. What was lost stays lost: the 13.5 hours between the snapshot and the deletion, 12,762 files (about 1 GB) of application state from `AppData\Local` (the owner decided against a raw undelete), and the command text of 2026-11-22.
16. Junctions a run made, outside the walks fixed on 2026-11-24 (facts F1 to F6 in the section above; each is in `docs/NOW.md`'s backlog):
    - best-of-N: a candidate's junction is staged into its patch by `git add -A` (F6), and its worktree stays in the scratch folder until the sweep, which no longer deletes through it;

    - nothing stops a walking process of the harness at the kernel when it meets a junction (Windows' RedirectionGuard was not tried); the walks fixed here rely on reading the listing first;
    - Node's asynchronous `fs.rm` (what rimraf uses) can delete through a junction on EPERM; the harness runs under Bun and uses the synchronous form (F5 measured the synchronous one only).
