# Unattended runs are contained: a throwaway home, a low-integrity token, judged paths, a record written first, and an integrity latch

**Date:** 2026-11-23 (built 2026-11-23 to 2026-11-24 in nine slices)
**Status:** Built and unit-tested; not merged; not proven on this PC (the acceptance has been run only without live fire; its live-fire and real-profile stages, below, have not). Merging waits on the owner's yes to the capabilities an unattended run loses (decision sheet item 2), which this record is to quote with its date before the merge. Asked for by the owner after F242 as six requirements; a seventh (a decision model on a second PC that answers yes or no before a destructive command) is designed separately and gets only its hook here (the `escalate` verdict).
**Guard:** `engine/__tests__/guards/containmentWiring.test.ts`, `engine/__tests__/guards/containmentDefaultsAreNotLive.test.ts`, `engine/__tests__/tools/containmentAttacks.test.ts`, `scripts/__tests__/cynco-containment-acceptance.test.mjs`, `scripts/__tests__/cynco-campaign-integrity.test.mjs`, and each layer's own tests (named under each mechanism)
**Source:** `docs/cynco-failure-log.md` F242. The owner's decision sheet of 2026-11-23 is kept with the recovery notes, outside the repository (`C:\cynco-recovery-2026-11-22\phase3\final\owner-decisions.md`); its items are cited here by number.

## What was there

A mission ran with approve-all, a shell holding the owner's environment and token, file tools that wrote wherever a path pointed, one deletion pattern in a text check that calls itself "NOT a sandbox", and its only record of tool input inside the home folder. On 2026-11-22 one Bash call deleted the 25 dot-folders of the home folder, about 285 GB, and the record of the command with them. The mission then ran 108 more turns, about 2 hours 10 minutes, and nothing noticed.

## What the owner can do afterwards

Leave a campaign or a daemon mission running unattended and know that (a) a command aimed at the home folder is refused before it runs and, if the refusal misses it, is denied by Windows on NTFS or lands in a throwaway folder; (b) if a protected folder changes anyway, the run stops within about a minute (a lost folder) or the latch is written at its end (any change), and nothing more unattended starts; the latch pages the owner when the process that writes it holds `CYNCO_NTFY_URL`, and otherwise the page waits in the guard folder until the daemon sends it, which the services script does not start under a latch (decision sheet items 22 and 26); (c) what every tool call was asked to run can be read afterwards from a log outside the home folder, written before the call ran. To be shown on this PC by `bun scripts/cynco-containment-acceptance.mjs --stage fake` and its real-profile stage, with their printed evidence. **None of this has been shown on this PC yet** (see Verification).

## Scope

Unattended runs only: a dispatched mission, a daemon one-shot (`--run-task`), the daemon's precheck, the campaign runner's ideation one-shot and its graders, calibration and the authoring runner's gate runs. One predicate says whether a process must become a contained run (`isContainedRun`, `engine/missionEnv.ts`); whether it is one is the run context (`runContainment()`, `engine/containment.ts`), which is the only thing any layer consults, so a message typed into a mission engine's chat box without the `unattended` flag runs contained too. Interactive sessions, the phone engine and project chats are not contained, by design; three things reach them anyway (decision sheet item 15): the sealed, immutable and secret checks now read nested path keys, patch headers, decoded payloads and real paths in every mode (a commit message that spells a sealed gate's file name is refused; a secret refusal now wins over an approval); a profile save is refused while an unattended run is open; and `scripts\cynco-services.ps1 start daemon` is refused under the integrity latch. An unattended run that cannot be given every layer is refused with a named reason before any model call (the F140 shape). There is one switch, `LOCALCODE_CONTAINMENT_OFF`, with the words `lowil` and `paths`; it is honoured only for a context a test built, and a real run in which it is set at all is refused. One variable widens what a run may write: `CYNCO_MISSION_ALSO_LABEL`, a `;` list `scripts/dispatch-mission.sh` hands to `cynco-sandbox.mjs create` as `--also` (extra roots labelled low for the run). Only `scripts/cynco-gate-author.mjs` sets it (the BASE archive of an authoring mission), but any shell that runs the dispatch script can; every folder it names passes the same refusals of `establishContainment` as a mission folder (below), and no tool child ever holds it (`toolEnv` drops it in every mode). The audit and the integrity layer cannot be switched off.

## What it adds, and the six questions

**The run context, the per-run sandbox and the low-integrity launcher** (`engine/containment.ts`, `engine/lowIntegrityLauncher.ts` with its own `engine/lowIntegrityLauncher.bunfig.toml`, `scripts/cynco-sandbox.mjs`; `<LOCALCODE_SANDBOX_ROOT, default C:/cynco-sandbox>/<run id>/{home,tmp,scratch}` and a `containment.json` record per run).
- *Problem*: a tool process needed somewhere to write that is not the owner's home and a token that cannot write the owner's files; every layer needs one answer to "is this a contained run".
- *Why the existing thing is insufficient*: `CYNCO_HOME` moves the engine's state, not a tool's `~` (and redirecting `HOME` for the engine itself moves its tokens, profiles and binary: F161, F241); `C:\tmp` is shared by every mission and by the owner; the per-message `unattended` flag is absent on a message typed into a mission engine's chat box; the engine's Job Object ends processes, it does not limit what they write.
- *State, dependencies, failure modes*: one folder and one record per run, written by the starter at the engine's integrity; `icacls` and `bun:ffi` on Windows (part of Bun, no new package). `toolEnv` sets `HOME`, `USERPROFILE`, `HOMEDRIVE`, `HOMEPATH`, `APPDATA`, `LOCALAPPDATA`, `TEMP`, `TMP`, `TMPDIR` and `CYNCO_SCRATCH` into the sandbox and never deletes them (with the keys absent node's `os.homedir()` answers the real home, measured); `GIT_CONFIG_GLOBAL` is a file in the sandbox that includes the owner's, so commits keep an identity and `git config --global` cannot touch the owner's file. The launcher lowers its own token, reads the level back, makes every inherited handle but its three standard ones non-inheritable (a child could read a medium Git Bash's environment through one, measured), then starts the child; it is started from the checkout with `--no-env-file` and its own config, so a `bunfig.toml` or `.env` planted in a mission folder runs nothing at the engine's integrity. A launcher that cannot run exits 197 and a vanished child 198, each followed by a per-spawn seal line only the launcher holds (`CYNCO_LAUNCHER_SEAL`, an environment key that is not a switch); a launcher that could not run reads as "did not run", never as a failed check (F35). That a low child cannot read the seal from the launcher's memory was measured (it cannot open the launcher or its starter with any right that reads memory). Each contained command costs the launcher's start, measured at about 30 ms on top of a PowerShell start. A label is set on a folder root with inheritance and never with `/T` (measured: `icacls /T` carried the Low label through a junction into a folder outside). Release relabels the root and walks the folder, never entering a link, resetting every label the run set itself (measured at about 32 ms per non-empty folder, so a repository of a few hundred folders adds seconds to each release); a folder still reading low with no live run holding it, and a folder holding a file with more than one name (a hard link carries the label to every name), are refused. A run that dies keeps its label until the next dispatch or daemon start releases it. The sweep is the one recursive delete this change adds to the engine: sandboxes older than seven days, direct children of the sandbox root that carry their own record only, a link removed without being entered.

## A mission folder that is refused

`establishContainment` refuses, each with a named reason, a mission folder (or a folder handed in with it) that does not exist; is, contains or is inside the checkout the engine runs from; is the home folder or contains it; is a volume root, on a network share, or on a volume integrity labels cannot protect; is, contains or is inside the guard, audit, models or sandbox-root folder or CynCo's state folder (except below `<state>/authoring`, the authoring mission's staging folder); is inside a dot-folder of the home folder (same exception); holds a link to a place outside itself in its top two levels; holds a file with more than one name; still reads low with no live run holding it; or, for a mission, is not the top of its own git repository. A sandbox is refused while a volume without integrity labels is attached and not named in `LOCALCODE_UNPROTECTED_VOLUMES_OK`. A daemon task that names no `cwd` is refused. The daemon's two-hourly precheck never labels the mission folder. `establishContainment` does not ask Task Scheduler what runs from a folder: the setup script does, once, and prints STOP for every scheduled action inside a daemon mission's folder (decision sheet item 5).

## New authority

CynCo stops its own campaigns, dispatches and daemon missions by itself, kills a running one-shot, ends a mission's turn, and pages the owner, when a protected folder changes. It sets and removes an integrity label on a mission's repository. It refuses a model's tool call on its own judgement of a path. It deletes sandboxes older than seven days, mission logs older than 90 days in `C:/tmp`, and the previous `.1` of a service log at rotation.

## Review triggers this change sets off (`AGENTS.md`)

- A separately running process per contained tool call (the launcher), and a new launcher for a service (`scripts/run-daemon.cmd`).
- Three persistent stores outside the home folder (the sandbox root, the guard folder, the audit folder).
- Seven environment variables: `LOCALCODE_SANDBOX_ROOT`, `LOCALCODE_GUARD_DIR`, `LOCALCODE_AUDIT_DIR`, `LOCALCODE_MODELS_DIR`, `LOCALCODE_CONTAINMENT_OFF`, `LOCALCODE_UNPROTECTED_VOLUMES_OK`, `LOCALCODE_MISSION_RUN_ID`; `CYNCO_MISSION_ALSO_LABEL`, read by `scripts/dispatch-mission.sh`, which widens the folders a run may write (set by `scripts/cynco-gate-author.mjs`; see Scope); three environment keys that are not switches: `CYNCO_LAUNCHER_SEAL`, `CYNCO_SCRATCH` (set in every contained child to its scratch folder) and `LOCALCODE_CONTAINMENT_REAL_PROFILE` (read by the acceptance script only).
- Shared mutable state across packages: the fault sink and the audit writer cores (`toolAudit.ts`), the judged-input map (`protectedPaths.ts`), the tripwire (`integrity.ts`).
- Cross-cutting behaviour at every site that starts a process for a run, and in every tool call of a contained run; three capability words the driver refuses on (`contained-tools` or `contained-overlay`, `path-guard`, `tool-audit`); the sealed, immutable and secret checks refuse more in every mode.
- Autonomous authority to halt dispatch, end a run, kill a one-shot, page the owner, change integrity labels and delete files (above).
- Removed capabilities (below).
- An hourly timer in the daemon that pages.

## Capability removed

The owner's yes: **not yet given.** Decision sheet item 2 is BLOCKED for the merge until it is, and it is quoted here with its date when it is. An unattended run no longer has: the real home (no SSH keys, so no `git push` over SSH; no user-level tool configuration; no `pip install --user`; empty package caches in each sandbox); any program of Git's Unix runtime on Windows (`bash`, `sh`, `grep`, `sed`, `tail`, `head`, and git hooks written as shell scripts: measured, they cannot start at low integrity while any ordinary Git Bash runs, and the dispatch script is one); writing to `C:\tmp`; a mission folder that is a git worktree, not the top of a repository, or inside the engine's checkout (a mission on CynCo itself works in a clone made with `git clone --no-hardlinks`); a daemon task with no `cwd`; the driver pointed by hand at an engine it did not start. ## Where the requirements were narrowed, and why

- "Executions must land inside the roots" became: a script or program operand outside the roots is refused only when it lies in the always-denied set. A script outside the roots is one the run could not have written, and the authoring check is such a script. The stricter rule (an unclassified operand outside the roots, T6a and T6aExec) was measured by the reviewer at 9 and 3 of the owner's 3,342 past commands and would refuse two must-pass rows of the specification (scan.py over site-packages, the authoring check); it was not adopted. A lexical net over inline calls that look like mutations was measured at 111 refusals and not adopted.
- `GIT_CONFIG_GLOBAL` is an include file in the sandbox, not the owner's file (decided for the owner, item 4).
- Under the latch only the daemon is refused a start by the services script; the phone engine and the dashboard keep working, because the owner needs them then (decided for the owner, item 10). Whether the daemon, the one process here that holds the doorman's page address, may start under a latch is the owner's (decision sheet item 26, review finding 4.M1; as built, it may not).
- `~/.ollama/models` is watched for loss only, not frozen: processes outside any run add to it.
- The copy of the audit log on the NAS is cut from this change.
- The `env` rule of `bashSafety.ts` is left exactly as it is.
- The stream debug log stays in the run's working folder, capped and refusing links; a review recommended moving it out, and that is open.

## Rejected alternatives

- **More patterns in `bashSafety.ts`.** The failure mode the 2026-11-06 record already names: it judges spelling.
- **A separate Windows user for missions.** A stronger boundary than a label, and exFAT would still be open to it; it needs a second profile, credentials and a logon for every tool call. Kept as the next step if low integrity proves too weak.
- **A container or a virtual machine.** The mission needs the GPU's model server, the repository and the Python user site; nothing in the repository runs that way today, and the owner has ruled Docker out on this PC.
- **Redirecting `HOME` for the engine itself.** `cyncoHome()` follows it; the engine would lose its tokens, profiles and binary (the F241 class).
- **An off switch a dispatch can carry.** Both earlier security records refused one; a switch that widens what an unattended run may do is the thing that will be set on the night it matters. The one widening a dispatch does carry, `CYNCO_MISSION_ALSO_LABEL`, switches no layer off: it names extra folders, each refused as a mission folder would be (see Scope).
- **Observe, then advise, then enforce** (`AGENTS.md`, "What a mechanism is"). That ladder is for experimental policy. This is a boundary asked for after a loss; it refuses from the first commit. What is unmeasured is said below.
- **Anything of CynCo's on `D:`.** It is the owner's camera drive.

## What it does not cover

1. Reading is not restricted, and the network is open. A contained run can read `~/.ssh`, `.env` files, every log and `~/.cynco/tokens.json`, and can send them anywhere; with the token file it can ask the engine's own loopback API, a process at the engine's integrity, to act for it. This change protects against destruction, not against disclosure.
2. The file tools have one layer. Write, Edit, MultiEdit, NotebookEdit, ReplaceFunction and ApplyPatch's own writes run inside the engine with its token and the real home. Only the path check stands in front of them; it is exact for them, but a bug in it is a direct write anywhere.
3. Drive `D:` and the NAS are not protected by Windows. Integrity labels exist on NTFS only. What stands in front of them: the path check (it reads text), the manifest of their top level (detection afterwards, at the end of the run), and the refusal to dispatch while such a volume is attached and not acknowledged by name. Acknowledging it does not protect it: in a run with such a volume acknowledged, an inline program's write through a path it computes (`open(chr(68) + ':/DCIM/a.jpg', 'w')`) is only escalated, run and logged, because the drive is not in its text. A real block is the owner's to choose: a second copy of the videos, the volume read-only or detached while unattended runs are enabled, or NTFS (decision sheet item 1).
4. The shell half of the path check reads text and can be walked around by anything that does not spell its target: a script written and then run, a module run with `-m`, a path a program computes, a name set in one call and used in the next. On NTFS the overlay and the token stand behind it; on `D:` and network shares nothing does. It has been attacked in nine review rounds, each of which found walk-arounds; the rule since the sixth is under "The protected-path check" above.
5. Programs that act for a caller at their own level were not tested: Docker, WSL, Task Scheduler, WMI process creation, out-of-process COM servers (decision sheet item 12).
6. Unattended is narrower than "nobody is watching". Not contained: `bun engine/main.ts --run-ablation`, the benchmark harness loops, and any engine a person starts with `LOCALCODE_APPROVE_ALL=true` (decision sheet item 10).
7. Code a run leaves behind is run later by others. Tests, scripts and launchers the run wrote are executed afterwards by the owner with the real home, and the fantasyman launchers by Task Scheduler at logon (decision sheet item 5). The harness's own git is neutralised by a list, which is a list.
8. One contained run can write another run's sandbox, and any folder labelled low at that moment; only the path check stands in front of that.
9. The integrity check detects, after the fact, and coarsely. Not seen: a file lost or altered outside the FROZEN folders, a folder emptied below its first level, a FROZEN file rewritten with its size and time restored (`verify --deep` sees that for the models only), anything in a `.git` or `__pycache__` folder inside a FROZEN root, anything that happens while no run is open, who did it, and up to a minute (or one second of tool calls) between two looks of the tripwire. Volume roots are keyed by drive letter, so another volume at `D:` reads as the camera drive's entries gone.
10. Evidence can still be destroyed by an uncontained process: `C:\cynco-audit` and `C:\cynco-guard` are ordinary folders, and the audit has no copy off this machine.
11. A low child holds terminate rights on its launcher and on the engine (measured): it can kill them. A launcher killed that way leaves no seal line and reads as the command's own status, never as a forged "did not run"; it is a denial of service, not a way out.
12. The Windows layer is proved by hand, not by CI, and has not yet been proved by hand. The real-profile stage proves refusal, not survival: no deletion is ever executed against the real profile.
13. Off Windows there is no kernel layer; the engine says `contained-overlay`.
14. PowerShell 7 is not installed and was not measured. The Bash tool prefers it when present, and it may resolve `~` and `$HOME` without the variables. Run the acceptance again before installing it (decision sheet item 24).
15. What was lost stays lost: the 13.5 hours between the snapshot and the deletion, and the command text of 2026-11-22.
